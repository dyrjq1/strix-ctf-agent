## 三、口径说明

- **solved** 以平台 `my_fully_solved` 为准（`list_competition_challenges` 字段）。多问题题（如 003 的 `flag`+`technique`）拿一半只能记 `half`，不能记 `solved`。009 已核对：仅 `flag` 一问，`my_fully_solved=true`，算完整解出。
- **solve_time_s** 取平台 `submit_answer` 返回值，不用本地墙钟（两者差 ~12s，本地含起实例）。
- **checkpoint** 分五档：`recon`（拿到技术栈与至少 3 条真实路由）→ `surface`（知道有哪些方法可用）→ `contract`（知道参数名与类型）→ `exec`（有代码执行/文件读/DB 读）→ `flag`。任何一次"未解"都要标停在哪一档，否则无法区分"方向对但没跑完"和"完全没方向"。
- **provenance** 记 flag 首次出现的工具输出及其来源 host。来源 host ≠ 本题 target，或 flag 在第一次交互就出现，一律标 `suspicious`（对应 CTF-ABACUS 的 shortcut 判定）。

### 4.18 P24 `method_sweep` 断连丢证据（2026-10-31 夜，已修）

**怎么发现的**：框架文档 v4 的收尾检查里，`tests/test_discovery.py` 全量跑偶发红
（单文件跑必过）。起初怀疑是测试间共享状态；实测 400 轮直连探针后定位为真缺陷。

**根因（两个叠加）**：

1. 靶机在参数校验失败时**不等请求体读完就回包并关连接**，客户端还没发完 body 就收到
   RST（Windows 10053），**连已到达的 400 响应一起丢掉**。实测 `data=b"{}"` 约 5% 命中，
   `data=None` 0/300。
2. 旧代码 `except` 里直接 `return {"status": 0}`，`interesting()` 又把 `status == 0`
   当成「有信息量」输出成 `ERR` 行——**语义上把「没测到」和「这个方法不存在」混成了一件
   事**。而丢掉的那一行，往往就是「这个路径上存在 POST」的全部证据（CTFARENA-009 的
   `POST /api/plugins/preview` 正是这么被找到的）。

**修法**（`src/ctf_strix/discovery.py`）：body 型请求给三次机会，前两次 `b"{}"`，
**最后一次降级为空 body**（少的是「字段名」这一层，保住的是「有这个方法」这一层）；
全部失败才记 `status=0`，并在 note 里写明 `after 3 tries`。非 body 方法同样重试。

**验证**：

| 检查 | 结果 |
|---|---|
| 新增 `test_method_sweep_survives_server_that_never_reads_body`（连跑 12 次） | 新代码 13/13 绿；**旧代码必红**（反例验证，不是改测试迁就代码） |
| 全量单测连续 8 轮 | 8/8 全绿，`189 passed`（此前 10 轮里 2 次偶发红） |
| 直连探针 300 轮 | `tries=1` 失败 9/200；`tries=3` 失败 0/200 |

**回滚**：`git checkout -- src/ctf_strix/discovery.py tests/test_discovery.py`。

**教训**：「测试偶发失败」先当缺陷查，再当环境问题放。这次差一点被归成
「Windows 临时目录权限问题」放过——那会让 agent 在正式赛里继续静默丢证据。

### 4.22 软截止收尾死锁：一个会污染所有时间数据的 bug（2026-10-31 夜，已修）

**怎么发现的**：第二轮扩样的 074/GLM 日志里出现了自相矛盾的三行：

```
[done] 218.9s  result=RunResultStreaming
[guard] ... finish: refused=0 allowed=1
[usage] calls=22 in=1041311 out=13346 total=1054657

[WALLCLOCK TIMEOUT after 600s]
```

`[done]` 说明 `run_strix_scan` 已经返回、`finish_scan` 已经放行、用量已经打完，
可进程又空等了 381 秒才被墙钟杀掉。缺失的那一行是 `[deadline]`。

**根因**：`DeadlineGuard.snapshot()` 在 `with self._lock:` 里面调用了
`should_kill()`，而后者又会 `with self._lock:`。`threading.Lock` 不可重入，
于是最后一次打印成了自死锁。

**影响面**：只要 `--soft-deadline > 0` 就必现。两个后果都致命：

1. 时间数据全错——解出的题被记成"墙钟打满"；
2. 结论反转——074/GLM 真实 62s，被记成 600s，于是得出"GLM 慢 15 倍"的错误结论，
   并写进了 4.20 的初版。

**修法**：先取锁算状态，出锁后再调 `should_kill()`。

**回归测试的写法**（这次的重点）：`tests/test_deadline_snapshot.py` 除了 4 条正常路径，
还有 1 条反例——把**旧实现**装回去，在工作线程里跑带 1 秒超时的 `snapshot()`，
断言它必须被判死锁。这样即使以后实现又改回旧写法，测试也不会"因为新实现修好了"
而默默通过。实测：新实现 0.03s 返回，旧实现超时被捕获。

**修复后重跑（可用数据）**：

| 题 | 模型 | 结果 | 工具 | agent 墙钟 | solve | token |
|---|---|---|---:|---:|---:|---:|
| 074 | GLM | ✅ | 11 | **62.1s** | 72.8s | 350,322 |
| 074 | DeepSeek | ✅ | 14 | **42.9s** | 51.6s | 437,479 |
| 095 | DeepSeek | ❌ | 26 | 600.1s | — | 1,871,949 |
| 095 | GLM | ✅ | 21 | 252.6s | 263.9s | 1,014,368 |

**教训（比 bug 本身更值钱）**：一次 A/B 里如果某条臂"解出但耗时打满"，
先怀疑测量而不是模型。此处三条独立信号同时指向 bug——`[done]` 与
`WALLCLOCK TIMEOUT` 并存、`[deadline]` 缺行、`usage.json` 的 mtime 比
`run.log` 早 6 分钟。任何一个单独看都像噪声，三个一起看就是确证。

### 4.25 上下文管理：一次被数据否决的优化（2026-11-01）

**目的**：验证"压缩历史"在 DeepSeek prefix cache 计费模型下到底省不省钱。

**背景**：上轮把 043/047 的 2.2M input 归因为"历史重发的平方增长"，据此写了
按龄裁剪（最近 N 条原文 / 更早头尾截断 / 更早一行存根）。

**做法**：同题 043、同模型 DeepSeek-V4.1-Flash-1017、同 40 轮 / 1000s，跑三臂。

| 臂 | 配置 | 请求 | 工具 | raw input | cache hit | 命中率 | 等效成本 | 墙钟 |
|---|---|---:|---:|---:|---:|---:|---:|---:|
| A | 短提示 + 裁剪未触发 | 40 | 42 | 1,735,886 | 1,660,416 | **95.7%** | **108,678** | 342s |
| B | 按龄裁剪 v3 | 40 | 43 | 1,580,500 | 914,048 | **57.8%** | **684,733** | 595s |
| C | 幂等内容封顶 | 40 | 55 | 1,838,512 | 1,717,888 | **93.4%** | 154,982 | 504s |

等效成本 = \`hit x 0.02 + miss\`（DeepSeek 官方价：hit \`$0.006/M\`、miss \`$0.3/M\`，差 50 倍）。

**结论（否定）**：按龄裁剪是负优化。raw token 只降 9%，等效成本涨 6.3 倍、墙钟涨 74%，
**解题率完全没变**（三臂全 FAILED）。

**根因**：DeepSeek 缓存按"完整前缀单元"匹配，\`A+C\` 命不中 \`A+B\`。按龄裁剪让同一条
历史在第 10 轮是原文、第 11 轮截断、第 21 轮存根——**每跨档位前缀就整体改变一次**。
逐请求命中率曲线：A 全程 92-99%，B 从第 8 轮起塌到 40-50%。

**修复**：改成逐条、按内容、与位置无关的封顶（\`HistoryCapper\`），保证第 N+1 轮请求
是第 N 轮的严格前缀扩展。实测命中率回到 93.4%，\`capped_requests 18/40\`、
\`saved_chars 352,919\`。

**另一个发现**：DeepSeek-V4.1-Flash 上下文 **1M**，40 轮峰值仅 **74,263** token，
**不存在溢出**。这解释了 strix 自带 \`maybe_compact\`（阈值 180k）为何从未生效——
不是 bug，是这个场景压根不需要它。

**局限**：三臂都是 n=1，且工具调用数不同（42/43/55），raw input 不可直接横比。
可比的只有命中率。C 臂工具更多是模型行为差异，不是封顶导致的。

**下一步**：上下文线**到此为止**，不再投入。瓶颈在行为判据（见 \`docs/21\` §7.3、
\`docs/20\` P20-b/c/g）。

### 4.28 校准暴露的三个真 bug（2026-11-01，按严重度）

#### P0 · `sweep_guard` 从未接线（已修）

`sweep_guard.py` 只有 `sweep_summary()` / `hint_for()` 两个**纯函数**，既没有
`install()`，也没有任何地方 import 它们。而 `enum_guard` 是按**调用**去重：

```
[guard] enum_keys: ?, enum_hits: 0     ← CTFARENA-050 实测全零
```

050 的做法是把几万个候选路径塞进**一条** `exec_command` 的 Python 脚本里循环打。
在调用层看是 1 次探测，在语义层是同一个假设重试 36,000 次——`enum_guard` 的计数器
永远够不到阈值。**这是"守卫装了但等于没装"的第二次复现**（第一次是 012 的
`_with_bounded_result` 挂不到 `exec_command`）。

修法：给 `sweep_guard` 加 `install()`，挂在与其它守卫相同的
`factory._with_bounded_result` 上；命中即在结果尾部追加提示（不拒绝，理由同
`enum_guard`：拒绝会让模型重发）。同时把它登记进 `guard_mount.verify_mount()`
的期望标记，让"没挂上"在启动时就出声。

#### P1 · 跨套件路由硬编码（已修，见 §4.29）

### 4.29 跨套件路由：静态表 → 平台自述兜底（2026-11-01，已修）

**现象**：calib1 的第 1、3 题（XBOW-052 / XBOW-007）以
`KeyError: 前缀不在已知 suite 表里` 秒退。结果表上看是 `FAILED`，实际是**根本没跑**。
这类"看起来是评测结果、其实是选题崩了"的数据，比没有数据更危险。

1. 静态表保持快路径（批测每题都要路由，不该每题发一次 HTTP）；
2. 未命中 → 进程级缓存 → `GET /api/v1/suites` 实时解析，按

3. 前缀匹配**最长优先**（`AGENT-DEFENSE-001` 不能被假想的 `AGENT` 抢走）；
4. 仍解析不出才抛错，报错里带已此前缀清单。

**验证**：`_fetch_suite_map()` 线上拉到 13 个套件；`XBOW-052/007`、`CTFARENA-080`、
`SQLILABS-064`、`AGENT-DEFENSE-001`、`MMLU-CS-0001` 全部路由正确；`NOPE-1` 按预期
报错并列出已知前缀。单测 5 条（快路径不发请求 / 兜底解析 / 最长前缀 / 报错带清单 /
标题规范化），`tests/test_batch_eval.py` 17 passed。

**复跑结果**：两道 XBOW 题路由正常后，暴露出**下一层**问题——它们是
`access: vpn`（只给 `xxx.internal`），所以仍然跳过。但这次跳过的理由是对的
（`SKIPPED(需隧道)`），并且是 P2 的证据。

### 4.31 `sweep_guard` 接线：修好了，但没解出（2026-11-01）

**一句话**：接线是真的断了，修好之后守卫确实介入了（9 次），**但 050 仍然失败**。
这次修的是"看得见看不见"，不是"解不解得出来"。

#### 断在哪（两个独立缺陷，都必须修）

**缺陷 1 · 没有 install()**。`sweep_guard.py` 只有 `sweep_summary()` /
`hint_for()` 两个纯函数，模块文档写得很完整，**但没有任何地方 import 它们**。
判定逻辑再对，没人调用就等于零。

**缺陷 2 · 拿到的是转义后的参数**。补上 `install()` 之后仍然 0 命中。原因是
`on_invoke_tool(ctx, raw_input)` 里的 `raw_input` 是**JSON 序列化后**的字符串：

```
真实参数:      a=["api","v1"]        ← 正则能匹配
到手的样子:    a=[\"api\",\"v1\"]    ← 引号前有反斜杠，匹配失败
```

字面量正则 `["\']([\w./:-]+)["\']` 在左引号能匹配、右引号前多一个 `\`
就失败，于是**整条调用的所有字面量全部丢失**。1440 个候选路径被判成 `None`。
这是同一个教训的第三次复现：**守卫的输入形态，必须用真实调用的原始串验证过**。

修法：加 `_normalise()` 做反转义（只做替换，不解析 JSON——参数可能被截断）。

**缺陷 3 · 规模估算恒等于硬阈值**。`_generated_sweep` 末尾写的是
`return "generated", max(estimate, SWEEP_HARD)`——下限直接顶到硬阈值，
于是"两个正则都命中"就等于"硬爆破"，估算形同虚设。代价是
`for i in 1 2 3; do curl ...; done` 也会被判成 8000 次扫描。
实测误伤 **1/10**。提示一旦恒亮，模型就学会忽略它，比不装更差。

修法：改成四条独立线索取最大（字面量数 / 同变量 `product` 平方 /
推导式数 / `range(N)` 上界），低于起步阈值不报。

#### 三个缺陷的判定证据（回放 + 实测）

| 阶段 | 回放 050 上一次日志（18–25 次调用） | 误伤（10 条正常调用） |
|---|---:|---:|
| 原始（无 install） | 0 命中 | — |
| + install（无反转义） | **0 命中** | 0/10 |
| + 反转义 | 3 命中（wordlist 27/25、generated 80） | 1/10 |
| + 估算修正 | **3 命中** | **0/10** |

#### 端到端复跑（同题同预算：`--turns 25` → medium 40 轮 / 1350s）

| 臂 | 守卫命中 | 工具调用 | agent 墙钟 | token | 结果 |
|---|---:|---:|---:|---:|---|
| 修前（`calib2` 第 6 题） | **0** | 44 | 577.0s | 1.26M | FAILED |
| 修后（本轮） | **9** | 62 | **1033.7s** | — | **FAILED** |

`[guard] reach=109`（守卫被调用 109 次）、`finish_refused=3`（收工守卫拒了 3 次）。

**必须说清的两件事**

1. **它确实改变了行为**。命中之后模型从"继续暴力扫"转成了逐条假设验证：
   `/secret/alice`、`/vault/alice`、`token=`/`jwt=`/`access_token=` 三种参数名、
   `Host: vault-api` 等 —— 都是在测假设，不再是纯枚举。
2. **但它没有解出**，而且**花得更多**（577s → 1034s，44 → 62 次调用）。
   所以本轮**不能声称"提升了能力"**。按 `docs/23` 的判据，这属于
   "接线类修复"（正确性由"有没有生效"判定），不是能力改进。

**为什么仍然值得修**：修之前，`sweep` 这条线在所有题上恒为 0，与"今天没触发"
无法区分；修之后它至少是一个可观测、可 A/B 的变量。**下一步才是真正的课题**：
提示该说什么、在什么时机说，才能让模型**真的换机制**而不是换个姿势继续扫。
这需要多题样本，不是一题能定的。

### 4.32 TCP 题接入通路：从「一律跳过」到「一条命令拿 flag」（2026-11-01）

**这一条是今天唯一可归因的能力增量。**

#### 断在哪（一行代码，代价是 0 分）

`batch_eval._public_url()` 对所有 service 一律拼 HTTP URL：

```python
scheme = "https" if svc["service_type"] == "https" or svc["port"] == 443 else "http"
return f"{scheme}://{host}:{port}/"        # 端口 1337 的原始 TCP 服务 → http://host:1337/
```

于是一道「连上去、读 banner、发 `flag`」的 TCP 题，交给 agent 的是**一个 HTTP URL**。
它用 curl 打，拿到乱码或超时，然后在"是不是 TLS / 是不是路径写错"上烧预算——
日志里看不出任何异常，结果表上只是一行 `FAILED`。

`ctf_strix.tcp_bridge.TcpBridge` 和 `ctf_strix.vpn.VpnTunnel` 早就写好了
（`scripts/eval_sample.py` 在用），但**批测走的另一条更早的路径**，只认 HTTP。

#### 修法（接线类，共 5 处）

1. `is_tcp_service(svc)`：按 `service_type` 判 TCP，字段缺失时按端口兜底
   （非 80/443/8000/8080… 视为 TCP）。
2. `wait_ready()` 对 TCP 返回 **service 字典**而不是 URL（调用方才知道桥的生命周期）。
3. `main()` 建 `TcpBridge(...).start()`，把靶址换成 `127.0.0.1:PORT`，`target_kind="tcp"`。
4. `run_agent()` 新增 `--target-kind`，让 `run_strix_ctf.py` 用 TCP 目标模式
   （否则桥建了、子进程仍按 web 打，等于没建）。
5. `_probe_tcp()`：用 socket 探连通，读 banner。**不能用 HTTP 探测**——
   它会读到 `CTFy TCP test service` 解析失败，判"不可达"，把好题换掉。

#### 实测（同题同预算 `--turns 25` → easy 25 轮 / 900s）

| 题 | 修前 | 修后 |
|---|---|---|
| SAMPLE-014（tcp / connectivity / easy） | **SKIP 需隧道**（0 分，0 次调用） | **SOLVED**，5 次调用 / 21.8s |
| CYBENCH-011（pwn / format_string / easy） | SKIP 需隧道 | 仍 SKIP（`access=vpn`） |

SAMPLE-014 的日志首行即为：

```
ready in 19.9s -> tcp bridge sax2ekljbmotjmpa7.node1.ctfy.run:443 (tls_sni) => 127.0.0.1:45623
可达 (tcp open banner='CTFy TCP test service\n>')
-> SOLVED  tools=5 agent=21.8s
```

**手工旁证**：直接用 `TcpBridge` 连同一实例，一次交互就拿到
`FLAG{b904fb3c…afcd}`——说明这条题从来就不难，
难的是"让 agent 看见它"。5 次调用也印证了这一点（成功题 p50 是 9–16 次）。

#### 覆盖面（为什么值得修）

| 接入方式 | 能否直连 | 题量（非 QA） | 修前 | 修后 |
|---|---|---:|---|---|
| `public_port` / `tls_sni` | 能 | SAMPLE 的 014/015，部分 CYBENCH | 当 HTTP 打，必挂 | **可测** |
| `vpn` | 否（需 WireGuard） | CYBENCH 大部份、XBOW 少量 | SKIP | 仍 SKIP |
| `web` | 能 | 375 道 | 正常 | 正常 |

按 `GET /challenges` 实测：非 QA 383 道里 `category=web` 375，非 web 只有 8 道
（都在 SAMPLE）；CYBENCH 40 道标 `web` 但实为 TCP 二进制题。也就是说
**「非 web 能力」的可见样本一共只有约 48 道，而其中 44 道要 VPN**。

#### 诚实结论

- 这条修复让 **SAMPLE-014/015 与少量 public_port 的 CYBENCH 题**从"测不了"变成"能测"，
  是**真实增量**，但样本只有个位数，不足以说"非 web 能力提升了 X%"。
- 真正的天花板仍是 **VPN 隧道**：44 道题卡在那里。隧道已验证能 `up`（`ip addr` 有地址、
  路由有 `172.16.4.0/24`），但对端 **0 字节回包**（`wg show` 显示 `0 received`）。
  卡点已定位在下一次要查的地方：平台 UDP 中继是否要求先 `POST` 激活、或源 IP 绑定。
- 按 `docs/23` 判据，本条属于**接线类修复**（正确性由"有没有生效"判定，不需要 A/B）。

#### 回归

- `tests/test_batch_eval.py`：**21 passed**（新增 4 条：TCP 不被当网页、socket 探测

### 4.33 VPN 通路接进批测（2026-11-01，已打通）

#### 结论先行

`access: vpn` 的题**能跑了**。CYBENCH-011 端到端：

```
ready in 25.8s -> tcp bridge 172.16.3.2:1337 (vpn) => 127.0.0.1:38907 via wg49042
可达 (tcp open banner='\x1b[2J\x1b[0;0H      🟨🟨🟨')
-> FAILED  tools=26 agent=290.8s
```

环境零错误，失败发生在**解题策略**层，不是接入层。这是本节最重要的一句：
以前 44/48 道非 web 题"没跑过"，现在它们有资格进评测了。

#### 修了什么（`batch_eval.py`）

| 改动 | 为什么 |
|---|---|
| `Client.vpn_config(iid)` | 拉实例级 profile；`eval_sample.py` 早有，批测没有 |
| `is_private_service(svc)` | `.internal` 判定独立成函数，`wait_ready` 与 `_attach` 共用 |
| `wait_ready()` 私有域名 → 返回 service | 原来直接抛 `TunnelRequiredError` 整题跳过 |
| `_attach(iid, svc, client)` | 隧道 up → DNS 解析 → `TcpBridge` → 返回 `(bridge, tunnel, target, kind, host, access)` |
| `finally` 先 `bridge.stop()` 再 `tunnel.down()` | 顺序反了会让桥的转发线程挂在死 socket 上 |
| 模块顶部 `sys.path.insert(0, ../src)` | 主进程要 import `ctf_strix`；缺这行直接 `ModuleNotFoundError` |

#### 真因：AppArmor 拦 `wg` 读文件（踩了两小时）

`wg setconf <if> /tmp/x.wg` 在 **root** 下也报 `fopen: Permission denied`。
排查过程：换权限（600/644）、换目录（/tmp、/home、/etc）全失败 →
`dmesg` 才是答案：

```
apparmor="DENIED" operation="open" profile="wg" name="/tmp/t4.wg"
requested_mask="r" denied_mask="r" fsuid=0 ouid=1000
apparmor="DENIED" operation="capable" profile="wg" capability=1 capname="dac_override"
```

Ubuntu 自带 `/etc/apparmor.d/wg` 只放行 `@{etc_rw}/wireguard/{,**}`，
且不给 `dac_override`。所以 **root 读自己 0600 的文件也会被拒**——
这个错误信息看起来像普通权限问题，实际是路径白名单。

**修法（不放宽策略）**：加一个 20 行的 root 包装 `scripts/ctfvpn-wg`：
从 stdin 收配置 → 写成 `/etc/wireguard/<if>.conf`（profile 放行）→
`wg setconf` → `trap` 立刻删除。私钥不落盘留存。
`vpn.py` 的 `_setconf()` 优先走它，没装则退回临时文件（老路径）。
sudoers 只放行 5 个路径：`ip` / `wg` / `wg-quick` / `dig` / `ctfvpn-wg`。

#### 纪律两条（复用）

1. **不用 `sudo -S` 读密码**。批测无人值守，等密码提示 = 整批挂死。
   用 `sudo -n` + 白名单，拿不到立刻失败并报出真实原因。
2. **批测跑着时不许手动起/删实例**。§4.30 那个错误结论就是这么来的：
   `reap_orphans()` 的前提是"串行批测时任何存活实例都是泄漏"。

#### 这道题为什么还是没解出（不是接入问题）

26 次调用里，**至少 8 次在侦查评测框架**：
`/proc/49042/cmdline`、`/proc/*/environ`、`bench011.jsonl`、`plan011.json`、
`batch_eval.py` 源码、`ps aux`、`ss -lntp`。

它甚至找到了 `172.16.3.2:1337` 直连成功，也正确识别出
"31 字节格式化串、参数在第 8 位"。真正解出需要写 GOT/栈上的运行时标志，
但预算被前 8 次"找题"吃掉了。

**这是通用缺陷，不是这道题特有**：agent 不知道"评测框架不在范围内"，
主机上的 `/proc` 和结果文件看起来像有用线索。已加通用规则到
`config/ctf_goal.txt`（「The grading harness is not part of the challenge」），
明确列出不许读的四类东西。命名测试：不含题号/IP/路径，可迁移。

**但按 `docs/12` 判据，这只是 prompt 改动，还没有在留出集上验证过，
不能声称提分。** 下一轮需要用同一批题 A/B。

### 4.37 失败轨迹逐条读完：主导形态是"自我破坏"和"脚本抖动"（2026-11-01）

#### 形态 A：破坏性探测把自己打瞎（022）

| 步 | 发生了什么 |
|---:|---|
| 19 | 找到 `POST /api/profile/update`，是对象深合并 |
| 20 | `{"constructor":{"prototype":{"isAdmin":true,"polluted":"yes"}}}` —— **一次写进三个键** |
| 21 | 之后**所有**路径返回 500，包括 `/api/任意乱码` |

**关键**：污染确实成功了（回显里能看到 `constructor.prototype` 被写进
`Object.prototype`），但 agent 同时把 Next.js 的错误处理打坏了，
于是**失去了区分"路由存在"和"路由不存在"的能力**，剩下的 10 次调用
都是在盲打。这不是"方向错"，是"自己拆了自己的观测面"。

对照 `docs/12` 的命名测试，这条改动是 G 级：
"进程级状态修改后必须重新确认基线，基线坏了就先恢复再继续"。

#### 形态 B：同一假设换 15 个文件名重写（094）

27 次调用里 **15 次**是 `cat > /tmp/{orig,p,f,h,q,host,c,s,m,x,y,z,w,v,u}.py <<EOF`，
每个脚本都是"同一份 SSL 上下文 + 换一个 header 组合"。第 9 次它还去找
wordlist，说明它自己也不知道下一步要验什么。

`enum_guard` 抓不到这种，因为它按 **host + 路径族** 计数，而这些脚本
打的是同一个 `/api/widgets`，指纹完全相同 → **应该早就触发了**。
需要核实 `enum_guard` 是否真的挂在 `exec_command` 上生效了。
如果生效了还这样，说明"同响应重复"这个判据不够——这里的重复是
**同一脚本、不同 header**，响应体不同（500 vs 200），指纹判"不同"。

#### 形态 C：答案在眼前但读不出来（061）

`/_ignition/execute-solution` 读到 `/flag`，但 Laravel 的异常参数转储
**只显示前 15 个字符**（`FLAG{0829a5e72c...`）。之后 8 次调用都在
做"完整 RCE 好 cat /flag"，最后卡在 phar 的 base64 padding 上。

这类题的正确解法不是"再去搞 RCE"，而是**找一个不截断的回显通道**：
写文件到静态目录、报错页的另一个字段、或者时间盲注逐字符读。
agent 从头到尾没有考虑过"截断"这件事本身，只想着"换更强的利用"。

#### 形态 D：供应链题一次都没碰包索引（067 / 065 / 064）

067（rubygems）31 次调用：目录爆破、wordlist、openssl 证书、`/tmp/*.html` 解析。
065（pypi）29 次调用：找到了 `POST /api/extensions/install` 会执行
`pip install <name>`，然后**枚举包名**，没有一次去碰索引本身。

这和 `docs/19` §7 记录的 064 完全同形：**提示里没有任何一句说过
"这类题的存在"**，模型只能在自己知道的搜索空间里找，而它知道的只有 web 路由。

#### 这四条的共性

不是"预算不够"，也不是"模型不会想"。是**判据缺失**：

- 不知道自己把环境搞坏了（A）
- 不知道自己在一个假设上打转（B）
- 不知道"部分可见"也是一种失败（C）
- 不知道有一整类题的存在（D）

A/B/C 是**运行时判据**，可以写进代码；D 是**知识覆盖**，只能写进技能包。
这两件事的验证方式不同：A/B/C 看同一批题的行为是否改变，D 看新题型是否开始被尝试。

### 4.44 第一批非 web 工具：6 个原语 + 一个"附件题一直没装上工具"的真 bug（2026-11-02）

**背景**：`docs/14` 只做到"装系统工具"，代码侧一直只有一个 `file_triage`。
这一轮把升级包里实测过的非 web 原语落地，原则是**独立重写、不复制**——
`all-directions-pack-20261101` 全包没有 LICENSE 文件（递归查找 `*LICENSE*` 零命中），
所以照行为写自己的实现，注释里标注行为来源。

**新增 `src/ctf_strix/nonweb.py`**

| 工具 | 解决的问题 | 关键设计 |
|---|---|---|
| `decode_blob` | 多层编码靠猜，一层一层手写 | 贪心链 + 0.85 可打印率闸门；rot13 只在与 flag/英文词数比较后采信 |
| `unpack_archive` | 嵌套压缩包一层一个回合 | 魔数识别；四道闸（绝对路径 / `..` / `is_relative_to` / 符号链接）；预算**跨递归共享** 64MB / 2000 文件 |
| `hexpeek` | 容器里未必有 `xxd` | hex + ASCII 双栏，越界/续读都有明确 offset |
| `tcp` | 未必有 `nc` / `pwntools` | 先收 banner 再发 payload（否则 banner 被自己的回显埋掉） |
| `tcp_batch` | padding oracle 要对比 200 个响应 | 一条连接、每行一个摘要，比"200 次调用"省 199 个上下文窗口 |
| `elfpeek` / `elffind` | `readelf`/`objdump` 未必齐，且输出太长 | 纯 stdlib 解析；capstone 可选，缺失时退化为固定模式扫描 |

**本轮从真实题库里查出的 3 个缺陷（不是从文档抄的）**

1. **`file_triage` 从来没装上过。** `function_tool(timeout=120)` 对**同步**函数直接抛
   `ValueError`，而两个入口都用 `try/except` 包着，只打印一行 `registration failed`。
   也就是说所有附件题实际上没有入口原语——与 `guard_mount` 那次是同一个"静默失效"形态。
   修法：`_as_async()` 包一层 `asyncio.to_thread`，`functools.wraps` 保住 schema。

2. **zip 末尾追加数据会被判成损坏。** 真实附件 `1.zip`：EOCD 在 2,379，后面还有
   143,535 字节（polyglot/overlay）。`zipfile` 只扫最后 64KB，直接 `BadZipFile`。
   修法：找到第一个 EOCD 截断重试，并在输出里说明"忽略了 N 字节"。

3. **base64 分行 + 填充位隐写。** 81 行、每行独立编码，整文件解码必然失败；
   而 flag 藏在每行最后一个字符的填充位里（两个 `=` 4 bit，一个 `=` 2 bit）。
   修法：逐行解码兜底 + 填充位还原。实测直接给出 `flag{BASE64_i5_…}`。

**接入位置（web 路径一个字符没动）**

- `agent.py` / `scripts/run_strix_ctf.py`：`kind in ("file", "tcp")` 才注册；
  `file` 装 5 个附件原语，`tcp` 装 2 个 socket 原语。
- `probe_surface.NETWORK_TOOLS`：`tcp` / `tcp_batch` **刻意不进** `PROBE_TOOLS`。
  理由写进代码：`sweep_guard` 在"单次调用 ≥24 个不同取值"时报警，而 `tcp_batch`
  的存在意义就是一次发 200 个——放进去等于让守卫对正确用法常亮，而常亮的提示
  会被模型学会忽略。

**常驻成本（字符数，含 description + schema）**
