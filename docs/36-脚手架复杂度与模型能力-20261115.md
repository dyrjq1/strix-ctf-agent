# 36 · 脚手架复杂度与模型能力：这个说法对我们适用多少（2026-11-15）

> 触发：用户转述一个流行说法——「越聪明的模型，复杂 agent 是累赘；不聪明的模型才需要
> harness 约束」。本文核实外部出处，并用本项目自己的同题消融数据判断它对我们的适用面。
> **只做判定，不做代码改动。**

## 0. 结论先行

这个说法是**半真**，一半成立、一半不成立，区分点不在「模型多聪明」，而在**脚手架给的是什么**：

| 脚手架给的东西 | 随模型变强 | 说法是否成立 |
|---|---|---|
| **建议**：下一步该做什么、用什么策略、提醒某个机制类别 | 价值衰减，强模型上可能变噪声 | **成立** |
| **事实**：工具能看到的输出、错误的真实原因、状态与契约落盘 | 不衰减，强模型同样受益 | **不成立** |
| **成本**：上下文封顶、前缀缓存纪律 | 不衰减；做错就变负 | 部分成立（复杂度必须隐形） |

对我们的正确动作不是「拆 harness」，而是**砍建议层、做厚事实层**：建议型组件默认关（我们
已经这么做），事实型组件可以留（但仍要消融）。**用一句可执行判据**：新增一项之前先问
「它给模型的是事实，还是建议？」给建议的默认进 opt-in，给事实的才配默认开。

## 1. 外部出处（2026-11-15 检索；WebFetch 直连被网络策略拦，以下按检索摘要转述）

- **Epoch AI《Why benchmarking is hard》**（2025-12）：SWE-bench Verified 上**只换
  scaffold**，同一模型分数就能摆到 GPT-5 最高 **11%**、Kimi K2 最高 **15%** 的差距。
  → 结论：即使最强的模型，harness 仍然显著影响分数——「聪明就不需要 harness」不成立。
- **arXiv:2609.20804《An Empirical Study of Harness Design for Coding Agents》**（2026）：
  **planning 对弱模型是精度脚手架（提成功率），对强模型只是省钱手段（精度几乎不变）**。
  → 这是「建议型脚手架随能力衰减」最直接的证据，也是这个说法最站得住的一半。
- **arXiv:2605.23950《Stop Comparing LLM Agents Without Disclosing the Harness》**：
  同口径独立复述 11% / 15%，并主张跨模型比较必须披露 harness。
- **Meireles et al.《The Influence of Scaffolds on Coordination Scaling Laws》**：
  在更少规定性的脚手架下，能力随规模增长的曲线反而更明显——脚手架会**压掉**一部分模型差异。

⚠️ 注意流行说法里的偷换：把「scaffold 能在弱模型上刷出高分」等价成「scaffold 只是拐杖」。
基准里 11–15% 的摆动说明，拐杖之外还有一大块是**接口**——模型再强，也看不见它拿不到的数据。

## 2. 分层：我们项目里谁在哪一层

| 层 | 本项目组件 | 判定 |
|---|---|---|
| 事实/接口层 | `tool_arg_repair`（把 SDK 的误导性 `Invalid JSON` 还原成「哪个键错了」）、`result.json` 契约与 `autosubmit`、`http_probe`/`route_map`/`traffic_*` 输出形状、`file_triage`、沙箱与墙钟兜底 | **保留**；与模型强弱无关，属于「看得见/做得到」的地基 |
| 行为建议层 | `enum_guard` 的机制类别提示、`finish_guard` 的拒收改写（`_REDIRECT`）、`journey_guard`、S2 形状停滞判据、`viability_probe`、`fact_ledger` | **默认关 / opt-in**；价值随能力衰减，且实测有负例 |
| 成本层 | system prompt 替换（103k 字符的通用提示换掉）、内容封顶、前缀缓存纪律（**不按龄裁剪**） | **保留但必须隐形**；任何破坏前缀的动作都是负优化 |

## 3. 我们自己的实测（这才是判据，不是别人的论文）

| # | 组件（层） | 实测 | 读法 |
|---|---|---|---|
| 1 | `viability_probe`（建议） | 同 4 题同预算：**ON 2/4（77 调用、324s）vs OFF 4/4（39 调用、217s）** | 建议型最差案例：会「劝」偏，还多烧一倍调用；默认 `CTF_VIABILITY=0`（台账 §4.186） |
| 2 | S2 形状停滞判据（建议） | 44 场 run **零触发**；item 流重放 23/23 与线上一致 | 仪表没错，是总体里不存在该形态 ⇒ 判噪声、默认翻回（§4.190） |
| 3 | `fact_ledger`（建议/事实混合） | 零 token 预检：拒收时只有 **7%** 能指名（放宽 11%、每轮注入 13%）< 80% 门槛 | 预注册淘汰条件触发，A/B 取消，代码 opt-in 保留（§4.193） |
| 4 | `route_map` 采用率（事实层但需要模型主动调） | 11-07 后仅 **31/225** 场 run 调用 | 「给了接口」≠「会被用」；修法应是让事实自动出现（如并进探针输出），不是加提示劝它调 |
| 5 | `tool_arg_repair`（事实/接口） | 11-12 日志：`finish_scan` 145 次里 **127 次**失败全是形状错误，SDK 统一报「JSON 非法」，模型据此把参数越包越深；修复后默认开 | 事实层立竿见影，且换更强模型**依然有用**——SDK 的错误信息不会因为模型聪明就变对 |
| 6 | 上下文按龄裁剪（成本） | 缓存命中 95.7% → **57.8%**，等效成本涨 6 倍，已回滚 | 成本层的复杂度做错就是净损失 |

## 4. 对下一轮选型的含义

1. **前提校正**：我们跑的是 `deepseek-v4.1-flash`（中档快模型），「聪明到不需要约束」这一半
   不保护我们；但第 1–3 条说明「劝它」也不管用。有效形式是**替它把事实摆好、把错误说真话**。
2. **选型判据（新增）**：一个候选组件先分类——给事实的（可默认开 + 消融）还是给建议的
   （默认关 + 预注册 + A/B）。这条判据不替代原有八步流程，只是在第 3 步加一问。
3. **不要现在拆脚手架**：11-19 冻结，拆任何默认开的组件都要重新验证（时间不够）；现在能做的
   只是确认「建议型已全部默认关」——`CTF_VIABILITY=0`、S2 已翻回、`fact_ledger` 默认关，
   三项已满足。
4. **反面提醒**：如果下一轮候选又是「提醒模型做某事」，按第 1–3 条的先验，它大概率先失败；
   优先选「让模型不提醒也能看到」的改动。
