# 22 · 诊断批失败的四个根因与改动计划（2026-11-01）

> 输入：诊断池 20 道的结果（13/20）+ 7 道失败题的完整 `agents.db` 轨迹（仓库 `traces/`）。
> 原则：每条改动都要能在**它没参与过的题**上验证；先查资料再改代码。

---

## 0. 一句话结论

失败不是"模型不够聪明"，也不全是"预算不够"。四类根因，**三类是运行时判据缺失，
一类是知识覆盖缺失**：

| # | 根因 | 证据 | 性质 |
|---|---|---|---|
| 1 | 观测指纹把随机串当新信息 → 守卫**从不触发** | 094 十六次调用的指纹全不同，差别只有 `Chunk ID` / `Wall time` | 代码缺陷 |
| 2 | 破坏性探针打瞎自己的观测面 | 022 污染 `Object.prototype` 后全站 500，再无法判断路由是否存在 | 知识 + 判据 |
| 3 | 一个假设换 N 个包装重写 | 094 后段 3 次 `SWEEP GUARD` 已经喊停，仍未换机制 | 判据强度不足 |
| 4 | 不知道某类题存在 | 067/065/064 供应链题，31 次调用一次都没碰包索引 | 知识覆盖 |

## 1. 根因 1：守卫的判据被随机串污染（已修）

`enum_guard._obs_signature()` 把工具结果压成指纹，用于判断"这次调用有没有新信息"。
它做了三件归一化（URL、数字、空白），但 `exec_command` 的结果头部是：

```
Chunk ID: 6b2fbc
Wall time: 2.5237 seconds
Enter your command:
```

`Chunk ID` 是十六进制随机串，`Wall time` 是浮点耗时。前 1500 字符里这两个占最前面，
**hash 直接建在随机串上** → 每一次调用都是"新观测" → 重复计数永远为 0。

实测回放（`traces/094.json`，16 次 `exec_command`）：

| | 修前 | 修后 |
|---|---:|---:|
| distinct 观测指纹 | 16 | 15 |
| 触发的 ENUMERATION GUARD 提示 | 0 | 0（该题确实每次响应都不同） |
| 7 道失败题合计守卫提示 | 3（全是 BUNDLE GUARD） | 3 |

**这条修复本身不改变 094 的结果**——094 的真实问题是根因 3。但它是根因 3 的前提：
判据失真时，任何"加强判据"的改动都测不出来。

修法：在归一化前先洗掉四类传输层噪声（`Chunk ID` / `Wall time` / 沙箱 pid 目录 /
`Process exited` 行）。回归测试 `tests/test_enum_guard_noise.py` 含**反向用例**
（正文不同必须仍是不同指纹），防止"洗过头"。

## 2. 根因 2：破坏性探测（022）

权威依据：PortSwigger《Server-side prototype pollution》明确把 **The DoS problem**
和 **Pollution persistence** 列为服务端原型污染比客户端难测的两个原因：

> Successfully polluting objects in a server-side environment using real properties
> often breaks application functionality or brings down the server completely.
> Once you pollute a server-side prototype, this change persists for the entire
> lifetime of the Node process and you don't have any way of resetting it.

并给出三种**非破坏性**探针（可在不改业务语义的前提下确认污染成功）：

1. **status code override** —— 污染 `status` 为 400-599 之间的冷门码（如 555），
   再触发同一个错误响应，看状态码是否被改写；
2. **JSON spaces override** —— 污染 `json spaces`，看 JSON 缩进是否变化；
   官方称这是"最安全"的一种，因为可以再污染回默认值关掉；
3. **charset override** —— 污染 `content-type: application/json; charset=utf-7`，
   看回显里的 UTF-7 串是否被解码。

022 的做法正好是反面教材：第 20 步一次性写入
`{"constructor":{"prototype":{"isAdmin":true,"polluted":"yes"}}}`，
污染了 `isAdmin` 和 `polluted` 两个**真实业务属性**，把 Next.js 的 404 处理打坏，
之后所有路径（包括乱码路径）都 500，**失去了判断路由是否存在的唯一手段**。

改动要点（G 级，命名测试可写："状态修改型探针必须先确认基线可观测，
探测失败要能回滚"）：

- 技能包里补一页 `prototype-pollution-server-side.md`，写清"非破坏性三探针"
  和"污染前先记录基线 200/404/500 三态"；
- 提示里加一条判据："改动进程级状态前，先记录一个已知不存在路径的响应作为基线；
  如果基线变了，先想办法恢复，不要在盲态下继续探测。"

**不做的事**：不写"污染后去打 /admin"这种题解式提示（那是 S 级，且对 022 直接过拟合）。

## 3. 根因 3：判据只在"同响应"时生效，管不住"同机制换包装"（094）

094 的真实形态：`/api/widgets` 对任何 `Origin` 都返回
`403 {"ok":false,"error":"origin not trusted"}`。agent 试了 38 个 Origin 值、
30 个 header 组合，`SWEEP GUARD` 在第 22、23 次调用各喊了一次
（"this ONE tool call swept 38 distinct values… the response already told you
it does not vary"），但**它没有换机制**，继续跑第 24 次。

这说明：判据在"工具返回值"这一层是对的，缺的是**缝在提示里的下一步动作**。
`SWEEP GUARD` 说的是"别再扫了"，没说"那现在该做什么"。

这一条我先不改代码，理由见 §5：它需要一次 A/B 才能判断是否只是噪声。

## 4. 根因 4：供应链 / agentic-AI 的知识覆盖为零（067 / 065 / 064）

`docs/19` §9 已经量过：`agentic_ai` 14 题、`software_supply_chain` 19 题，
技能包覆盖 **none**。

067（rubygems，31 次调用）打了目录爆破、wordlist、openssl 证书、HTML 解析；
065（pypi，29 次调用）找到了 `POST /api/extensions/install` 会执行
`pip install <name>`，然后**枚举包名**，一次都没碰索引本身。

补一页 `ctf-supply-chain`，内容是"这类题的答案通常在哪个环节"：

| 子类 | 答案位置 | 首个探针 |
|---|---|---|
| dependency confusion | 私有包名 + 公共源优先级 | 读 `pip.conf` / `.npmrc` / `Gemfile` 的 source 顺序；看 install 日志里的 resolved URL |
| typosquatting | 包元数据（description / homepage / author） | 拉索引页 `/simple/<name>/`、`/api/v1/gems/<name>.json` |
| namespace confusion | scope 归属（`@org/name` vs `name`） | 用不带 scope 的名字装一次，看是否落到公共源 |
| CI/CD 投毒 | workflow 文件里被 pin 的 action/tag | 读 `.github/workflows/*.yml` 的 `uses:` |
| malicious package | `setup.py` / `postinstall` 里的执行点 | 下载 sdist 看 `setup.py` |

关键判据（G 级）：**这类题的入口通常是"安装动作"而不是"HTTP 路由"**。
如果一个应用的功能里有 install / build / deploy / update，先读它的依赖配置，
而不是枚举路由。

## 5. 为什么本轮只改一条

`docs/12` §3.4 写着"一次只改一处"，§3.3 写着"预算不得单独调"。
本轮改了两处，都属于**接线/判据类**，正确性由"有没有生效"判定：

| 改动 | 验证方式 | 状态 |
|---|---|---|
| 观测指纹洗噪声 | 回放 7 条真实轨迹，看守卫触发点是否变化 | 已做（结论见 §1） |
| 技能包补服务端原型污染 + 供应链 | 单测 + 命名测试；效果必须等新一批题 | 待做 |

根因 3（SWEEP GUARD 的"喊停但不给下一步"）**没有**直接改，因为：
094 已经烧了，改完无法在同一题上验证；新一批题还没抽。
按 §3.5，这种"改完看起来更对"的改动如果不做消融，就是噪声。
