# 05 · 运行时守卫与契约校验

> 本轮针对上一批实验暴露的失败模式做工程加固。核心判断：**凡是写在 prompt 里的行为约束都不可靠**，因为模型在第 N 轮时，历史里的规则已经被后来的工具输出埋掉了。三处最贵的失败（枚举不收、不登录就打、没 flag 就收工）全部属于这一类。

## 1. 问题从哪来

上一批（15 题）的平台判定是 9/15。失败题的形态不是随机的，归纳后只有三种：

| 失败形态 | 代表题 | 证据 | 原 prompt 规则是否生效 |
|---|---|---|---|
| 枚举不收，刷同族端点直到撞墙 | CTFARENA-018 | 同一族 `/api` 探测重复 38 次 | ❌ 写了两版文字规则都没拦住 |
| 不登录就灌攻击载荷 | CTFARENA-012 | 全文没有一次成功的注册/登录；失败后自称"环境缺 nmap/ffuf" | ⚠️ 改了 prompt 后 002/016 通过，但只有 2 个样本 |
| 没 flag 就收工 | CTFARENA-013 | 用了 260s/780s 预算，已注入成功、读到 `sqlite_master`，却直接 `finish_scan` | ❌ 写了"收工前三问"，没用 |

第三种最贵：它不是在错误方向上烧钱，而是**在正确的方向上提前离场**。

## 2. 三个守卫

三者都通过包装 `factory._with_bounded_result` 来改 `on_invoke_tool`——这是 strix 自己在 `agents/factory.py:149` 用的手法，所以**不动 vendor 代码，升级不需要 rebase**。三个标记互相独立，可以叠加。

### 2.1 `enum_guard.py` — 枚举收敛（沿用，本轮补观测）

指纹 = 工具名 + host + 路径倒数第二段。`/api/coins/stats` 与 `/api/coins/tiers` 归为同族（`coins`），这才是"换个叶子刷新"的真实形态。第 4 次起警告，第 7 次升级为硬指令。

### 2.2 `journey_guard.py` — 先走通用户旅程（新增）

**激活条件是关键设计**：必须先观察到"探测了认证端点且被 401/403 拒绝"，守卫才开始计数。不能一上来就要求注册——纯注入题（命令注入、SSTI、文件读取）根本没有账号体系，强制要求会把模型推向更错的方向。

解除条件有两条，任一满足即**永久静默**：

- 输出里出现 `Set-Cookie` / `access_token` / `token` 等认证成功信号；
- 发出了写请求且响应带 `201` 或 `"id": <数字>`。

### 2.3 `finish_guard.py` — 没有 flag 不许收工（新增）

`finish_scan` 是 root agent 的终止工具，**调用它等于整个 run 结束，没有下一轮**。所以这里不是提示，是拒绝：返回符合它自身契约的 `{"success": False, "error": ...}`，把控制权交回模型，并给出三条具体动作（有执行能力就去读文件、只证明了漏洞就转成读数据、没认证就去注册）。

两个边界：

- **只拦 `finish_scan`，不拦 `agent_finish`**。子 agent 的分工是侦察/利用/验证，recon 干完活时本来就没有 flag，拦它会把正常编排打死。
- **连续拒绝 3 次后放行**。真要解不出来时，硬拦会让模型在预算末尾反复撞墙；失败的 run 也应该干净地收尾，而不是耗尽轮次。

## 3. 入口的三个 bug

`src/ctf_strix/agent.py` 是正赛真正跑的入口，本轮查出三处问题，其中第一处是**正赛级**的：

| 问题 | 后果 | 修法 |
|---|---|---|
| `_extract_flag` 用 `found[-1]` | 取"最后一个 flag"，会提交到别题残留的诱饵——这正是我在评测脚本里修掉的 bug，但**入口没修** | 委托给 `flag_extract.best_flag`，带靶机 host 做证据判定；并改为**逐条输出单独判定**，不再拼接后整体判定（拼接后距离信息会被淹没） |
| `result.json` 缺 `schema_version` | `inspect_probe` 报 `no_schema_version`（advisory） | 写入 `BRIEF_SCHEMA_VERSION = 2` |
| 不支持 `dry_run` | dry run 会真去打靶机，跑满 `DRY_RUN_BUDGET_S=180` 后被标记 `dry_run_ignored` | 检测 `task.json` 的 `dry_run`，直接写 `stop_reason: "dry_run"` 并退出 |

`dry_run` 那条尤其值得修：平台在提交阶段会反复跑 dry run 做契约检查，每次 180 秒的等待纯属白烧，而且会被记一条告警。

## 4. 契约校验本地化：把最大的未知项消掉一半

原本的阻塞项是 `ctfy agent check` 需要 Docker，而开发机没有。但读 `core/harness_conformance.py` 后发现，**动态检查只有两条 blocking**：

```
did_not_start   容器起不来
no_result_file  没写出可读的 result 文件
```

其余三条（`no_schema_version` / `dry_run_ignored` / `nonzero_exit`）都是 advisory。也就是说，容器层之外的部分完全可以本地验证——`scripts/check_contract.py` 直接执行入口脚本、用 **ctfy 自己的 `inspect_probe`** 打分，判据不是我自己编的。

四个场景全过：

| 场景 | 验的是什么 | 结果 |
|---|---|---|
| `dry_run` | 快速退出、不碰靶机、`stop_reason` 正确 | 0.0s，PASS |
| `no_scope` | 没有靶机时仍写文件 | PASS |
| `declared_path` | 跟随 `task.json` 的 `result.path`（相对路径 `out/r.json`） | 写到 `work/out/r.json`，PASS |
| `import_crash` | strix 完全缺失时仍写文件且 exit 0 | 1.5s，PASS |

第四个场景是有价值的：它模拟"镜像里依赖没装好"，验证 `except BaseException` 分支真的会把文件写出去——而不是让平台看到"容器跑完了但什么都没留下"。

**残余风险**：镜像层（entrypoint、架构、拉取）本地无法验证，仍需一次真机 dry run。

## 5. 观测缺口：守卫统计必须进数据

上一轮枚举守卫的教训是"装了、单测过了、真实日志重放也过了，但真实运行里一次都没触发，而结果表上看不出区别"。所以本轮把守卫计数写进 `results.jsonl` 的 `guard` 字段：

```json
{"enum_keys": 1, "enum_hits": 0, "journey_wall": 1, "journey_authed": false,
 "journey_payloads": 5, "journey_hits": 2, "finish_refused": 2}
```

`*_hits` 从日志里数提示文本出现次数，`journey_wall` / `finish_refused` 从运行末尾的 `[guard]` 汇总行解析。两者对不上就说明注入通道本身有问题。

## 6. 自测固化

`scripts/selftest.py` 一条命令跑 **38 项断言**，覆盖 flag 抽取 6 场景、枚举守卫 7 项、旅程守卫 9 项、收工守卫 6 项、入口 3 项、三守卫叠加 7 项。

之所以要固化：三层守卫都改同一个 `on_invoke_tool`，改其中一层很容易把另一层弄哑，而"弄哑了"在真实运行里表现为"守卫没触发"，看起来和"这题不需要介入"一模一样。

固化过程中自测抓到一个真实缺陷：`journey_guard` 的 SQLi 正则原本要求载荷**必须带引号**（`'\s*or\s+1=1`），实测 `?id=1 or 1=1` 这种不带引号的写法完全不命中，守卫静默失效。已改为引号可选。

## 7. 实测：守卫在真实运行中的介入情况

必须把"守卫写好了"和"守卫起作用了"分开说。CTFARENA-013 复跑是第一个真实数据点：

| 指标 | 上次（run4） | 本次（复跑） |
|---|---|---|
| 结果 | ❌ 24 次调用 / 260s 就 `finish_scan` | ✅ **42 次调用 / 509s，平台验真 rank 12** |
| 预算 | 25 轮 / 780s | 60 轮 / 1793s |
| 三个守卫介入 | 不存在 | **全部 0 次** |

`finish: refused=0 allowed=1` —— `finish_scan` 只调用了一次，而且**这次带了 flag**，所以守卫正确放行。

**结论必须诚实：013 的好转不是新守卫的功劳。** 时间线对得上：上次跑 013 时 `ctf_goal.txt` 还没有"先走通用户旅程"那一段，本次有。所以这是 prompt 累积改进的效果。三个守卫这次纯属"没被触发"，也没有误伤（0 次误拦），这本身是一个正向信号但不是有效性证明。

守卫的有效性目前只有两个层次的证据：

1. **单元层面**：38 项断言（`scripts/selftest.py`），含"无认证墙不误伤"、"已登录后不介入"这类反例。
2. **真实日志重放**：把 CTFARENA-018 的 46 次调用序列喂给枚举守卫，能识别出 `api` 族被刷了 8 次（这是它当初真实失败的原因）。

**缺的是第三种证据：真实运行中被触发并扭转了结果。** 这只能靠跑更多题积累，不能靠单测代替。

## 8. 预算分层的修正

上一版给 hard 开 96 轮 / 2870s（40×2.4 / 1248×2.3），依据是"010 在 25 轮处轮次耗尽、018 在 780s 处被墙钟切断"。但后来 002（11 次 / 235s）、016（10 次 / 380s）、013（42 次 / 509s）都用远低于上限的预算解出——**那个依据不成立**。

改为按实测值定上限：

| 难度 | 轮次 | 墙钟 | 实测所需 |
|---|---|---|---|
| easy | 25 | 13 分钟 | 11-82 次 / 163-728s |
| medium | 40 | 20 分钟 | 18-51 次 / 174-358s |
| hard | 60 | 30 分钟 | 10-42 次 / 235-509s |

**方向对了 25 轮就够，方向错了 96 轮只是把失败成本放大 4 倍。**

## 9. 工具面统一

发现一处会污染全部评测结论的不一致：评测脚本默认不裁剪工具，而正赛入口 `agent.py` 装了 `install_ctf_toolset()` 会摘掉 17 个记账工具（含 `list_notes`、`create_vulnerability_report` 等）。两者工具面不同，评测出的轮次和 token 就不能用来推断正赛。

改为**两边都只摘 Caido 那 6 个**（`drop_bookkeeping=False`）：

- 摘 Caido 是纯收益——本机没有 `caido-cli`，这 6 个调用必然报错；
- 记账工具的裁剪收益已被证伪（`--trim-tools` 的 006 用 48 次调用，未裁剪的 011 只用 42 次），保留它们只多占 schema token，但消除了"prompt 教用被摘掉的工具"这个更贵的风险。

### 9.1 顺带裁掉 `web_search`

012 复跑的日志里出现了一轮：

```
web_search {"query": "ctfy.run node2 CTF challenge \"FLAG{\" PinBoard web challe..."}
```

agent 去**搜索引擎找 flag**。但比赛配置是 `internet_policy=deny`、`agent_internet=deny`——**正赛没有外网**，这个工具在正赛里必然失败。

更麻烦的是它制造了**测试与正赛的环境差异**：评测机有网，于是 agent 会去搜；正赛没网，同样的策略会立刻失败。测出来的行为不能用来推断正赛。

所以无条件裁掉 `web_search`，并在 `ctf_goal.txt` 里补一段"这个环境没有互联网"——裁工具只能阻止它用这个工具，它完全可能改用 `curl` 去访问搜索接口。

## 10. 死代理：一个会让每道题都白跑的配置缺陷

这是本轮最有价值的发现，而且它**不是**从代码审查里看出来的，是从"靶机通了但 agent 说 000"这个矛盾里挖出来的。

### 现象

复跑 CTFARENA-012 时，agent 的 `curl` 一直返回：

```
000 0 https://<target>/
Wall time: 0.0230 seconds
```

同时我在评测机上直接 `curl` 同一个地址：**HTTP 200，0.09 秒**。

`000` 且耗时 **0.023 秒**——这不是超时，是连接被立即拒绝。

### 根因

`vendor/src/strix/runtime/session_manager.py:308-314` 给沙箱环境写死了：

```python
"http_proxy": f"http://127.0.0.1:{_CONTAINER_CAIDO_PORT}",
"https_proxy": f"http://127.0.0.1:{_CONTAINER_CAIDO_PORT}",
"ALL_PROXY":  f"http://127.0.0.1:{_CONTAINER_CAIDO_PORT}",
```

这是给 Docker 镜像里的 Caido sidecar 用的。**本机没有 Caido 在那个端口监听**，所以每一次走代理的请求都打到一个死端口，立即失败。

`unix_local.py:434` 会把这些变量 `update` 进每次 exec 的环境，所以命令类工具全部中招。

### 为什么之前没发现

因为 **agent 自己会绕过它，只是要花轮次**。CTFARENA-013 的日志里能清楚看到这段自救过程：

```
exec_command {"cmd": "env | grep -i proxy; echo \"---\"; ss -ltnp ..."}
exec_command {"cmd": "curl -sS -m 25 --noproxy '*' -D - https://... "}
```

013 花了十几次调用才诊断出"要走 `--noproxy '*'`"，然后成功了。012 没诊断出来，一直在 `000` 上重试到撞墙。

**这意味着一部分"题做不出来"其实是环境在收税**，而且税率取决于模型当天愿不愿意去查 `env`。

### 修法

在适配层（`src/ctf_strix/local_backend.py`）把 `manifest.environment.value` 里的六个代理变量删掉。因为 `environment.value` 是可变 dict 且 `unix_local.py:434` 会把它注入 exec，改这里就生效，不用碰 vendor 代码。

验证：修复后同一条 `curl` 的 `Wall time` 从 **0.0230s → 0.5684s**（真实往返），

### 附带修的：ready ≠ 可达

`wait_ready` 只看平台返回的 `status == "ready"`，那不是"从这台机器能连上"的证明。加了 `probe_reachable`：实例就绪后真打一次，连接层失败就换实例重试一次。

注意判定口径：**4xx/5xx 都算可达**——题目本来就可能把根路径设成 404/403。只有 DNS 失败、连接被拒、超时才算法不可达。

## 11. 守卫挂载点：三个守卫一起静默失效

这是继"死代理"之后**第二个"看着在工作、其实从未执行"的缺陷**，而且它比死代理更隐蔽——死代理至少留下了 `000` 这种异常现象，这个连异常都没有，计数器安安静静地躺着 0。

### 现象

CTFARENA-012 复跑：**45 次工具调用、1170 秒撞墙钟**，日志里有 **16 次 401/403**。收尾统计：

```
[guard] enum keys=0 | journey: wall=0 authed=False created=False payloads=0 prompts=0
```

三个守卫全部 0。上一轮我把这解释成"守卫没识别出认证墙"，准备去改正则。

### 定位过程（关键在于不猜）

strix 把每条消息都存进了 `.state/agents.db`（`agent_messages` 表，`message_data` 是 JSON）。里面有完整的 `function_call.arguments` 和 `function_call_output.output`——**这就是真实运行的逐条回放数据**。

所以不需要重跑靶机，直接把这次会话灌进同一个守卫类：

```
[14] exec_command  authHint=1 denied=1 | wall=1
[19] exec_command  authHint=1 denied=1 payload=1 | wall=4 pl=3 | HINT!
[27] exec_command  authHint=0 denied=0 payload=1 | wall=5 pl=6 | HINT!
[44] exec_command  authHint=0 denied=0 payload=1 | wall=7 pl=9 | HINT!

FINAL: wall_hit=7 payloads=9 prompts=3
```

**判定逻辑完全正确，离线重放能触发 3 次。** 那为什么真实运行是 0？

答案是那次运行里守卫的 `observe()` 从来**没有被调用过**。规则没错，是接线没接上。

### 根因

三个守卫都是替换 `factory._with_bounded_result` 来挂 `on_invoke_tool` 的。这个选择看起来天经地义——它就是 strix 自己的工具包装层。

但 strix 建 agent 时走**三条**路：

| 路径 | 覆盖的工具 | 是否经过 `_with_bounded_result` |
|---|---|---|
| `_build_agent` 里的常规工具列表（`factory.py:707`） | `think`、`create_agent`、`view_agent_graph`… | ✅ 经过 |
| `Filesystem` capability（`_configure_filesystem_tools`） | `apply_patch`、`view_image` | ✅ 经过 |
| **`Shell` capability（`_configure_shell_tools`，`factory.py:486`）** | **`exec_command`、`write_stdin`** | ❌ **完全绕过** |

`_configure_shell_tools` 只做 `_with_strictness(_with_coerced_arguments(tool))` + `_wrap_exec_command`，然后直接 `setattr` 回 toolset。

**而 `exec_command` 是唯一能把请求真正打到靶机上的工具。**

所以守卫实际覆盖的是 `view_agent_graph`、`create_agent`、`think` 这类流程工具——它们永远不会发出攻击载荷。守卫装得很好，只是守错了门。

### 为什么这个错误能活到线上

因为它**没有任何报错**。启动时打印了：

```
[guard] enumeration guard installed (warn>=4, hard>=7)
[guard] journey guard installed (activates only after a 401/403 on auth)
[guard] finish guard installed (refuses flagless finish_scan, max 3)
```

三行都打印了，因为 `install()` 确实执行成功了。它只是把一个包装函数装到了一个没人走的岔路上。

**"计数器为 0"和"守卫没接线"在旧日志里长得一模一样。** 这是这次真正该记住的东西。

### 修法

新增 `src/ctf_strix/guard_mount.py`，用**三重挂钩**把 `_with_bounded_result` 变成名副其实的统一挂载点：

```python
factory._configure_shell_tools = shell_hook   # 原函数跑完后，再逐个 mount
factory._configure_filesystem_tools = fs_hook # 同上
factory._with_bounded_result = patched        # 三个守卫照旧替换这个
```

顺序有硬约束：**必须先 `install_mount_hook()`，再装守卫**。因为钩子里读的是 `factory._with_bounded_result` 的**当前**属性（不是 import 时的快照），守卫晚装也能被看到。反过来装就漏。

再补一个 `verify_mount()`：装完守卫后造一个假 toolset 走一遍真实配置路径，检查 `exec_command` 上有没有守卫标记。两个入口都在启动时打印 `mount verified=True/False`——把"是否真的挂上"提前到第一秒就能看见。

### 顺带挖出来的三个小坑

修完主链路后，自测接连失败，每一个都是真 bug：

1. **`_PROBE_TOOLS` 里有不存在的工具名**。原写作 `("exec_command", "write_stdin", "browser_", "http_request")`——`browser_*` 和 `http_request` 在 strix 里**根本不存在**（核对 `factory._BASE_TOOLS` 和 `Shell` capability 得到的实际名单是 `exec_command` / `write_stdin` / `repeat_request`）。不存在的名字不会报错，只会让守卫永远不匹配。已改为实际存在的三个。

2. **载荷正则漏 URL 编码**。`?id=1 or 1=1` 能命中，`?id=1%20or%201=1` 不能。真实运维里模型大量使用 URL 编码（`urllib.parse.quote`、`--data-urlencode`），实测 `wall=9 payloads=0`：墙识别对了，载荷一发没数到。已允许 `%20` / `+` / `/**/` 出现在运算符之间，并容忍引号紧贴关键字。22 个正负用例全覆盖，且不误伤 `order`、`store` 这类正常词。

3. **"既是认证探测又是载荷"的调用被整条吞掉**。原代码在识别到认证墙后直接 `return None`，注释写着"这一次不算载荷，是探测本身"。但 `curl '.../api/login?id=1 or 1=1'` 恰恰就是最常见的那种调用。改成识别墙和数载荷分开算——同一发调用可以既确认有墙、又算一发载荷。修完真实会话重放的 `payloads` 从 9 → 14，`prompts` 从 3 → 4。

### 沉淀：两个新的观测字段

- `JourneyState.observe_calls` / `EnumerationGuard.observe_calls`：守卫被调用的次数。
- 收尾日志新增 `reach=N (calls into guards)`；`reach=0` 时直接打 WARNING，并在评测结果里标 `mount_broken`。

有了它，下次再出现"守卫全 0"，第一眼就能分清是**规则没命中**还是**根本没接线**。

### 验收

- 自测从 38 项扩到 **49 项**，新增一节"守卫挂载点"，断言走**真实配置路径**造出来的 `exec_command` 必须带三个守卫标记。
- 新增"真实会话重放"回归：直接读 `tests/fixtures/ctfarena-012-session.db`（那次失败运行的原样会话），要求 `wall>0`、`payloads>=10`、`prompts>=3`。这是端到端验收——任一环写紧一点就会掉到 0。

## 12. 已知局限

- **守卫状态是进程级单例**，多 agent 共享。单靶机场景下这是对的（同一个会话概念），但如果一题里有多个独立服务，状态会串。
- **收工守卫依赖 flag 格式是 `FLAG{...}`**。这与题目定义、平台判分口径一致，但如果遇到自定义格式的题会误拦（好在 3 次后放行）。
- **失败成本问题没有解决**。prompt 占 token 的 99.9%，因为每次工具调用都重发全部历史。这只能靠减少轮次或改 strix 的上下文管理，不在本轮范围内。
- `max_turns` 是 root 的预算，**子 agent 轮次独立计算**——实测 018 在 `--turns 40` 下跑了 47 次调用。
- **挂载钩子依赖 vendor 的内部函数名**（`_configure_shell_tools` / `_configure_filesystem_tools` / `_with_bounded_result`）。strix 升级时这几个名字若变，钩子会静默失效——但 `verify_mount()` 会在启动时报出来，这正是加它的另一个理由。
