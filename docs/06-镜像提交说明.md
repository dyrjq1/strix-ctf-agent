# 提交到 CTFY 的镜像：怎么构建、怎么自检、哪里还可能翻车

> 平台页面上那个输入框要的不是 tar 包，是一个**容器镜像地址**（`ghcr.io/me/agent:1`）。
> 本目录就是把 `strix-ctf-agent` 打成符合 **CTFY-0001** 的镜像所需的一切。

---

## 一、平台到底查什么

判据不是我编的，来自 `ctfy.core.harness_conformance`——`ctfy agent check`、
`POST /eval/harnesses/{id}/conformance` 和 dispatch 探针共用同一份实现。
**只有两条 blocking：**

| 判据 | 含义 |
|---|---|
| `did_not_start` | 容器起不来 |
| `no_result_file` | 在 `$CTFY_WORK_DIR` 里没写出可读的 result 文件 |

其余全是 advisory（会显示，但不拦）：`no_command` / `relative_entrypoint` /
`arch_mismatch` / `os_mismatch` / `oversize` / `no_schema_version` /
`dry_run_ignored` / `nonzero_exit` / `tag_moved`。

⚠️ **注意“没文件”和“空文件”是两回事。** `no_result_file` 是平台记录一次失败 run，
而且它在界面上看起来像**模型放弃了**——不是像镜像不合规。所以本镜像的第一原则是：

> 不管发生什么，退出前 result 文件必须存在，哪怕里面写着“我没跑起来”。

## 二、构建

```bash
cd /workspace
docker build -f docker/Dockerfile -t strix-ctf-agent:1.0.0 .
```

三个设计点，都是踩过的坑：

| 选择 | 为什么 |
|---|---|
| `pip install --no-deps -r requirements.lock` | 锁文件是环境快照，里面有 `fastmcp 4.1.4` 要 `mcp>=2.3` 而实际装 `mcp 1.30` 的死结。任何解析器都会拒绝（`No solution found`），但那套组合实测能跑。照单装才是忠实复现 |
| 依赖层在源码层之前 | 改代码不触发依赖重装，重建从几分钟降到几秒 |
| `ENTRYPOINT` 用绝对路径 | 平台把工作目录设成它下发的 `/ctfy/work`，相对路径会按它解析，然后 `can't open file` 起不来（→ `relative_entrypoint` + `did_not_start`） |

## 三、入口的三道保险

`docker/entrypoint.sh` 按「最坏情况先写文件」的顺序排：

1. **读 `task.json` 拿 `result.path`**（平台可能改路径），读不到就退回 `result.json`；
2. **没有 `task.json` 也写文件**——本地 `docker run` 自测时就是没有，而“能起、能写”正是 conformance 要测的全部；
3. **主流程退出后检查文件在不在**，不在就补写一份带原因的。

用 `python3 /app/src/ctf_strix/agent.py` 而不是 `-m ctf_strix.agent`：平台会给容器注入自己的 env（可能覆盖 `PYTHONPATH`），`-m` 在 import 阶段就崩，连“我崩了”都写不出来。

脚本恒 `exit 0`。`nonzero_exit` 只是 advisory，但“跑完没解出”和“进程崩了”在平台侧本来就不是一回事，用退出码表达后者是错位的。

## 四、自检（按这个顺序，别跳）

```bash
# 1. 静态 + 动态，平台自己的判据
ctfy agent check strix-ctf-agent:1.0.0

# 2. 手工复现一次 dry run（不花模型钱）
mkdir -p /tmp/work && cat > /tmp/work/task.json <<'JSON'
{"schema_version": 2, "dry_run": true, "run_mode": "instance",
 "challenge": {"name": "smoke"}, "scope": [], "result": {"path": "result.json"}}
JSON
docker run --rm -w /ctfy/work -e CTFY_WORK_DIR=/ctfy/work \
  -v /tmp/work:/ctfy/work strix-ctf-agent:1.0.0
cat /tmp/work/result.json    # 应该有 schema_version 和 stop_reason=dry_run

# 3. 没有 task.json 时也必须写文件（本地 run 场景）
mkdir -p /tmp/work2 && rm -f /tmp/work2/*
docker run --rm -w /ctfy/work -e CTFY_WORK_DIR=/ctfy/work \
  -v /tmp/work2:/ctfy/work strix-ctf-agent:1.0.0
cat /tmp/work2/result.json   # 应该写的是 entrypoint fallback
```

第 3 条容易被跳过，但它测的正是 `no_result_file` 那一类失败。

## 五、还有哪些没验证

诚实地列出来，这些本地测不了：

| 项 | 为什么测不了 | 怎么补 |
|---|---|---|
| **registry 可达性** | 平台要从它自己的网络拉 `ghcr.io/...` | 先在平台页面试一次引用；拉不到会直接显示 |
| **干净网络下的依赖完整性** | 本机 `.venv` 有 124 个包，镜像里也装了同一份，但环境差异只在真跑时暴露 | 镜像跑一次真题（不 dry run）确认工具链够用 |
| **`arch` 匹配** | 本机是 amd64，平台 worker 也是 amd64（`DEFAULT_ARCH`），但 buildx 可能产出 arm 索引 | 检查 `docker manifest inspect` 只有一个 amd64 |
| **模型凭据怎么进容器** | 平台注入 `LLM_*` 还是需要自己带，取决于报名表单 | 先看平台文档的 env 约定；没给就在镜像里留 `.env.example` 的位置说明 |

## 六、构建之后

镜像推上去、平台引用成功之后，**还要在平台上跑一次 dry run**（页面上的步骤 2「模型」、步骤 3「开始」会做）。
那一步会真的走 `inspect_probe`，任何 `did_not_start` 都会在那里以最清楚的形式暴露。

只有 `ctfy agent check` 和平台 dry run **都过了**，才算“能提交”。在那之前说“已经能提交”是不诚实的。
