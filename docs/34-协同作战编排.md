## 2. 数据与通信

## 3. 协议（钉死，双方按此读写）

**派单（总 Claude → 工位）**——每份 brief 头部固定 `[情报]` 广播段（§4.6），正文含题号/链接或附件/优先级/止损时限/回报格式：

```
[情报] <广播：诱饵 tags、平台动态、共享发现>
[派单] 题号: <ID>
链接: <url / 实例接入 / 附件路径>
优先级: high|normal|low
止损: <mm:ss，默认 15:00>
备注: <补充情报/约束/上一手报告（接手题必附）>
```

**回报（工位 → 总 Claude，issue 评论或日志文件）**
```
[回报] 题号: <ID>
状态: solved|failed|sealed-candidate
flag: FLAG{...}   (solved 必填；PoE 题填 verify_exploit 证据)
解法: <一句话>
证据: <关键请求/文件/截图路径>
耗时: <mm:ss>
下一手建议: <已探明方向/已排除方向/推荐思路>   (failed 必填)
```

**提交留痕（总 Claude → issue 评论，每次平台提交后）**
```
[提交] 题号: <ID>
flag: FLAG{...}
结果: <平台原始响应摘要>
时间: <UTC+8)
```

**状态机**：`未开始 → 已派单 → 打题中 → 待质检 → 已提交 → solved/被拒(重排)`；failed 接手后回到 `已派单`；接手再败 → `封存`。blocked = 需调度者决策。

## 4. 轮次制调度（v2.0 核心，队长设计 + 11-05 实测修正）

### 4.1 硬约束（先于一切排兵）
1. **实例配额 = 1**：每轮牌面 ≤ 1 道实例题，其余为附件题（不占锁）；或多个工位协同打同一实例。
2. **本机进程上限 2 个 agent**：内存警戒 ~2GB（2026-11-05 实测 codex 被内存压力回收杀掉一次）。超配只能给 VM 侧（strix）或等内存释放。派单前查空闲内存。
3. **VM 代码必须先同步**：VM 停在 `616ca78`（11-03），落后本地 `8e5659d` 一大截；strix 上工位前先推 src/。
4. **解出 15 分钟环境销毁**（`solve_env_mode: destroy`）：取证在解出当下进报告，质检+提交压缩在几分钟内完成。

### 4.2 发牌（按强项，不轮流）
| 工位 | 优先给 |
|---|---|
| strix（VM） | web / 实例题（40 解几乎全 web） |
| Codex | rev / pwn / 批量磨题 / 附件题初分；**可超配**多任务同发（并发优势） |
| CodeBuddy | 自包含 crypto / 脚本类附件题（白名单 python/curl/openssl/Write，打不了实例题） |
| 子 Claude #1 | 新题型 / 难题 / 需要工具链组合的题 |

动态积分（0/1 解 = 1000 分，随解出队数下降）：**easy 先行银行分**，难题后置。同题可多工位并打（各开独立会话），但注意 §4.1 资源约束。

### 4.3 轮次结构
1. 总 Claude 组一轮牌（≤1 实例题 + N 附件题），按 §4.2 分派，各工位**独立会话**、**15 分钟止损**。
2. 到点未解 → 工位强制交**结构化交接报告**（[回报] 的 failed 格式），总 Claude 写入题板 attempt log。
3. 解出 → 当下取证进报告 → 交子 Claude #2 质检。
4. 本轮收齐（解出/超时/交接报告齐）→ 组下一轮。

### 4.4 接手与封存
- 未解题由**子 Claude #1 接手**再 15 分钟；brief 内嵌上一手报告（含已探明/已排除方向）。
- **换模型原则**：接手者与首发者不得同模型（codex 败 → claude 接，别 codex 接 codex；不同模型 = 不同假设空间）。
- 接手仍未解 → **封存**：题板记卡点 + 已排除方向 + 复活触发器。
- **强信号规则**：两个工位同题同卡点 → 不再派第三个，总 Claude 亲打（11-05 演练实证）。
- **复活触发器**（任一命中则解封再给 15 分钟）：广播情报命中该题 / 新能力上板（工具箱/代码同步）/ 赛末余量充足。

### 4.5 质检与提交（子 Claude #2 → 总 Claude）
质检清单（全部通过才提交）：
1. flag 格式与题面要求一致；
2. 来源链：非自回显（agent 自己 echo 出来的不算）、非诱饵附件、tags 已核对；
3. `verify_answer` 预检（有实例时）；
4. PoE 分支：`mode=checker` 题 → 不交 flag，走 `verify_exploit`（**必须带 question_id**），题板记 question_id。
通过 → 总 Claude 立即提交（授权沿用：质检过即提交，不必等队长）→ [提交] 留痕 → 关 issue。被拒 → 标记 + 排回队列（dynamic flag 可能已轮换，方向已知则快速重解）。

### 4.6 广播
总 Claude 可随时向全部在打工位广播关键情报：诱饵 tags 发现、平台动态（新 hint/规则变化）、某题的共享发现。落地方式 = 后续每份 brief 头部的 `[情报]` 段（对无 repo 访问的 CodeBuddy 尤其重要）。

## 5. 夜间模式（队长离场）

- 轮次循环不停（闹钟自唤醒 + 后台任务通知），flag 过检即提交（已授权）+ 留痕。
- 附件题是夜间主场（不占实例锁）；实例题串行。
- 内存余量低时自动降并发（§4.1.2），宁慢勿崩。
- 队长醒来看 issue 流水 + 题板汇总。

### 演练发现（写进流程的修正）
1. **per_team 附件必须先起实例**：`download_challenge_attachment` 对 per_team 文件 409；正确顺序 = start_instance（要带 competition_id）→ REST `/instances/{id}/attachments/{filename}`。三通道回退链（REST→实例→MCP）在协同侧同样适用。
2. **submit_answer 的真实 schema** 只要 `instance_id` + `answer`（challenge_id 是多余参数，平台会拒）；SAMPLE 套件走 instance 通道提交，练习场判分含 solve_rank。
3. **演练即实战**：SAMPLE-010 被分支④抢先解出并真实提交（correct=true），不是假数据。
4. Python 直接跑交互脚本会卡会话（licencecheck 等 argv），用 Start-Process 带超时。
5. **PoE 题（mode=checker）协同打法**：agent 负责攻击本体，调度者重放/确认后调 `verify_exploit`（**必须带 question_id**，本题是 `deface` 不是 `flag`）——平台 sidecar 判定即 solved，无 flag 字符串。题板记录 question_id 而非 flag。
6. **派单前核 tags + question mode**：`per-team-artifact` → 起实例拉真附件（SAMPLE-002 的公共附件是诱饵）；`mode=checker` → 流程走 verify_exploit 而非 submit_answer。
7. **两个 worker 同题同卡点 = 强信号**（SAMPLE-002 实证）：别让它们继续磨，调度者亲打。
8. **诱饵附件**：公共附件可能是假货骗时间（SAMPLE-002 的 XOR 假附件），per-team-artifact tags 必先起实例拉真附件。
