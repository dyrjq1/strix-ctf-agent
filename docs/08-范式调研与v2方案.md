# 08 · 范式调研与 v2 改造方案（2026-10-30）

> 结论先行：**009 的失败不是"模型不懂 Web"，而是"观测带宽太窄 + 发现动作没有被产品化"。**
> 因此 v2 的主线不是再写 prompt、再堆技能文档，而是**把 009 里侥幸奏效的那几个动作，做成一次调用就能拿到结构化结果的原语**。
> 本文件只记录调研与决策；每一处改动在 `09-实验台账.md` 里必须有一行对应的基线/回滚记录。

---

## 一、调研来源与裁决

只采信三类来源：同行评审/预印本论文（可复现）、模型厂商的工程实证、安全社区的成熟方法论。
下表每一行的最后一列是**"对我们做什么"的裁决**——调研不落到裁决就是白读。

| # | 来源 | 核心结论（原文口径） | 对我们的裁决 |
|---|---|---|---|
| S1 | EnIGMA, arXiv:2409.16165（ICML 2025），390 题 / 4 个 benchmark | 交互式 agent 工具（gdb / 远程连接）比"一次性命令"显著更强：整体 29.5% vs 去掉 IAT 27.4%；去掉 demonstrations 掉到 23.3%（-6.2pp）；用交互工具平均 11.5 轮解出，不用要 14.9 轮（快 22.8%）。另发现 **soliloquizing**：38.4%–48.4% 的轨迹里模型"自己编造观测"，根本没碰环境 | 我们把"交互"理解窄了：对 Web 而言，交互 = **同一路由上换方法/换载荷并读回错误信息**。另外必须防 soliloquy，见 S7 |
| S2 | Anthropic《Effective context engineering for AI agents》(2025-09-29) | 上下文是有限注意力预算，存在 **context rot**；追求"最小的高信号 token 集合"；三大手段：compaction / 结构化笔记 / 子 agent 隔离 | 我们要**减上下文**而不是加：技能索引一次灌 16.5KB 是净负担；约束要贴在决策点，不要堆在 system prompt |
| S3 | Anthropic《Writing effective tools for agents》(2025) | 工具是"确定性系统与非确定性 agent 之间的契约"，不能照 API 的样子写；要为 agent 的 token 预算做返回裁剪；错误信息要携带可行动的上下文 | 直接支撑 P1：现在的网络原语是 `exec_command` + `curl` 字符串拼接，失败被压成 `000`，**没有可行动的上下文** |
| S4 | "When Skills Don't Help", arXiv:2605.20023 | 技能文档从 591 → 36001 tokens，通过率只 +8.9pp，**p=0.71，不显著**；5/6 组 Cohen's h < 0.2。作者给出的缺失变量是 **environment-feedback bandwidth**：当工具层返回严格、schema 校验、低延迟的观测时，环境本身就提供了技能文档想提供的纠错信号 | **止损**：不再扩充 `skills_strix/`。投入顺序按"观测质量 > 发现原语 > 纪律约束 > 文档" |
| S5 | STRIATUM-CTF, arXiv:2603.22577 | 基于 MCP 的标准化工具接口（系统自省 / 反编译 / 运行时调试）；2025 年底在真实校际 CTF 中**自主参赛拿第一，胜过 21 支人类队伍**；作者称 MCP 工具抽象显著降低幻觉 | 支持把关键动作做成**有 schema 的工具**而不是自由 shell；与 S3 同向 |
| S6 | "Evaluating Context Segmentation…", arXiv:2609.12839 | 两级 agent 框架把任务切成上下文隔离的子问题；在标准 agent 失败的题上**额外解出 18.52%**，且 token 更省 | 子 agent 是有效手段但**不是第一优先级**；先修观测层，再考虑切分 |
| S7 | CTF-ABACUS, arXiv:2608.26237 | 轨迹级溯源审计：1435 次尝试 / 240 题里，**只有 62%–87% 的"拿到 flag"是轨迹可验证的真实利用**，其余是直接暴露、记忆、外部查找或凭空断言 | 我们必须能回答"这个 flag 是从哪条工具输出里第一次出现的"，否则成绩不可信（这正是 035 被人工解过那类污染的同类问题） |
| S8 | DeepRed, arXiv:2604.19354 | 用 checkpoint 做部分给分；十个商用 LLM 在 10 道 VM 题上最好的也只有 **35% checkpoint 完成度**；**最弱项是"非标准发现"与"长程适应"** | 009 正是"非标准发现"（未文档化的 POST 端点）。评估指标必须记 checkpoint（走到哪一步），不能只看 solved/unsolved |

### 归纳出的三条法则

- **L1 观测带宽 > 提示词。** 模型的错误里有一半其实是"工具没告诉它真相"。`000` 既可能是不通、也可能是自己脚本写错——把这两种情况混在一个字符串里，模型必然误判。（S3、S4、S5）
- **L2 约束必须贴着决策。** 写在 system prompt 里的自我约束会随轮次衰减（本仓库 `enum_guard.py` 已用两版 prompt 验证过）。计数器必须放在**工具返回值**里，紧挨下一次决策。（S2 + 本仓库实测）
- **L3 发现动作要可复用。** 一次成功的探索如果只存在于某条轨迹里，就只是一次运气。要把"方法扫描 / 读错误消息当 schema / 从 JS 提路由"变成固定原语。（S1、S6、S8）

## 二、009 的实证诊断

同一道题跑了两遍，正好构成天然对照。

### v1（`--turns 8` → medium 实得 12 轮，失败）

| 轮 | 动作 | 判定 |
|---|---|---|
| 1–3 | `load_skill` 三次（triage + ctf-web 索引 16.5KB） | 半浪费：索引过大，且没有给出可执行的检查表 |
| 4 | `cd /workspace && mkdir pm` | **纯浪费**：目录不存在，命令链直接断，还烧掉一轮 |
| 5–8 | 下载 5 个 `_nuxt/*.js`，然后 `cat` / `head -c 8000` / `tail -c 7000` | **4 轮低信号**：196KB 压缩代码逐段肉眼读，**从未 grep `"/api/"`** |
| 9 | 23 条路径 GET 扫描 | 有价值，但只测了 GET |
| 10 | POST 三连测 | **静默失败**：`$B` 未定义（每次 `exec_command` 是新 shell）、`/tmp/o` 不存在 → 全部 `000`，agent 读成"POST 不支持" |
| 11–12 | `finish_scan` ×2（都被 finish_guard 拒绝） | 预算耗尽 |

12 轮里，**约 7 轮对解题零信息量**。

### v2（`--turns 25` → 40 轮预算，成功，140.1s，19 次调用）

制胜序列（来自 `agents.db` 逐条回放）：

1. 先用 `curl` 拿到 `x-powered-by: Nuxt`，并从 HTML 里读出 5 个 chunk 名；
2. **GET 扫描 + POST 方法扫描**（用 Python `urllib`，不再用 curl 拼串）→ `POST /api/plugins/preview` 返回 `{"error":"code_b64 required"}`；
3. **把错误消息当 schema**：空 body → `{"ok":true,"preview":"undefined"}`；`module` → `module is not defined`；`throw` → 原样回显 `boom`；`Object.keys(globalThis)` → 拿到完整全局表；
4. 发现 `_importMeta_` 与 `fetch` 存在 → `import('fs').readFileSync('/flag')`。

**关键事实：这四步里没有一步依赖"知道 Nuxt 的哪个 CVE"，全部依赖"敢换方法、会读错误、会枚举运行时"。**

### 由此定位的五个缺陷

| 编号 | 缺陷 | 证据 | 后果 |
|---|---|---|---|
| D1 | 网络原语是字符串拼接的 shell | `$B` 不跨调用持久；`head: cannot open '/tmp/o'`；`000` 语义混合 | 模型把自己的 bug 读成"目标不支持" |
| D2 | 没有"发现"原语 | 196KB JS 靠 `head -c` 肉眼读；无 `grep -o '"/api/[^"]*"'` | 4 轮换 0 信息 |
| D3 | 方法维度默认缺失 | 23 条路径只测 GET；POST 扫描是第 11 轮才想起来 | 唯一入口藏在 POST 上，差点整题丢掉 |
| D4 | 预算感知太晚 | 第 8 轮才意识到"只剩 3 轮"（原文："Only 3 turns left!"） | 恐慌式乱打，放弃结构化推进 |
| D5 | 角色冲突未裁决 | 第 2 轮原文："root agent shouldn't do hands-on testing… However… Let me balance"；第 3 轮又纠结一次 | 12 轮里 2 轮用于自我辩论；且全程没派子 agent |

## 三、v2 改造计划

排序原则：**先让测量可信，再让观测变宽，再管纪律，最后才碰架构。**
每一步都满足：单一变量、可独立回滚、有明确验收。

### P0 · 测量可信度（先做，否则后面全是幻觉）

- **问题**：`batch_eval.py` 用 `batch-{idx:02d}-{cid}` 命名，`box.mkdir(exist_ok=True)` 从不清理。于是同名目录被复用 → `strix_runs/` 命中 session resume → **同一个 agent id、同一份沙箱、DB 里 31 轮连在一起**。上一次"140.1s 解出"其实是**续跑**，不是干净基线。这会让 solve rate 虚高、耗时虚低。
- **改法**：每次运行生成唯一 `run_id`（时间戳+随机后缀），目录 `rm -rf` 后重建；运行结束把 `run.log` 与 `agents.db` 归档到 `~/runs/<run_id>/`；结果行里写入 `run_id` 与 git commit。
- **验收**：连跑两次，`strix_runs/.state` 的 session id 必须不同；两次日志首行 agent id 不同。
- **回滚**：单文件改动，`git revert` 即回。

### P1 · 观测层：把 `curl` 换成结构化 `http_probe`

- **依据**：S3（错误要带可行动上下文）、S4（schema 校验的观测本身就是纠错信号）。
- **改法**：新增一个工具，参数 `method / url / headers / body / timeout / follow_redirects`，返回结构化结果：
  `{"ok": bool, "phase": "dns|connect|tls|http", "status": int, "bytes": int, "ctype": str, "location": str, "body_head": str, "error_class": str}`
  - 传输层失败 → `phase != "http"`，且 `error_class` 明确（`NAME_NOT_RESOLVED` / `CONNECT_REFUSED` / `TIMEOUT`）。
  - 绝不出现"只有一个 `000`"的情况；也不允许 agent 自己拼 shell 导致 `$B` 这种状态丢失。
- **验收**：在 009 上复跑，v1 的第 10 轮那种"三个 000"现象不可能再现（工具层直接区分"目标不通"与"参数非法"）。
- **回滚**：新增文件 + 一行注册；删除即回，不影响旧路径。

### P2 · 发现层：`route_map` + `method_sweep`

- **依据**：S8（最弱项是非标准发现）、S1（交互式探测优于一次性命令）。
- **改法**：
  - `route_map(base_url)`：抓首页 HTML → 解析 `<script src>` / `<link rel=modulepreload>` → 抓取所有 chunk → 正则提取 `"/api/..."`、`"/_nuxt/..."`、`fetch("...")` 里的路径 → 按出现次数排序返回候选表（含来源文件）。**只做一次调用**，替代 v1 的 4 轮肉眼读。
  - `method_sweep(paths)`：对给定路径集合并发发 `OPTIONS/GET/POST/PUT/PATCH`，只回报**非 404/405** 的组合以及**非空错误体**（如 `{"error":"code_b64 required"}`）。
- **验收**：在 009 上，从首页到发现 `POST /api/plugins/preview` 的工具调用数 ≤ 4（基线是 11）。
- **回滚**：独立模块，从注册表摘掉即回。

### P3 · 纪律层：把预算与"无新增信息"注入到工具结果

- **依据**：S2（约束贴决策点）+ 本仓库已验证的 `enum_guard` 结论。
- **改法**：
  - 每次工具返回尾部追加一行极短的状态：`[STATE] turn 7/40 · 已用 132s/900s · 连续 2 次无新增信息`。
  - 把 `enum_guard` 从"同路径族重复 N 次"扩展为"**同族 + 观测指纹未变**"才算重复（v1 的 23 条路径各不同，所以旧规则一次都没触发）。
- **验收**：在 009 上，D4 现象（第 8 轮才发现预算）不再出现；日志里第一次出现 `[STATE]` 的轮次 ≤ 3。
- **回滚**：`enum_guard` 是独立模块；状态行由单一函数生成，关掉一个开关即回。

### P4 · 角色冲突裁决

- **依据**：D5 的原文证据。这是**配置错误**，不是模型能力问题。
- **改法**：显式规定"默认单 agent 直做；仅当出现两个以上**互相独立**且都能用一句话描述的假设时才 `create_agent`"，并把 root 的 orchestration 指令在 CTF 模式下关闭。
- **验收**：009 上检查轨迹，不再出现"should I delegate"式的自我辩论轮。
- **回滚**：只改 `config/` 文本与一个开关。

### P5 · 出处审计（provenance）

- **依据**：S7（只有 62–87% 的 flag 是轨迹可验证的）、以及 035 已被人工解过这个坑。
- **改法**：记录 `flag` 字符串**第一次**出现在哪条工具输出、该输出的来源 host 是否等于本题 `target`。提交时把这三元组写进结果行。
- **验收**：对历史 `solved-009` 回放，能判定"flag 来自 node1 的 preview 响应"；对人工解过的题能标记 `provenance=external`。
- **回滚**：纯记录，不影响行为。

### 明确不做（有依据的止损）

- **不扩技能文档**：S4 的负结果 + 本仓库 `tool_trim` 注释里"prompt 仍在教被摘掉的工具"的教训。
- **不先上子 agent 切分**：S6 有效但收益依赖观测层；先 P1/P2 再评估。
- **不并发起实例**：平台 `max_instances_per_team_effective = 1`，且红线段禁止。
- **不用镜像 harness**：`hosted_eval=false`。

## 四、实验协议（每一步都要能对比）

1. **单变量**：一次只改一个 P，`git commit` 一个，台账记 commit hash。
2. **干净基线**：每跑前 `rm -rf /tmp/ctfbox/*`；确认 `run_id` 唯一（P0 之后自动）。
3. **同题同预算**：先固定 `--turns 25 --wallclock 600` 在 009 上做 A/B；再有余量扩到 3–5 道 medium。
4. **记账字段**：`run_id / commit / challenge / solved / solve_time_s / tool_calls / agent_s / total_s / tokens / provenance / notes`。
5. **判定口径**：solved 之外同时记 **checkpoint**（P0→P2 各阶段是否达成），避免"差一点"和"完全没方向"被记成同一件事（S8）。
6. **回滚**：任何一步验收不过，`git revert <commit>` + 台账标 `rolled back`，不带着坏改动往下走。
