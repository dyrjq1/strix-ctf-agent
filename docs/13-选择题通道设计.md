## 1. 判分契约（读平台源码得到的，不是猜的）

平台源码就在 VM 的 venv 里：`.venv/lib/python3.14/site-packages/ctfy/`。

| 项 | 事实 | 出处 |
|---|---|---|
| 提交端点 | `POST /qa/submissions`，body `{challenge_id, competition_id, question_id, answer}` | `server/routes/qa.py:71` |
| 单选取值 | `sub = submission.strip(); sub in choices and sub == answer` → **大小写敏感、必须原样等于某个选项** | `challenge/runtime.py:184` |
| 静态题 | `submission.strip() == answer.strip()`（同样大小写敏感） | 同上 |
| 错误次数上限 | `single_select: 3`，`multi_select/static: 10`；锁死后只有管理员能重置 | `core/config.py:2023`、`cli/qa.py` 模块注释 |
| 提交限速 | 600 次 / 60 秒 | `core/constants.py:299` |
| 前置条件 | 必须已加入该 suite（`POST /competitions/{id}/teams {"mode":"solo"}`），否则 403 `not_registered`；题必须在该 competition 范围内，否则 403 `challenge_out_of_competition` | `server/auth.py:580`、`server/routes/qa.py` |
| 题面结构 | 题干与选项都在 `description` 里（`A) ... B) ...`），`questions[].choices` 只有字母 | 实测 3 个 bucket |

**结论：这是一道精度题。** 四选一随机猜，期望 0.75 次错误/题；错 3 次锁死，
所以"多答"没有意义，**"答不准就不交"**才是唯一正确策略。

## 2. 设计

1. **取题**：`GET /qa/challenges?competition_id=` 拿题干、选项、本队已解/已答错状态；已解或已锁的题直接跳过（可断点续跑）。
2. **解析**：正则按 `\b([A-D])\)\s` 切出四个选项；少于 2 个就跳过，不猜。
3. **三次采样 + 打乱选项**：第 1 次按原序，第 2/3 次洗牌后再问，票映射回**原始字母**。
   - 依据：`Zheng et al. 2023 (arXiv 2309.03882)` 证明 LLM 作多选题选择器有系统性位置偏置；`Wang et al. 2022 (arXiv 2203.11171)` 的自一致性说明多次采样取多数优于单次贪心。
4. **判定**：3/3 一致才提交；2/3 或更散 → 弃权。弃权不消耗任何机会。
5. **回写**：每题一行 JSONL（choice/votes/agree/correct/attempts_remaining），支持断点续跑。

## 3. 实测（2026-10-30，deepseek-v4.1-flash）

| 实验 | 结果 |
|---|---|
| 题库可达性 | MMLU-CS 100 / CTI-MCQ 100 / SECQA 210，`GET /qa/challenges` 全 200 |
| 干跑 6 题 | 5 题三票一致，1 题 `['B','A','B']` → 按规则弃权 |
| 真实提交 5 题 | 注册 201；**4/4 提交全部 correct，`attempts_remaining` 仍为 3**；1 题弃权 |

## 4. 踩到的坑（会重复踩，记下来）

- **reasoning 模型**：`max_tokens=8` 时 8 个 token 全进 `reasoning_content`，
  `content` 返回空串（`finish_reason=length`）。必须给足 600，并在 `content`
  为空时回退读 `reasoning_content` 的**最后一个**字母（结论在结尾，前面会复述选项）。
- **大小写**：判分是 `sub in choices`，选项是 `["A","B","C","D"]`，交 `"a"` 直接判错。
- **不要从 `choices` 取文本**：那里只有字母，选项文本在 `description` 里。

## 5. 下一步（未做）

1. **自适应采样**：3/3 → 交；2/3 → 追加 2 票，达到 4/5 才交。可在不增加锁定风险的前提下把可用题量从"一致率"提高到"多数率"。
2. **全量 410 题**：按当前 6–10 秒/题，串行约 50–70 分钟；并发 4 可压到 15 分钟（限速 600/min 不是瓶颈）。
3. **质量门槛**：全量跑之前先在 20 题上测准确率；低于 80% 就退回去调提示（例如给"先排除明显错误项"的推理步骤），而不是硬交。

## 6. 20 题准确率实测（2026-10-30 15:2x）

| 指标 | 数值 |
|---|---|
| 已提交 | 21 |
| 判对 | 19 |
| **准确率** | **90.5%** |
| 弃权 | 3（`split`，一票都不浪费） |
| 裁决分布 | unanimous 16 / majority 1 / split 3 |

**关键发现：3 票一致不等于必对。** `MMLU-CS-0021` 三票一致选 A，仍然判错——
说明"一致"只是高概率，不是证据。这也是必须保留 `attempts_remaining` 回写的
原因：任何一次提交后都要知道这道题还剩几次机会。

**自适应采样的收益**：1 道 `majority`（5 票里 4 票同向）被救回并判对；
3 道 `split` 弃权，一次机会都没消耗。

**域偏移熔断**（已实现）：同一 suite 交够 25 题后，若累计准确率 < 60% 立即停，
不把剩下的题拿去试错。换 bucket（MMLU → CTI → SECQA）时这条会生效。

```
for S in MMLU-CS CTI-MCQ SECQA; do
  .venv/bin/python -u scripts/qa_eval.py --suite $S --limit 500 --submit --register --out ~/qa-live.jsonl
done
```
