# 41 · 为什么单改动总是负反馈：归因与「消费端」测量（2026-11-15）

> 读者 = 下一个统筹窗口。本文回答用户提出的一个方法论问题：
> **是不是别的机制没跟上，才导致我们每次只改一处时拿到的都是负反馈？**
> 结论：**两类负反馈要分开算；绝大多数否决死在「前提不存在」，而不是「协同缺失」。
> 剩下的消费端有信号，但量级不足以支撑立项。**

---

## 1. 两类负反馈，不能混为一谈

| 类型 | 判据形态 | 我们记录里的例子 | 能不能被"补上别的机制"翻转 |
|---|---|---|---|
| **A. 前提测量被否**（离线、零 token） | 前提发生率 < 预注册地板 | A 平段 8.6%（地板 30%）、D 同命令 ≥3 次 0.6%、E′ 截断增量 3.1%（地板 10%）、F 主类占比反向、G 覆盖 8.9%（地板 10%）、H 拦下调用 0.5–2% | **不能**。没有任何别的机制能把 0.6% 变成 20% |
| **B. 上线后消融无差异** | A/B 两臂同预算 | S2 形状停滞 0/20 触发、`negative_guard` 0 注入、`viability_probe` 无人调用、`fact_ledger` 7% 覆盖 | 理论上可能，但我们的 B 类**几乎全是零触发**——那是接线/挂载问题，不是能力协同 |

**反证**：单改动成功的案例不少——B-23 把隧道重派 262 条压到 15 条、`llm_preflight` 止住坏 key、
派单 canary 停队、`finish_guard` 是唯一高频生效的守卫。**"单改动必负"不成立**，负的是我们选的
作用点。

**B 类里真正意义上的"别的机制没跟上"有过一次**，形态是**接线**：`turn_budget` 未挂载、
autosubmit 未接线、工具没注册。修完都是正反馈。这是"管道没接上"，不是"能力互补"。

---

## 2. 「缺一环循环」的检验：观测之后到底有没有想

用户假设：agent 只猜不做 / 认死方向，是因为缺「感知→推理→行动→观察→判定」的闭环。
零 token 重放 422 个可解析 `agents.db`，看每次 `function_call` 紧邻的前一项是什么：

| 指标 | 解出组 (n=205) | 未解出组 (n=163) |
|---|---|---|
| 反射调用占比（上一项是工具输出，没有 reasoning/message） | 中位 0.000 / 均值 **0.100** | 中位 0.029 / 均值 **0.076** |
| 每条调用的 reasoning+message 数 | **1.22** | **1.26** |
| 反射占比 ≥0.10 的 run | 35.1% | 27.0% |

**两组持平，解出组反而更"反射"一点。** 加上此前量的驻留、切换、连段（`docs/38` §8.10）：
**闭环的每一节在两组里都同样在场**——缺的那一节如果真缺，解出组也该缺。

对应地，**失败组不是不挖，也不是死守**：调用 p50 40 vs 14、方向 11 vs 6、最长连段 6 vs 4、
每 10 次切换 5.54 vs 5.30、解出组 61% 的方向只碰一次。**它只是同样地动、动得更久、没命中。**

## 3. 消费端：事实产出了，有没有被用

这是"别的机制没跟上"最像的一环（生产者有、消费者无）。零 token 重放，按响应哈希分三档：

| 指标 | 解出组 | 未解出组 |
|---|---|---|
| 字面重复（同签名同响应） | 均值 0.010 | 0.016 |
| **重新推导（同响应、不同签名）** | 均值 **0.014** | **0.036** |
| 不同响应 / 调用数 | 0.976 | 0.948 |
| `rederive_share ≥ 5%` 的 run | **8.8%** | **23.3%** |

**信号存在且方向正确**（失败组是解出组的 2.6 倍，触达 23.3% 的失败 run），
**但绝对量太小**：失败组平均只有 3.6% 的调用在重推已知事实（42 次调用里约 1.5 次）。
即使做一个完美的消费端机制，省下的也只是这 1.5 次调用——**不足以改变解出率**。

对照：`docs/38` §8.6 候选 E 已经量过"探到不跟"——**失败组跟得更全**（.767 vs .728）。
所以"观测到了不消费"在两个不同口径上都**不是**失败组的主要特征。

## 4. 为什么流程类机制效应必然趋近 0（本文的正面结论）

把上面三组数字放在一起看，失败组与解出组在**过程统计上几乎逐项相同**：

| 过程量 | 解出 | 失败 | 差异 |
|---|---|---|---|
| 首次接触位置 | 第 1–2 次调用 | 同 | 无 |
| 接触成功率 | 98.1% | 98.6% | 无 |
| 每 10 步换类 | 3.19 | 4.24 | 失败**更**频繁 |
| 每条调用前的思考 | 1.22 | 1.26 | 无 |
| 反射调用占比 | 0.100 | 0.076 | 无（解出略高） |
| 重推已知事实 | 0.014 | 0.036 | 失败略高，量小 |

⇒ **区分变量不在"怎么动"**。守卫、门、换向、记忆隐藏都只能约束"怎么动"，提供不了
"往哪动"的信息，因此对两组一视同仁，**期望效应量趋近于 0**——这不是协同缺失，是
**作用点不在区分变量上**。

**诚实的限制（统计功效）**：我们的 A/B 多是 20–40 题/臂、解出率 ~50%，检测 <10pp 的差异
本身就需要上百场；"无差异"经常是"检不出"而不是"没用"。但第 1 节的 A 类否决是**计数**，
不受功效限制——那部分结论是硬的。

## 5. 若将来要验证"协同效应"，正确的做法

用户假设的可检验形态是「机制 X 只在机制 Y 存在时有效」。这需要 **2×2 设计**
（X 开/关 × Y 开/关，四臂同题同预算），成本约 4 组 × 20 题。**赛前（11-20）不做**：
现有 8 项否决里没有一项是"激活了但没收益"，全是"前提不存在"或"零触发"，不值得为一个
未出现的现象付四臂成本。

**消费端若重启**，预注册要求：
1. 触发门槛：`rederive_share ≥ 5%` 的失败 run 占比 ≥20%（本次 23.3%，勉强过线）；
2. 收益门槛：机制必须证明能把重推次数降到 0 且**解出率不降**——先做 3 题消融，再看迁移；
3. 反例测试必须包含"页面在两次访问之间发生变化"的情形（否则会挡掉合法的重读）。

## 7. 边界

- 方向/签名归一化是启发式的（数字→#、空白折叠、前 1500 字符），跨 run 不可比、组内可比。
- "重新推导"里包含合法重读（页面内容在两次访问间变化、附件未变但工具重读），
  本文只量规模，不判定好坏。
- 结局标签取结果行 `correct`，受平台判分影响；`unknown` 组 54 场未计入比较。
