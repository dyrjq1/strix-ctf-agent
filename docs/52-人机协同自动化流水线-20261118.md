# 52 · 人机协同自动化流水线（京华杯/THUCTF 2026）

> 写于 2026-11-18。读者：参赛者本人 + 负责实现的 agent。
> 目标：人只做「平台操作 + 最终提交」，其余（读题后的分析、开工作区、派发多个 agent、
> 汇总 flag 与题号、生成 WP 草稿）全部自动化。
>
> 依据：`CCF-TPCTF赛事规则手册-v2.7.pdf`（2026-11-17）与
> `首届CCF网络安全智能挑战赛 Q & A (2).xlsx`（截至 11-16）。

---

## 0. 一句话裁决

**京华杯 232 是人机协同个人赛：平台交互必须由人完成；平台之外的一切都可以自动化。**
原设想里的「自动读题、自动开实例、自动提交」在规则上不成立——不是技术问题，是合规问题。
把人的动作压缩到「复制题面 / 下载附件 / 点开实例 / 粘贴 flag」四步，其余交给流水线。

## 1. 规则裁决（先看这一节，再谈架构）

### 1.1 可以做 vs 不可以做

| 环节 | 谁做 | 依据 |
|---|---|---|
| 登录平台、浏览题目、复制题面 | **人** | Q&A #1：「与比赛平台的交互获取题目/提交 Flag 等不允许大模型智能体直接交互」 |
| 下载附件、启动/重置题目实例 | **人** | 同上；Q&A #51：「人机协同赛道不要使用智能体对平台进行任何自动化操作」 |
| 提交 flag | **人** | Q&A #1；手册 §二(二)「独立提交 Flag」 |
| 题面/附件落到本地后的**分析、逆向、写 EXP、跑利用链** | 全部自动化 | Q&A #1「无限制，选手自由使用人机协同方式」；#44「分析模式不限」 |
| 同时跑多个本地 agent（strix / codex / Claude Code / 原版 strix） | 全部自动化 | 规则只限「每队同时启动的题目实例数」（且那是智能体赛道口径）；人机协同赛道未限本地 agent 数量（Q&A #104 该问题官方未答） |
| 自由选择大模型 | 全部自动化 | Q&A #1；手册 §二(一)「使用 AI 工具辅助分析、漏洞挖掘及 EXP 编写」 |
| 自动抓取平台题目列表 / 自动提交 flag | **禁止** | Q&A #1、#51；手册 §五(一) 禁止共享账号与不正当协助 |
| 队伍外人员代解 | **禁止** | 手册 §二(一)、§五(一) |

### 1.2 三条容易踩的细则

1. **单题有提交次数上限**（Q&A #60：无扣分，但「设置单题最多提交次数」，具体值未公布）。
   → 流水线只输出高置信度 flag，宁可标「待人工判断」也不刷提交。
2. **每道获分题要交 WriteUp**，赛后 4 小时内发 `thuctf@tsinghua.edu.cn`；
   用 AI 的必须说明「AI 的作用 + 人工验证过程」，否则撤分（手册 §五(三)）。
   → 流水线必须落盘完整 transcript 并自动生成 WP 草稿；人负责核对与签名。
3. **Flag 是按赛道/队伍/实例动态生成的**，只能提交本队授权实例的 flag（手册 §五(三)）。
   → 不能拿网上的 flag，也不能跨实例复用。

### 1.3 如果你其实想要「全自动」

唯一的合法路径是**智能体赛道**（不是京华杯 232）：agent 部署在主办方 VPS、自主拉题、
自主并发（平台限制每队同时 3 个题目实例）、赛前部署后不允许人工调试。那条赛道的
工程形态与本文完全不同，且与人机协同赛道在正式赛互斥（Q&A #9/#22/#65）。
本文只覆盖 **人机协同（京华杯 232）**。

## 2. 架构：一条人工边界，两边各司其职

```
 [人] 浏览器（本机）                      [机器] 本机工作台 ~/ctf-desk
 ─────────────────                      ────────────────────────────────
 看题 ──复制题面──┐                     inbox watcher
 下载附件 ────────┼──→ 直接拖进 inbox ──→ │ 注册题目、判题型
 点开实例 ────────┘      (零传输)         ▼
                                     orchestrator（队列 + 并发 + 预算）
                                        ├─ worker A: strix（web/pwn）
 读 submit-sheet ←──── 同一个目录 ──────  ├─ worker B: codex 改造版（rev/crypto）
 复制 flag → 平台提交                     ├─ worker C: Claude Code（rev/misc）
                                        └─ worker D: 原版 strix / 通用 CLI（兜底）
                                              │ 隔离 workdir、独立预算
                                              ▼
                                     flag 提取 / 归一 / 去重 / 置信度
                                              │
                                     outbox/：submit-sheet.md + flags.jsonl
                                              + wp/<题号>.md + evidence/
```

**关键点：流水线代码里没有任何访问比赛平台的网络调用。** 合规不是靠自觉，是靠架构保证——
平台凭据不进机器、不写配置、代码里没有提交函数。

### 2.1 为什么默认在本机跑（VPS 不是必需）

规则禁的是「智能体对平台做自动化操作」，**没规定在哪台机器上算题**。人机协同赛道
选手自己的网络是通的（与智能体赛道的 `internet_policy=deny` 完全不同），题目实例从本机
直连即可。因此默认方案是**本机**：

- 人的浏览器、题面、附件、提交单都在同一台机器上，**零传输**——省掉 scp/上传页这层
  最容易出错、也最磨人的步骤；
- 仓库 `.venv` 现成，`ctfdesk.py` 只用标准库；
- 例外是 **pwn**：gdb/ELF 工具链在 Windows 上没有，且反弹 shell / 带外回连需要**公网可达
  地址**（家里 NAT 给不了）。这类题优先丢 **VPS**（工具链 + 公网 IP 一举两得），本机
  Ubuntu VM（`192.168.38.130`）作备份；不是每道题都过线。

VPS（`39.107.41.223`）降级为**可选**，只在两种情况下启用：8 天赛程里人离开电脑、
想让题继续跑；或本机并发撑不住。启用时才需要那条人工同步链路（`scp`/`rsync` 或
80 端口上传页），upload 页只接收文件、不访问比赛平台，不属于「对平台的自动化操作」。

## 3. 目录与数据契约

```
~/ctf-desk/
  inbox/<challenge_id>/
    statement.md        # 人粘贴的题面（必须由人产生）
    meta.json           # 人填：name/category/url/host/port/flag_format/notes
    files/              # 人下载的附件
  work/<challenge_id>/<agent>/   # 每个 agent 的隔离工作区
  outbox/
    flags.jsonl         # 每行一个候选：{id, flag, confidence, agent, elapsed_s, evidence}
    submit-sheet.md     # 人看的表：题号 | 题名 | flag | 置信度 | 来源
    wp/<challenge_id>.md
    evidence/<challenge_id>/<agent>/transcript.jsonl
  state.db              # sqlite：题目状态、派发记录、提交回执（人填）
```

`meta.json` 最小字段：

```json
{"id":"WEB-01","name":"...","category":"web","target":"http://10.0.0.5:8080",
 "flag_format":"flag\\{[^}]+\\}","notes":"登录页 500","added_at":"2026-11-20T10:05:00+08:00"}
```

设计约束：**没有 `meta.json` 就不派发**。这样流水线永远不会自己去猜平台上的题。

## 4. Agent 适配器（统一接口，异构后端）

```python
class AgentAdapter:
    name: str
    def solve(self, task_dir: Path, meta: dict, budget: Budget) -> SolveResult: ...
```

`SolveResult = {flag, confidence, transcript, artifacts_dir, notes, exit_state}`

| 适配器 | 调用方式 | 适合题型 | 备注 |
|---|---|---|---|
| `strix` | `scripts/run_strix_ctf.py` + `agent.py` 官方入口（task.json → result.json） | web/pwn/rev/misc | 现成工具面最全，优先 |
| `codex` | `codex exec --cd <workdir> "<task>"`，解析最后消息与落盘文件 | rev/crypto/web | 改造版；沙箱 `[windows] sandbox="unelevated"` 或 Linux 直跑 |
| `claude` | `claude -p --output-format stream-json` 或 Agent SDK，允许 Read/Bash/Grep | 通用 | 长上下文、读代码强 |
| `generic` | 命令模板 + 环境变量（`$TASK_DIR`/`$META`/`$BUDGET`） | 任意 | 接原版 strix / 其他 CLI |

统一约定（所有适配器必须遵守）：

1. 只在 `work/<id>/<agent>/` 内读写，禁止访问 `inbox/` 以外的其它题；
2. 结束时把候选 flag 写到 `RESULT.json`（`{"flag":..., "confidence":..., "notes":...}`）；
3. 完整 transcript 落 `transcript.jsonl`（供 WP 与复核）；
4. 超时/超轮次由 orchestrator 杀进程，不看 agent 自觉。

## 5. 调度与并发

- **并发单位是题**：默认 `--workers 3`（本地 agent 并发不受平台限制；受本机 CPU/内存与
  模型 API 限流约束）。
- **内存闸门**：每轮派发前读一次可用内存，按「保底 1.5 GB + 每路 700 MB」收窄并发，
  低于保底线只跑 1 路，并把 `free mem=... -> workers=...` 打进日志。
  这台机器（i7-14650HX / 16C24T / 15.7 GB）只留 VM + 浏览器时的配置：
  **`--workers 3`，VM 分 4 GB，浏览器占 1.5 GB**。
- **同题可赛马**：难题同时派 `strix` + `codex`（不同模型），先产出高置信 flag 者停另一路。
  这是「发挥并发优势」的正确用法——并发的对象是题和 agent，不是平台实例。
- **预算**：每题 wall-clock 默认 15 分钟（对齐 §6.4 时间盒），easy/medium/hard 可配；
  全局 token/费用上限单独记账，超限只降并发不降质量。
- **防重复**：`state.db` 里同题同 agent 不重复派发；已产出 `confidence>=0.9` 的题不再跑。
- **题型路由**：web → strix/代码 agent；rev/crypto → codex/claude；pwn → strix（工具链）；
  misc → 通用 + 解码工具。

### 5.1 赛期口径（232，2026-11-18 核实）

- **11-20 10:00 → 11-28 20:00 连续 8 天多，没有每日 10–20 关门**。`10:00` / `20:00` 是赛期
  **两端的时刻**，不是每天开关机。依据：DataCon 232 详情正文「该赛道的比赛时间为
  11月20日10:00-11月28日20:00**连续举办**」；平台赛事列表 `beginTime/endTime` 只有一对。
- 容易混淆的「每日 10:00–20:00」是**全国赛**（231）口径：初选 11-20 单日、正式 11-21/22 每日。
  232 借它同一批题，但赛期不同。
- 由此确定三件事：①夜里也能跑、也能交，机器不关就能通宵推题；②预算按 **8 天累计**记，
  不是每天重置；③**232 与 231 初选同题，231 在 11-20 20:00 结束**——当晚之后同题
  writeup 大概率上网，agent 检索策略里应包含「赛后公开资料」，但 flag 按队伍/实例动态
  生成，只能用思路、不能取答案。

## 6. 输出与人工提交

`submit-sheet.md` 示例：

```
| 题号 | 题名 | Flag | 置信度 | 来源 | 用时 |
|---|---|---|---|---|---|
| WEB-01 | 登录绕过 | flag{...} | 0.95 | strix | 6m12s |
| REV-03 | 反调试 | flag{...} | 0.70 | codex ⚠ | 14m50s |
```

- 置信度 ≥0.9：可直接提交；
- 0.6–0.9：标 ⚠，建议人看一眼 evidence 再交；
- <0.6：不进提交单，只进 `flags.jsonl` 备查。

人提交后回填 `state.db`（或直接在表里打勾），流水线据此停掉该题所有 worker。

## 7. WP 与证据（容易被忽略、但会撤分）

规则要求「每道获分题 4 小时内提交 WP，含关键分析、复现步骤、代码，并说明 AI 作用与
人工验证过程」。流水线在解题时就该把材料攒好：

- 每个 worker 的 `transcript.jsonl`（工具调用、命令、输出、关键推理）；
- `artifacts/`（脚本、payload、截图）；
- 自动生成 `wp/<id>.md` 骨架：题目理解 → 侦察 → 漏洞/算法 → 利用 → flag 获取 → AI 使用说明；
- 人只补「人工验证过程」一节并核对事实。

**不要把「全自动」写成 WP 的卖点**——规则要看的是人确实验证过。

### 7.1 「人工验证」到底验证什么（不会安全也能做）

规则要的不是「你会做题」，而是**证明 flag 是本题真解出来的、不是编的/抄的**。验证对象是
flag 的真实性与来源，不是你的漏洞知识。按四级做，做到 L2 就是合格的人工验证：

| 级别 | 做什么 | 不会安全的人能否完成 |
|---|---|---|
| L1 可复现 | 跑 agent 写的 `VERIFY.md` 里的命令，看到同一个 flag | ✅ 复制粘贴一条命令 |
| L2 来源核对 | 命令打的是本队实例/本题附件；输出与 transcript 对得上 | ✅ 看 URL/文件名/时间戳 |
| L3 格式核对 | flag 符合题面给的格式，不是示例串；多 flag 题逐条对应 | ✅ 肉眼比对 |
| L4 解释 | 能用自己的话复述思路（照 WP 草稿念也行） | 可选，主办方不考你 |

**诚实原则**：没做过的不要写。若 flag 是一次性的（实例销毁后无法重放），就写
「依据 transcript 第 N 步的响应与实例 id 核对」，不要编造一次不存在的复现。

WP 里可以这样写（真实做过才写）：

> AI 完成分析并产出利用脚本。本人于 11-20 11:05 在本队实例 `<id>` 上执行该脚本，
> 输出包含 `flag{...}`，与题面格式一致；核对脚本只访问了本题目标。

工具支持：agent 现在必须产出 `VERIFY.md`（复现命令/期望输出/来源核对/人工核对要点），
并随证据一起落盘；人跑完验证后用一条命令存证：

```bash
python scripts/ctfdesk.py record --root ~/ctf-desk --id WEB-01 \
  --command "python exploit.py http://<本队实例>" \
  --observed "flag{...}" --source "本队实例 <id>" --result pass
```

记录写到 `outbox/verify/<题号>.md`，带时间戳，WP 的「人工验证记录」一节直接引用。

## 8. 合规红线（写进代码，不靠记性）

1. 代码中不出现任何比赛平台域名/接口/凭据；不做提交、不抓题、不起实例。
2. 不把平台 cookie/token 交给任何 agent。
3. flag 只从本队实例取得；不接入任何外部 flag 源。
4. 单题提交次数有限：流水线不自动重试提交，只产出候选。
5. 不做平台扫描/压测（Q&A #51 明确禁止）。

## 9. MVP 里程碑（按 11-20 开赛倒排）

| 时间 | 交付 | 验收 |
|---|---|---|
| 11-18 夜 | `ctf-desk` 骨架：inbox watcher + sqlite + strix 适配器 + submit-sheet | 手工建一道题，能出 flag 行 |
| 11-19 | codex / claude 适配器 + 并发池 + 超时杀进程 | 三题并发跑通，互不污染 |
| 11-19 夜 | WP 草稿生成 + evidence 落盘 | 任意一题能生成可读 WP |
| 11-20 开赛 | 实战；人只做四步平台操作 | 首题从上传到提交单 ≤ 15 分钟 |

### 9.1 已实现（MVP，2026-11-18 夜）

- `scripts/ctfdesk.py`：inbox 扫描 → 注册 → 并发派发 → 结果提取 → 提交单/WP/证据落盘；
  单文件、仅标准库、**代码里没有任何平台域名或提交函数**。
- `tests/test_ctfdesk.py`：假 agent 端到端（成功 / 无 flag 两条），`2 passed`，不联网。
- 默认 `agents.json` 已内置三个适配器：`strix`（走 `run_strix_ctf.py`）、
  `codex exec`、`claude -p`；可用命令模板接原版 strix 或其它 CLI。

```bash
python scripts/ctfdesk.py init  --root ~/ctf-desk
# 人：把题面/附件/元数据放进 ~/ctf-desk/inbox/<题号>/
python scripts/ctfdesk.py watch --root ~/ctf-desk --workers 3 --interval 30
python scripts/ctfdesk.py status --root ~/ctf-desk
```

已知限制（MVP 有意留的）：赛马时先解出的题不会杀掉仍在跑的另一路；进程崩溃后
`running` 状态要人工清；`codex`/`claude` 适配器尚未在本机实跑（11-19 验）；
pwn 需走 VPS / 本机 Ubuntu VM，`ctfdesk` 目前没有「远程工作区」适配器，暂按
本机 + `ssh` 命令模板接。
