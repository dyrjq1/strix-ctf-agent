# 42 · 两条剩余线索的前提测量：`write_stdin` 轮询与收尾被拒（2026-11-15）

> 读者 = 下一个统筹窗口。本文只做一件事：把 `docs/39` §5 里**唯二没量过前提**的两条线索
> 量掉——`write_stdin` 轮询吃工具墙钟、收尾被拒不给最短路径——并按同一套判据给出立/否。
> **结论：两条都否，且都不是"缺了协同"，一条是分母问题，一条是位置问题。**
> 零 token、零实例、只读 `agents.db` + 结果行。

## 0. 结论先行

| 线索 | `docs/39` 的断语 | 实测 | 判定 |
|---|---|---|---|
| `write_stdin` 轮询 | "占未解出组 **42.5% 墙钟**" | 占**工具墙钟** 43.4%（复现）；但工具只占整轮墙钟 31.8%，故占**整轮** 13.8%；真正空等的部分只占整轮 **6.2%** | **分母问题**：账是对的，可省的量是 6.2%，不是 42.5% |

两条都不立项。它们与此前 A–H 八项否决同型：**作用点不在区分变量上**（`docs/41` §4）。

## 1. 口径与可复现性

- **样本**：VM 全库 460 个 `agents.db`；按结果行 `correct` 分 解出 205 / 未解出 163 / 未知 54。
- **工具墙钟口径**：各次调用输出里自带的 `Wall time: N seconds` 之和（`exec_command` 与
  `write_stdin` 输出都带）。**`created_at` 不能用**：实测是秒级、按 agent 步批写（同一秒内
  多条），逐次差恒为 0，第一版脚本因此得空结果，已废弃。
- **空轮询判据**：`write_stdin` 输出里 `Output:` 之后为空（典型形态
  `Wall time: 15.0148 seconds | Process running with session ID … | Output: |`）。
  工具自身报错（`stdin is not available`）单列，不算空等。
- **收尾被拒判据**：`finish_scan` 输出含 `REFUSED`（`finish_guard._REFUSAL` 的原文）。

| 组 | runs | 调用 | agent_s 合计 | 工具墙钟 | `write_stdin` | 其中空等 | 工具占整轮 |
|---|---|---|---|---|---|---|---|
| 解出 | 205 | 3894 | 33 638s | 5166s | 1381s（26.7%） | 418s（30.3%） | 15.4% |
| 未解出 | 163 | 6935 | 95 161s | 30 219s | 13 126s（**43.4%**） | 5880s（44.8%） | 31.8% |
| 未知 | 54 | 1529 | — | 5131s | 1684s（32.8%） | 479s（28.4%） | — |

`docs/39` 的 42.5% 复现为 **43.4%**（样本集合略有差异），**账无误**。问题出在分母。

## 2. 线索 1：`write_stdin` 到底吃掉了什么

### 2.1 三层分母

```
未解出组整轮墙钟 95 161s
 ├─ 工具墙钟        30 219s  (31.8%)   ← 其余 68% 是模型/框架延迟
 │   ├─ exec_command 17 092s  (56.6%)
 │   └─ write_stdin  13 126s  (43.4%)
 │       ├─ 有新输出   7246s  (55.2%)  ← 模型确实需要这份输出
 │       └─ 空轮询     5880s  (44.8%)  ← 唯一可被机制消掉的部分 = 整轮的 6.2%
```

- 单 run：`write_stdin` 墙钟 p50 **30s** / p90 **234s** / 均值 **80.5s**；
  空等 p90 **110s**；`write_stdin` 占本 run 墙钟 均值 **10%**、p90 **31%**；
  **空等占本 run 墙钟** 均值 **5%**、p90 **16%**。
- 解出组对照：`write_stdin` 只占工具墙钟 26.7%，空等占整轮 **1.2%**。

### 2.2 覆盖：真正受影响的 run 只有两成

| 阈值（单 run 累计空等） | 未解出组 | 解出组 |
|---|---|---|
| ≥60s | **36 / 163 = 22.1%** | 2 / 205 = 1.0% |
| ≥120s | 15 / 163 = 9.2% | 2 / 205 = 1.0% |
| 空 poll ≥4 次 | 21 / 163 = 12.9% | 2 / 205 = 1.0% |

这 36 个 run 里，空等占**自身**墙钟 p50 **14.8%**、max **34.5%**。看起来可观——
但看它们为什么停：

| 停止原因 | 36 个受影响 run |
|---|---|
| 无记录 `<none>` | 28 |
| error | 2 |
| turn_capped | 2 |
| **wallclock** | **2** |
| unknown | 2 |

**墙钟并不是失败组的主要停止原因**（全组 163 个 run 里只有 26 个记 wallclock，
6 个 turn_capped，90 个无记录）。省下的墙钟换不到轮次；轮次是另一个预算。

### 2.3 空轮询在看什么：一半在盯自己起的循环

未解出组 222 次空 poll，回溯最近一次 `exec_command`：

| 上下文 | 次数 | 占比 |
|---|---|---|
| 循环/后台任务（`for`/`while`/`sleep`/`seq`/`xargs`） | 119 | **53.6%** |
| 单条命令 | 100 | 45.0% |
| 找不到（跨轮） | 3 | 1.4% |

典型样本：`sleep 45; B=https://…; for p in / /api/coins/stats; do curl …; done; dig …`
——模型起了一个慢命令，然后连发 3–5 次 `write_stdin` 每 15–30s 看一眼，输出还是一串 `404`。

⇒ **轮询是信使，不是病因**。真正的动作是把一条慢的、重复性概率极高的命令扔给 shell；
消掉轮询只是让它换个方式等同一段时间，或者更早拿到同一批 `404`。

### 2.4 判定：不立项

按与前八项一致的判据（覆盖 ≥10% 失败 run、可省 ≥10% 相关预算、是机制缺陷而非症状、
消融有可能动解出率）逐条：

1. 覆盖面：22.1% 的失败 run ≥60s —— **擦线过**；
2. 可省量：整组 6.2%、受影响 run 的 14.8% —— **不过线**（预注册地板 10%）；
3. 无消融可动的因果：受影响的 36 个 run 里只有 2 个是墙钟停的，**省时间换不来求解**；
4. 53.6% 的空轮询是在监视模型自己起的循环——这是"一直在试同一招"的**症状**，
   与 `docs/38` §8.10 驻留统计、`docs/41` §4 同源，属于内容层，不是调度层。

**若将来重开**（唯一合理形态，成本极低但预期效应≈0）：把 `write_stdin` 的单次阻塞窗口
从 15/30s 提到 45–60s，纯减少轮询次数，不改动作空间。**不立项的理由不是它有害，而是它
不改变解出率**；且它落在墙钟预算上，按红线不能单独调。

## 3. 线索 2：收尾被拒到底浪费了什么

### 3.1 规模

| 组 | `finish_scan` 调用 | 被拒 | 拒绝率 | 有 ≥1 次被拒的 run | 每 run 被拒次数（均值/p50/p90） |
|---|---|---|---|---|---|
| 未解出 | 369 | 218 | **59.1%** | **104 / 163 = 63.8%** | 1.34 / 1 / 3 |
| 解出 | 319 | 36 | 11.3% | 30 / 205 = 14.6% | 1.20 / 1 / 3 |
| 未知 | 71 | 45 | 63.4% | 25 / 54 = 46.3% | — |

解出组里被拒的 30 个 run，**100% 最终有一次被接受**，且 52.8% 的拒绝发生在"只剩 1 次
调用"处——模型在最后一发里把 summary 补上答案、收尾成功。**这是守卫在正常工作**。

### 3.2 `docs/39` 的断语"模型把它当可重试错误"——不成立

| 指标（未解出组） | 值 |
|---|---|
| 被拒后下一次调用**参数完全相同**的 `finish_scan` | **1 / 218 = 0.5%** |
| 被拒后下一次调用 = `exec_command`（回去干活） | 96 / 218 = 44.0% |
| 被拒后下一次调用 = 又一次 `finish_scan`（改措辞） | 73 / 218 = 33.5% |
| 被拒后 run 直接结束（没有下一次调用） | 37 / 218 = 17.0% |
| 被拒到下次收尾之间**产出新观测** | 窗口 n=157，新观测 p50 **1**、均值 2.32；零新增 47.8% |

⇒ 它不是"当瞬时错误重试"（0.5%），而是**换措辞重交 + 少量新观测**；有 44% 当场回去
执行 `exec_command` 并确实拿到新东西。**"重试死循环"这个画像不成立**。

### 3.3 真实缺陷是位置：拒绝落在预算耗尽点上

| 该次被拒后 run 还剩几次调用 | 0 | 1 | 2 | 3 | 4 | ≥5 |
|---|---|---|---|---|---|---|
| 未解出（n=218） | 37 | 50 | 27 | 15 | 10 | 79 |
| 解出（n=36） | 0 | 19 | 7 | 1 | 2 | 7 |

- 未解出组 **39.9%** 的拒绝发生在 ≤1 次调用、**52.3%** ≤2 次；解出组 52.8% / 72.2%。
  在那一格里，拒绝文本列的六条"回去拿 flag"路径**没有一次调用可执行**。
- 未解出组里 **58.7%（61/104）的 run，最后一次被拒之后再没试过收尾**——run 就这么结束。
- 但首次被拒之后总账：p50 还剩 3 次调用、均值 7.1 次，占该 run 调用数 **13.7%**；
  其中 43.3% 的 run ≥10%、26.9% ≥20%。这段尾巴里产出新观测 p50 2、均值 6.0。
  **不是纯烧**——一半以上的窗口在产出新事实。

停止原因对照（未解出）：有被拒的 104 个 run 调用 p50 44 / 均值 50.0；有 finish 但没被拒的
28 个 run p50 25；从没碰 finish 的 31 个 run p50 33。有被拒的 run 更长，但"更长"既可能是
守卫拉长，也可能是走得更深，**离线不能分辨**（要消融）。

### 3.4 案例复核：CYBENCH-037 的真相比 `docs/39` 写得更具体

`20261112-073140-CYBENCH-037`：靶子中途变成全站 `404 page not found`（19 字节）。
第 59/61/64 次调用三次 `finish_scan` 被拒，中间夹着 `exec_command` 对着死靶继续打
`root=404`；第 67 次才以 `{"success": true}` 收尾。**拒绝文本让它"回去拿 flag"，
而那时唯一可交付的就是"靶子没了"**。

但这个画像**不具代表性**：全部 218 次未解出组拒绝里，前 5 次观测中连接级失败
（refused / 解析失败 / 超时 / 5xx）≥3 次的只有 **3 次 = 1.4%**。所以"给死靶加一条
靶不可达就放行"的分支，**只能救 1.4% 的拒绝**，不构成立项理由。

### 3.5 判定：不立项

1. 行为缺陷不成立（原样重交 0.5%；44% 回去干活并拿到新观测）；
2. 可省的量是"首次被拒后的尾巴" = 13.7% 的调用，且其中一半在产出新事实；
3. 真正的"最短路径"问题是**位置**：39.9% 的拒绝落在 ≤1 次调用处。要修得让守卫**更早**
   触发（在还有 5–10 次调用时就提示），那是"提前提醒"类流程机制——
   `docs/41` §4 已证这类机制对解出/失败两组一视同仁，**期望效应趋近 0**；
4. 缩短拒绝文本有**反向风险**：解出组 14.6% 的 run 靠这段文本在 1 次调用内补齐答案。

**若将来重开**：只在 `turn_budget` 剩余 ≤2 次时把拒绝换成一句
"预算耗尽，这次就是最后一次；没有答案就写 `answer: <你手上最可能的串>`"——
这是文案层的零风险改动，收益上限 = 每 run 1–3 次调用。

## 4. 两条线索共同的教训

`docs/39` §4 把这两条排在"可修性 高"，依据是**占比**（42.5%、3/6 回合）。本次测量把占比
拆回口径后，两者都退化为：

- 一个是**分母问题**（占工具 43.4% vs 占整轮 13.8% vs 可省 6.2%）；
- 一个是**位置问题**（行为对了，但落在预算耗尽点）。

这与 `docs/41` 的正面结论完全一致：**失败组与解出组在过程统计上几乎逐项相同**，
所以凡是只改"何时/如何动"的机制——轮询节奏、收尾提示、守卫文案——**都只能改成本，
不能改命中**。能改命中的只剩内容层（往哪动），而内容层不在赛前窗口内。

## 6. 边界

- 工具墙钟取输出里自带的 `Wall time`，是工具侧自报值；`write_stdin` 的 15/30s 阻塞窗口
  会计入其中，因此"空等"包含"阻塞等输出"的合法部分。
- `agent_s` 只对 368 个解出/未解出 run 有效（54 个未知组无结果行），故整轮占比只用这两组。
- "有被拒的 run 更长"是观察不是因果：守卫拉长 vs 走得更深无法离线分辨，需同题消融。
- 空轮询上下文靠"回溯 6 次内最近 `exec_command`"归属，跨轮/子 agent 情形会漏判（3 条）。
