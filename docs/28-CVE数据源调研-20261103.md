## 3 版本匹配的坑：要不要混源

### 3.1 KEV 单独用会产生「有洞但判不了」

| 方案 | 结果 | 实测依据 |
|---|---|---|
| KEV → `rule` | **不可行** | 12 个字段里没有版本；`shortDescription` 里的版本是自然语言 |
| KEV 版本字段为空 → `evaluate("", ver)` | 全 True（空规则视为无约束） | `verrule` 语义：空表达式直接命中 |
| 后果 | 只要产品名对上，**该产品的全部 KEV 条目都会报出来** | 实测 `evaluate("", "1.0")` 与 `evaluate(None, None)` 均返回 `True`；Apache 的 41 条会一次全出，且不区分 2.4.49 / 2.4.58 |

这和 `aig_probe` 的既有硬规则「版本块不是命中依据」冲突：**会把已修版本误报成有洞**。CTF 里这等于把 agent 引向打不通的路径。

### 3.2 NVD cvelistV5 的 CNA 字段也不能直接用

实测 `CVE-2021-41773`（cvelistV5）：

```json
"affected": [{
  "vendor": "Apache Software Foundation",
  "product": "Apache HTTP Server",
  "versions": [{"status": "affected", "version": "Apache HTTP Server 2.4 2.4.49"}]
}]
```

版本是**自由文本**，`verrule` 无法比较。
`CVE-2021-44228` 稍好，用 `lessThan: "log4j-core*"` + `changes[]`，但仍是 CNA 自定义语义。
抽 20,000 条 cvelistV5 记录，**仅 18 条**含 `cpe:2.3` 字符串（0.09%）——CVE Program Container 装的是 references，不是 CPE。

而 KEV 的 1,766 条里，1,765 条在 cvelistV5 有记录、1,765 条有 `affected.versions`，但**只有 729 条**带 `lessThan`/`lessThanOrEqual` 这类边界（729/1765 = 41.3%；其中 `lessThan` 616、`lessThanOrEqual` 132，有重叠）。
剩下的是「`version: "1.2.3"` 精确值」或自由文本。

### 3.3 NVD `configurations[].cpeMatch[]` 才是可用形态

我把 25 个年度 feed 全解压，按 `cpeMatch` 生成表达式，规则模板：

```
exact:        version == "2.4.49"
range:        version >= "7.0.0" && version < "7.0.100"
multi-range:  (...) || (...) || (...)
```

实测生成率与正确性：

| 检验 | 结果 |
|---|---|
| 参与生成的 CVE | 10,369（限定 79 个产品族） |
| 生成表达式条数 | 10,678 |
| 用现有 `verrule.evaluate` 回放 | **全部可解析，0 异常** |
| `CVE-2021-41773` @ 2.4.49 / 2.4.51 | `True` / `False` ✅ |
| `CVE-2020-1938` @ 9.0.30 / 9.0.31 | `True` / `False` ✅ |
| `CVE-2024-4577` @ 8.3.7 / 8.3.8 | `True` / `False` ✅ |
| 表达式均长 | 191 字符（最长 7,019） |
| 形态分布 | 含 `\|\|` 7,608 / 纯 `==` 2,249 / 纯 `&&` 821 |

### 3.3.1 原型已知缺陷：CPE 的 update 段

CPE 2.3 的第 7 段是 `update`，承载 `sp1` / `rc1` / `beta1` 这类补丁级标识：

```
cpe:2.3:a:apache:http_server:1.3.14:*:*:*:*:*:*:*        <- 无 update
cpe:2.3:a:apache:http_server:2.0   :alpha9:*:*:*:*:*:*   <- update = alpha9
cpe:2.3:a:microsoft:exchange_server:5.5:sp1:*:*:*:*:*:*  <- update = sp1
```

我第一版原型**只取 `version` 段、丢弃了 `update`**。全量实测影响：

| 范围 | `cpeMatch` 总数 | 带非 `*` update | 占比 | 涉及 CVE |
|---|---|---|---|---|
| 全部 417,804 条 | 2,659,191 | 484,304 | 18.21% | — |
| 79 个 web 产品族内 | 92,894 | 15,940 | **17.16%** | **1,467** |

把 update 段拼回 `version`（`5.5` + `sp1` → `version == "5.5-sp1"`）后重新生成：

| 指标 | 结果 |
|---|---|
| 产品族 / 条目数 | 79 / 10,678（**不变**） |
| 规则串发生变化 | **1,535 条（14.4%）** |
| 新增条目 | 0 |

示例（`microsoft:exchange_server` / `CVE-2002-0054`）：

```
旧: (version == "5.5")
新: (version == "5.5") || (version == "5.5-sp1") || (version == "5.5-sp2") || (version == "5.5-sp3") || (version == "5.5-sp4")
```

**结论与取舍**：
- 丢弃 update 会**把 SP/RC/Beta 级差异抹平**——对 Exchange、Windows NT 这类按 SP 分版本的产品是系统性失真。
- 但把 update 直接拼进 `version` 也不是标准语义。NVD 的 `cpeMatch` 里，`5.5` + `sp1` 与 `5.5-sp1` 的 banner 写法并不总是对得上。
- **建议**：在索引里保留两个键 —— `r`（cpeMatch 原始区间，SU 无关）与 `u`（update 段列表）。运行时先按 `r` 判定，若目标 version 带 `-sp1` 之类后缀再按 `u` 收紧。这样既不丢信息，也不强行合并两种语义。
- **这一项必须在实现时写单测**，用 `exchange_server 5.5` / `5.5-sp1` 两个版本对跑。否则原型里 17% 的 CPE 是失真的，且从外面看不出来（条数一样）。

| 2025 | 45,449 | 19,383 | **42.6%** | 16,417 | 36.1% |
| 2026 | 83,685 | 47,095 | **56.3%** | 30,531 | 36.5% |

→ 越新的 CVE 越缺 CPE 富化（NVD 的 enrichment backlog）。而 CTF 出题恰恰偏好新洞。
**缓解**：KEV 恰好覆盖「新且被利用」的一批，两者互补——这正是混源的理由。

### 3.5 混源方案（推荐）

```
构建期：
  KEV  ──> 只取 (cveID, vendorProject, product, dateAdded, ransomware, cwes, desc)
           └─> 打 kev=true 标记 + 作为无版本时的「值得查」列表
  NVD  ──> cpeMatch ──> verrule 表达式
           └─> 按 vendor:product 建索引
  合并键：CVE id
运行时：
  lookup(product, version):
    1) 命中产品索引 → 逐条 evaluate(rule, version)
    2) version 为空 → 只返回 rule 为空 或 kev=true 的条目（明确标注「未定版本」）
```

理由（每条都有上面的实测支撑）：
1. KEV 无版本 → 只能当信号，不能当判定；
2. NVD 有版本 → 是唯一能喂 `verrule` 的机器可读源；
3. KEV 的 1,766 条里有 189 条落在 79 产品族索引内，能提高排序质量；
4. NVD 新洞覆盖率差 → 用 KEV 的「在野利用」标记兜住最新一批；
5. cvelistV5 与 GHSA 都不产生可用版本区间（0.09% / 90.6% 空），排除。

### 3.6 verrule 自身的三个坑（实测）

| 输入 | 表达式 | 结果 | 问题 |
|---|---|---|---|
| `2.4.49 (Unix)` | `version < "2.4.49"` | **True** | banner 后缀参与比较，把 2.4.49 判成小于 2.4.49 |
| `9.0.0.M1` | `version >= "9.0" && version <= "9.0.99"` | **False** | Tomcat 里程碑版被漏报 |
| `2.0-beta9` | `version >= "2.0.1" && version < "2.3.1"` | False | 正确（beta9 < 2.0.1），但需靠 NVD 的精确条目补上 |

**必须在取版本后做归一化**：剥离 `(Unix)` / `-ubuntu0.1` / `+deb12u1` 等发行版后缀，保留 `a.b.c` 与 `rc/beta/dev`。
归一化不做的漏报/误报，靠改表达式补不回来。

另：KEV 的 `vendorProject` 与 CPE vendor 字符串不是一套。用「小写+去空格后互为子串」做启发式，1,765 条里 **191 条不匹配**（如 KEV `Broadcom` / CPE `vmware`、`Palo Alto Networks` / `paloaltonetworks`）。→ 需要一张**别名表**，不能只做字符串归一。

## 4 快照老化与体积上限

### 4.1 增长速率

KEV（`dateAdded` 分年）：

| 年 | 2021 | 2022 | 2023 | 2024 | 2025 | 2026(至10-30) |
|---|---|---|---|---|---|---|
| 新增 | 311 | 555 | 187 | 186 | 245 | 282 |

- 近 365 天 +315；近 730 天 +565；近 1095 天 +744。
- 稳态约 **+250~320 条/年**。
- 3 年后 ≈ 2,600 条：minified ≈ 2.1 MB，gz ≈ 270 KB。**增长不是问题**。

NVD：

| 年 | 2021 | 2023 | 2024 | 2025 | 2026 |
|---|---|---|---|---|---|
| CVE | 23,481 | 31,475 | 39,362 | 45,449 | 83,685 |

- 年度 gz 从 16.9 MB（2021）涨到 43.3 MB（2026），5 年 **2.6 倍**。
- 全量已 245.5 MB gz / 2.90 GB raw。按 2021→2026 的年均 1.207 倍复利外推，2029 年累计约 **436.9 MB gz / 3.49 GB raw**（说明：2026 是截止 11-03 的部分数据，实际会更高）。

### 4.2 体积上限判断

镜像预算 100 GB 级，**磁盘不是瓶颈**：

| 物件 | 体积 | 占 100 GB |
|---|---|---|
| KEV 原文件 | 1.8 MB | 0.002% |
| NVD 25 年 gz | 245.5 MB | 0.25% |
| NVD 25 年 raw | 2.90 GB | 2.9% |
| cvelistV5 zip / raw | 717.0 MB / 3.36 GB | 0.7% / 3.4% |
| GHSA zip / raw | 500.1 MB / 599.9 MB | 0.5% / 0.6% |
| **裁剪后的运行时索引** | **2.56 MB（无描述）/ 4.31 MB（带描述）** | 0.004% |

**真正的约束是「常驻 schema / 启动开销」，不是镜像体积**：

| 变体 | 原始 | gzip |
|---|---|---|
| 79 产品 × 10,369 条（含 170 字描述） | 4,412,302 B（4.31 MB） | 484,784 B |
| 同上，去描述 | 2,619,263 B（2.56 MB） | 112,860 B |
| 同上，只留 severity+rule（无描述） | 2,619,263 B（2.56 MB） | 112,860 B |
| 只留 KEV 命中条目（52 产品 / 223 条） | 72,168 B | 14,230 B |

→ **带描述 4.3 MB、无描述 2.6 MB 是推荐区间**。JSON 解析后 Python 内存约 3–4 倍（10–16 MB），可接受，但应当**懒加载**（首次调用时读，不要 import 期读）。

**不建议**把 417,804 条全量建索引：按均 250–400 字节估算 **100–170 MB**，启动解析秒级，且 90% 与 CTF 无关。若将来要扩，转 SQLite + 按产品查询。

### 4.3 老化对策

- 构建期落 `manifest.json`：`{source, url, fetched_at, catalogVersion, sha256, entry_count}`。
  KEV 有 `catalogVersion`；NVD 每个 `.meta` 有 `sha256`；GHSA 用 commit sha。
- 镜像内**只读快照**，运行时零网络（符合 `agent_internet=deny`）。
- 重建节奏：KEV 日更（但赛前冻结即可）、NVD 周更。**赛前 3 天内重建一次**，冻结后不再变。
- 对 CTF 而言「新洞」比「全量」重要，冻结时间越接近开赛越好；但重建必须发生在**上传镜像之前**。

## 6 推荐方案

### 6.1 数据源与取舍

| 源 | 角色 | 体积 | 许可 |
|---|---|---|---|
| **CISA KEV** | 必带。`kev=true` 标记 + 无版本时的「值得查」列表 | 1.8 MB 原 / 184 KB gz | CC0 1.0，无义务 |
| **NVD 年度 feed** | 必带（构建期）。唯一机器可读版本区间来源 | 245.5 MB gz / 2.90 GB raw（可只保留产物） | NIST 公共信息，请求署名 |
| cvelistV5 | **不带**。版本是自由文本，0.09% 含 CPE | — | CVE ToU，需带 MITRE 版权声明 |
| GHSA | **不带**（除非将来做包生态题）。90.6% `affected` 为空 | — | CC-BY-4.0，须署名 |

### 6.2 产物

```
/var/ctf/cve/
├── web_cve_index.json      # 2.6 MB（无描述）/ 4.3 MB（带描述）
├── kev.json                # 1.4 MB minified（或直接并入索引的 kev 标记）
├── aliases.json            # banner 名 → vendor:product（手写 + 归一化）
├── manifest.json           # 来源 / 版本 / sha256 / 抓取时间
└── NOTICE                  # NIST + （若用）GHSA 署名
```

索引形状（与现有 `vuln_index.json` 同构，`lookup` 可复用）：

```json
{
  "apache:http_server": {
    "CVE-2021-41773": {
      "s": "high",
      "r": "version == \"2.4.49\"",
      "k": 1,
      "d": "Apache HTTP Server 2.4.49 path traversal ..."
    }
  }
}
```

- `s` = severity（NVD CVSS baseSeverity 小写，与现有口径一致）
- `r` = verrule 表达式
- `k` = 1 表示在 KEV 内
- `d` = 截断描述（≤170 字符）

### 6.3 映射到现有机制

1. `lookup(component, version, vendor)` 的**三级降级**保留，但在最前面插一层**别名词典**：
   `nginx → f5:nginx`、`Apache Tomcat → apache:tomcat`、`WebLogic → oracle:weblogic_server`。
   实测 nginx 在 NVD 里主要挂在 `f5:nginx`（41 条），而 `nginx:nginx` 只有 2 条 —— 不做别名会漏 95%。
2. `evaluate(rule, version)` 原样复用，**0 改动**。已用真实表达式回放验证（§3.3）。
3. `version is None` 时**不要**走 `evaluate("")`（会全命中）。返回 `k==1` 的条目并显式标注「无版本，仅候选」。
4. 取版本后先归一化（剥离 `(Unix)`、`-ubuntu*`、`+deb*`），再进 `evaluate`。
5. `scan()` 的 `top_vulns` 排序改为 `(kev desc, severity, cve)` —— KEV 命中优先。

### 6.4 常驻成本

- 新增 1 个工具：**+717 字符**（docstring 350 + schema 367），约 180 token/请求。
- 或扩展现有 `ai_cve_lookup`：**+0 字符**（仅 catalogue summary 一行）。
- 数据文件 2.6–4.3 MB 落盘，**不进 prompt**；懒加载，首次调用解析 <50 ms。

### 6.5 风险

| 风险 | 实测依据 | 缓解 |
|---|---|---|
| **新产品/小众组件无索引** | 只覆盖 79 个产品族 | 保留 `aliases.json` 可增量；未命中时回退到 KEV 关键词检索 |
| **NVD 新洞无 CPE** | 2026 年 56.3% 无 `configurations` | KEV 补新洞；索引里保留「无规则但 kev=true」桶 |
| **版本串噪声** | `2.4.49 (Unix)` 被判 `< 2.4.49` | 归一化 + 单测覆盖 banner 后缀 |
| **厂商名不一致** | 191/1,765 KEV vendor 与 CPE vendor 启发式不匹配 | 手工别名表，不用纯字符串匹配 |
| **误报量大** | httpd 2.4.49 一次命中 88 条 | 已有 `top_k` 截断；KEV 标记置顶 |
| **许可** | KEV CC0；NIST 请求署名；GHSA CC-BY-4.0 | 镜像内放 `NOTICE`，写明来源与许可 |
| **快照过期** | 2026-10-30 后新增漏洞不在内 | 赛前 3 天冻结重建；`manifest.json` 记录时间戳 |
| **过拟合** | —— | 索引按**产品族**建，不针对任何具体题目/路径/flag；见 §7 |

### 6.6 不建议做的事

- **不要**把 KEV 的 `shortDescription` 里的版本用正则抠出来当规则 —— 措辞不统一，且这是典型的「对着样本调」。
- **不要**为某个具体 CVE 写预置查询分支。
- **不要**在运行时联网校验快照。
- **不要**把 4.3 MB 索引塞进 system prompt。

| 判据 | 本方案 |
|---|---|
