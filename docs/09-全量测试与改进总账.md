## 1. 阶段①：A/B 基线实验（10-28）

### 设计

同一道题、同一模型、同一 turn 预算，**只改一处**：给 agent 的任务指令。

| 组 | 指令 |
|---|---|
| A 基线 | 空（strix 默认 prompt，只给 target URL） |
| B 对照 | `config/ctf_goal.txt`，**只重定义成功标准**，不含任何漏洞位置信息 |

B 组只说了三件事：成功 = 输出 `FLAG{...}`；不要产出报告；**拿到代码执行后立刻去找并读取目标文件**。第三条是方法论约束，不是答案。

### 主对照

| 指标 | A 基线 | B 对照 | 变化 |
|---|---|---|---|
| 拿到 flag | ❌ | ✅ `FLAG{b10c8d01…}` | — |
| 运行耗时 | 845.7 s | **432.5 s** | **−48.9%** |
| 工具调用 | 123 | **42** | **−65.9%** |
| 结束原因 | `MaxTurnsExceeded` | `[done]` 正常 | — |

### 泛化验证（指令一字不改）

| 题号 | 难度 | 机制 | 结果 | 调用 | 耗时 | solve_rank |
|---|---|---|---|---|---|---|
| UPLOADLABS-001 | easy | 纯前端扩展名校验 | ✅ | 42 | 432.5 s | 0 |
| UPLOADLABS-003 | medium | 后缀黑名单 + MIME | ✅ | 36 | 314.8 s | 0 |
| UPLOADLABS-011 | hard | 保存路径操纵 | ✅ | 42 | 436.0 s | 16 |
| UPLOADLABS-006 | medium | 尾缀接收 | ✅ | 48 | 559.0 s | 17 |

四题手法各不相同（`.php` 直传 / `GIF89a` 魔数 + `.phtml` / 路径操纵 / 尾缀接收），说明约束是**方法论级**的，不是答案泄露。

### 根因：A 组不是「能力不够」

日志证据——它**已经拿到** `uid=33(www-data)` 的任意命令执行，webshell 可用。紧接着的 8 个动作是：

```
create_note → update_coverage ×3 → save_threat_model
→ create_agent → create_vulnerability_report
```

**一次 `cat` / `find` 都没做。** 最后自己说 `Turn budget exhausted; confirmed RCE evidence already captured`。

> 它把 RCE 证据写进 coverage 就认为任务完成了。这是**目标函数问题**：strix 被训练成「交付渗透测试结论」，不是「取走目标物」。

### 预算去哪了

A 组 123 次调用分类：

| 类别 | 次数 | 占比 |
|---|---|---|
| 真实攻击动作 | 72 | 58.5% |
| **记账类**（coverage/notes/threat_model/report/graph） | **34** | **27.6%** |
| 子 agent 管理 | 10 | 8.1% |
| 其他 | 7 | 5.7% |

B 组 42 次里，**记账类降到 0**。这是工具面裁剪的依据。

### 一个诚实的负面结果

`tool_trim.py` 把 43 工具裁到 20，跑 006 得 48 次调用（011 未裁剪 42 次）。但两题难度机制不同，**不能证明裁剪有害**，也不能证明有益。能确定的只有：裁剪没引入崩溃；全程仅 1 次真实 `Tool not found`；**prompt 仍在教 agent 用已摘掉的工具**。

**结论：单摘工具不是收益点。** 想省预算必须同时改 prompt，否则只是把「调用记账工具」换成「调用失败」。

### 意外发现：root 应当只做调度

B 组三个 agent 分工：

| agent | 调用 | 干了什么 |
|---|---|---|
| root | **9** | 全是管理动作，**一次都没直接打靶机** |
| 侦察/攻击 | 21 | 18 次 exec + 2 次 apply_patch |
| 验证 | 11 | 10 次 exec，独立复现并 `cat /answers/flag` |

root 的上下文是最稀缺资源。A 组失败的一部分原因就是 root 自己也去做侦察（29 次调用），把上下文喂给一堆扫描输出。

### 关键：token 口径

prompt 占 **99.9%**。每次工具调用都把全部历史重发一遍，**所以「多刷几轮」的代价是平方级的**——018 和 010 各吃掉近 100 万 prompt token，等于两道题的预算。

一道题平均 40.7 万 prompt token。

### 三个致命缺陷（本轮最大收获）

**① flag 选取靠排序 → 提交到诱饵**

CTFARENA-015 日志里同时出现 3 个 flag：

| flag | 来源 |
|---|---|
| `FLAG{5245c057…}` | 目标机回显 —— **正确答案** |
| `FLAG{b99d5528…}` | agent `grep` 到 `/tmp/batch/` 下**上一题**的日志 |
| `FLAG{09622ca9…}` | 冒烟测试遗留的 `ctf_recon.md` |

原代码 `sorted(flags)[-1]` 取字典序最后一个，命中诱饵。

> **根因不是排序，是把「选哪个 flag」当成了排序问题。它本质是证据问题。**

**② flag 被物理切断**

日志钩子写 `output[:300]`，flag 正好落在截断边界：

```
TOOL finish_scan {"executive_summary": "...**Flag: FLAG{b9
```

`od -c` 确认 `FLAG{b9` 后面直接换行——完整 flag 从未进入日志。

**③ 跨题污染**

那两个诱饵不是被注入的，是 agent **自己翻到的**：它执行了 `ls /tmp`、`grep -r FLAG{ /workspace`，从历史日志里捡答案。正赛同一容器连打多题会直接导致提交错误 flag。

### 两道超时题的死因

- **018**：90 次调用里 `/api/coins` 相关探测重复 **38 次**，同一族端点反复列举，780s 全烧在枚举上。
- **010**：25 轮处被强停，停的那一刻**正在**用 `.well-known/jwks.json` 伪造 JWT。差一步。

都不是能力不足，是**预算与收敛策略**问题。

### 三个坏题是平台侧的

003/012 的 `README.txt` **逐字节相同**（md5 `9e469e58…`，236 字节），内容是 `TODO: replace this README…` 模板，路径还写着 `SAMPLE-003`（说明 012、004 是复制没改）。003/012 的服务端也是占位：

```
dev-edge health-check service v0.3
commands: ping / version / quit
```

### 昨日 8 题判 FAIL 的真正原因：判定链三层叠加

「解题」和「得分」在 CTFY 里是两个独立动作。agent 常拿到答案后直接 `finish_scan` 退出，一次都不提交。

| 层 | 症状 | 根因 |
|---|---|---|
| ① | `NOT SUBMITTED: 没有待答的 question` | 用 `answered_correctly` 过滤，但该字段**不拦提交** |
| ② | 日志说"没有 flag 类 question" | `_TIMEOUT=(10,45)` 元组传给 urllib（只吃浮点）→ `TypeError` → 被 `except Exception` 吞成空列表 |
| ③ | `ACCEPTED` 打出来了，父进程仍判 FAIL | run 结束后实例被销毁，父进程补交全撞 `instance_not_found` |

**checker 题同理**：`pending_checkers` 也用 `answered_correctly` 过滤，这类题的 checker question 一开局就是 `true`，于是 sidecar 一次都没跑——即使 agent 已经拿到 `FLAG{banner_defacement_confirmed_HACKED_BY_CTF}`。

### 判定口径（重构后，别再改回去）

**把三个信息源混成一个 bool 就是错的。**

```
solved_qids            本轮同实例拿到的 correct / passed。唯一成绩来源
platform_solved        实例级 answered_correctly。不可信，只做参考
team_solved            challenge API 的队伍账本。决定"这题还能不能测"
clean_start            队伍账本为空
unmeasurable           队伍账本覆盖全部 question，或附件是占位模板
ok = solved_qids 非空 且 remaining_qids 为空
```

### 瓶颈是延迟，不是轮次

单次 LLM 往返 25–30s。最多的 009 也只用了 19 次工具调用（上限 42），却耗时 618s。006/007/008 分别收在 389/421/420s，**后两题是贴着 420s 墙过的**——这层右截断会让 easy 的通过率混入延迟噪声。后来 easy 上调到 480s。

```

dify   0.6.9  -> 25 条    comfyui 0.3.27 -> 9 条
```

### 说明书里的三个坑

| 坑 | 后果 | 处理 |
|---|---|---|
| `register_skill_dir(整包)` | 145 条进 prompt，约 8.5k token/次调用 | 只注册 12 个索引，降到约 3k |
| 子文件路径是「背包根相对」 | 按 cwd 解析必然 404，模型猜一次就烧一轮 | 装载时注入 jail 内绝对路径提示 |
| `load_skill` 是 list 参数 | 照抄会 TypeError | 改 list 形式 |

> 路径提示要插在 frontmatter **之后**：strix 用 `^---` 锚定，插到最前面会让 `name`/`description` 解析失败，技能变「无名」。

### 一个只在带附件题触发的真 bug

```
mount: /var/ctf/jail/rt/files: special device reports/files/SAMPLE-001 does not exist
```

子进程 `Popen(..., cwd=box)` 起的，**cwd 不是仓库根**，而附件目录是相对路径。mount 按 box 解析 → 源不存在 → `set -e` 中断整次启动，还记成一次 FAIL。

### 已知问题：技能是「可得」不是「必用」

两跑同一道 mock 题（明确写「第一步必须 load_skill」）：一次真加载了，一次完全跳过、开局去 `find /` 找规则文件。

> 和枚举守卫是同一个教训：**prompt 里的顺序约束会衰减**。要稳定生效得用硬约束。

| CTFARENA-003 | medium | 🟡 半解 | 156.2s | 11 | 733k | flag 判对 `FLAG{f35e1bfb208019eef899669ae1817c70}`；第二问 `technique` 未答 |
| CTFARENA-006 | medium | ❌ 超时 | 156.8s | 12 | 810k | 撞墙 |

### 三个必须说清的判断

**① 五道 medium 全是「在干活时被掐断」**

工具调用 11/12/8/8/8，token 48–81 万，说明它一直在执行命令、读输出、换思路——只是 155 秒到了。**这轮数据测的是「155 秒能推进多少」，不是「GLM-5.2 能做多难的题」。**

**② medium 是双问题结构，成本被低估一倍**

`remaining_qids` 显示 medium 题为 `['flag', 'technique']`。拿 flag 只算一半，还要写清利用手法。

**③ 模型 id 是大写 `GLM-5.2`**

小写 `glm-5.2` 返回 `400 no healthy deployments for this model`。这是本轮最初 401/400 的真正原因，**不是 key 失效**。

### 本轮修掉的两个基建 bug

**LiteLLM 价目表远程拉取（必现，吃半题预算）**

`litellm` 启动去 `raw.githubusercontent.com` 拉价目表，该域名在本机不可达，每次 ConnectTimeout ≈ 22s × 重试 3 次 ≈ 66s。表现是「tokens=0，跑满 155 秒」。修法：`LITELLM_LOCAL_MODEL_COST_MAP=True`。

**智谱账号 5 小时配额**

`429 code=1308 已达到 5 小时的使用上限`，第一题 165k token 就把窗口用尽。换并行科技后消失（3.73M token 无限制）。

## 7. 阶段⑦：镜像 v1 与它的致命缺陷

### 成果

镜像 `strix-ctf-agent:1.0.0`（886 MB / amd64）推送成功：

```
registry.ctfy.io/f0aef9e3-3b15-4648-8b7c-e1e3c1a01f79/strix-ctf-agent:v1
digest sha256:2105671b…（15 层）
```

两条 blocking conformance 本地自检通过（无 task.json / dry_run 自定义路径）。

### 构建侧的两个优化

| 问题 | 修法 | 效果 |
|---|---|---|
| `docker build` 卡 654 秒（Debian 索引慢） | `--build-arg APT_MIRROR=` | **654s → 9s** |
| 改代码触发依赖重装 | 依赖层放在源码层之前 | 重建几分钟 → 几秒 |

依赖安装用 `pip install --no-deps -r requirements.lock`：锁文件里有 `fastmcp 4.1.4` 要 `mcp>=2.3` 而实际装 `mcp 1.30` 的死结，任何解析器都会拒绝，但那套组合实测能跑。**照单装才是忠实复现。**

### 🔴 v1 镜像带着一个致命缺陷

容器内 `RuntimeSettings.backend` 默认是 `"docker"`，strix 会去 Docker Hub 拉一个叫 `unused-local:latest` 的占位镜像：

```
APIError: 500 Server Error for http+docker://localhost/v1.47/images/create
  ?fromImage=unused-local:latest
```

**而 eval 脚本里设了 `STRIX_RUNTIME_BACKEND=local`，所以本地评测从没暴露。** v1 镜像推上去，dry run 能过（dry run 不跑 agent），**真跑必挂**。

修法一行：`docker/entrypoint.sh` 加 `export STRIX_RUNTIME_BACKEND=local`。**这是 v2 的第一优先级。**

### 查清「报告投递 404」的真因

现象：同一 URL、同一 token、同一份正文，run 内偶发 404 且返回前端 SPA 的 `index.html`。

对照实验：

| 实验 | 结果 |
|---|---|
| run 内并发保存 | 偶发 404 |
| 独立进程串行打同一 URL，**40 次** | **40/40 = 200** |
| 抓到的 404 正文在独立进程重放 | 200 |
| 12 KB 大正文 / 迷你正文 / 自定义 UA | 全 200 |

> **404 是网关的瞬时抖动，不是内容相关，也不是「端点不存在」。**

代价是致命的：平台**每次保存都抽证据计分**，一次抖动丢的那一版永远补不回来。实测出现过 `attempts=5, successes=1`——只存进去一版。

### 另一个静默失败

协议 §1.1 说平台注入 `CTFY_PLATFORM_URL`，但 §2 的 **engagement task.json 示例里既没有 `platform_url` 也没有 `platform` 字段**。三条路全空 → `configured()=False` → **静默跳过投递**，而 `result.json` 一切正常、`stop_reason=completed`。

日志里只有一行 `report delivery configured=False`，混在长输出里根本看不见。

### 一次值得记录的自身失误

第一轮端到端跑出来的报告写着 "port 80 was unavailable"、发现全空。查下来不是 agent 不行，是**我自己在清理时把靶机实例 `DELETE` 了**，`scope` 里的域名只剩 DNS 记录没有后端。

> 教训：本地测试前先 `GET /api/v1/instances` 确认非空。另外平台 `DELETE` 会同步等编排层销毁，偶尔先返回 503 但实例状态不变——直接重试即可，别当成已删除。

### 9.2 三条贯穿全部阶段的教训

**① 写在 prompt 里的自我约束会随轮次衰减，程序里的计数器不会忘。**

枚举收敛规则写了两版都没生效——模型在第 5 次调用时，前 4 次探测已被后来的工具输出埋没，它对「我重复了」没有感知。同理有「先走完正常用户旅程」「finish 前三问」，都是 prompt 版失败、硬约束版生效。技能加载也是同一现象。

**② 判定口径不能把多个信息源混成一个 bool。**

昨夜 8 题判 FAIL，根因全在判定链，不在模型。`solved_qids` / `platform_solved` / `team_solved` 三者含义不同，混用必错。

**③ 本地测不出来 ≠ 没问题。**

- `STRIX_RUNTIME_BACKEND` 在 `run.sh` 里设了，本地永远好，容器里必挂；
- `dry_run` 不跑 agent，所以它测不出「agent 起不来」；
- 附件 bind 的 cwd 问题只在带附件的题触发，11 题全过也没暴露。

**凡是「只有真实环境才走到的分支」，都必须单独造一次真实环境验证。**

## 12. 一句话总结

**50+ 题次跑出 20 多个缺陷，其中真正决定成败的不是模型能力，是四类工程问题**：目标函数错配（拿 RCE 就收工）、判定链断裂（解对了但没交）、预算分配失当（hard 题饿死）、容器契约遗漏（本地好、镜像挂）。

通过率从 73%（12 题）到 100%（SAMPLE 11 题）的变化，主要来自修 bug，不是换模型。
