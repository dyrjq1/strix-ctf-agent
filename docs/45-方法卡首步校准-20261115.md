# 45 · 方法卡首步校准（2026-11-15）

> 上游：`docs/44-解出题解法台账-20261115.md`（99 条解出 run / 74 道题的自述解法）。
> 本文只回答一件事：**用已知解法能不能优化方法卡**，以及如果能，改哪几处、怎么验收、什么时候必须回滚。

---

## 1 结论

能优化，但**不是**把解法抄成卡。可做的是三件事，按证据强度排序：

| 做法 | 判定 | 依据 |
|---|---|---|
| 从解法批量生成新卡 | **否** | 13 类手法里 11 类已有卡；99/99 次解出时卡一张都没注入 |
| 照解法文本写具体路径/参数进卡 | **否** | 违反命名测试；tag 路由会把个案招数泼到无关题 |
| **校准已有卡的「第一动作」** | **是** | 3 处严重错配，见 §3 |
| **把已解题固化成 A/B 回归语料** | **是** | 74 题有"无卡也能解"的真实反事实基线 |
| 从解法里找"还缺什么机制" | **部分** | 缺口的证据在失败侧（`docs/43`），解法只能当对照 |

---

## 2 为什么"抄解法"必然失败（三条硬证据）

1. **反事实为空**：全量 402 个 run 的 `agents.db` 首条消息里 `[Method cards]` 命中 **0**。
   那 99 次解出全部发生在无卡状态——解法里的每一步，agent 不带卡也已经会做。
   从这些题反推出来的卡，对它们自身的期望收益**按构造为 0**。
2. **覆盖率已饱和**：解法分布 13 类（信息泄漏 25 / 命令注入 23 / 上传 13 / 业务逻辑 9 /
   鉴权 8 / IDOR 7 / SQLi 6 / SSRF 5 / 穿越 5 / JWT 3 / XXE 2 / 逆向 1 / 弱加密 1），
   其中 11 类在 `method_cards.py` 里已有对应卡；只有逆向、弱加密没有，各 1 次，不值得为它加卡。
3. **误导是结构性的**：卡按 tag 路由。把"某题藏了个未公开 SKU"写成卡，它会在所有
   `business_logic` 题上注入，把几乎不成立的首步塞给无关题。这不是统计意义的过拟合，
   是**主动降分**。

## 3 首步对照：三处严重错配

数据来自 `scripts/experiments/card_first_move_probe.py`（对 `solve_notes.jsonl` 的
粗关键词归并，**结论只在比例极端时成立**；比例接近的子型不作数）。

### 3.1 信息泄漏卡 —— 首步正好是最少见的子型

卡现状：`先 http_probe /robots.txt、/sitemap.xml、/.git/HEAD、/.DS_Store；命中后落盘再 grep`

| 实际子型（提到信息泄漏类的 68 次内，重叠计数） | 次数 |
|---|---|
| sourcemap / bundle / chunk 里翻 | 23 |
| 页面 HTML / 响应体直接给 | 20 |
| 调试·诊断·遥测端点 | 6 |
| 已发布包（npm tarball / registry） | 5 |
| **经典文件（robots / .git / .DS_Store / sitemap）** | **1** |

判定：卡把唯一几乎不命中的子型放在第一步，把命中率最高的两类放在意识之外。

### 3.2 IDOR 卡 —— 默认动作比实际需要重一档

卡现状：`两个账号互换同名资源 id，看是否 200 且内容不同`

| 实际子型（IDOR/越权类 32 次内） | 次数 |
|---|---|
| 未认证直接改 id 就拿到 | 23 |
| 双账号（注册/登录/会话）后才验 | 17 |

判定：无认证场景占多数，双账号流程不是错，但作为**第一步**会多花注册/登录/会话切换的轮次。

### 3.3 上传卡 —— 只覆盖经典四维校验

卡现状：`先定校验维度（扩展名/MIME/魔术字节/内容），一次只改一个`

| 实际子型（上传/插件类 13 次内） | 次数 |
|---|---|
| 插件/配置驱动：`file` 类型目标指向任意路径后再触发 | 6 |
| 经典上传校验绕过 | 5 |

判定：一半以上的实际路径是"平台允许注册插件/配置对象，其目标路径本身就是任意读"，
与扩展名/MIME 校验无关。**但这条改动受 tag 门控**：如果这些题的平台标签不含
`file_upload/jsp_upload/webshell`，并进上传卡也不会触发（§5 的核对项）。

### 3.4 候选但未量：业务逻辑卡错配（不在本轮改）

`business_logic` 现在挂在"缓存/并发"卡里，卡文是`先确认单次是否幂等；并发 N 份看有无超额成功`。
实测的业务逻辑解出是"未公开 SKU / 审批闸门"这类，与并发相似度低。样本 9 次，**子型未量**，
列为下一轮候选，本轮不动。

## 4 拟改内容（一卡一 commit，全部可回滚）

| # | 卡 | 改法 | 命名测试句 |
|---|---|---|---|
| 1 | 信息泄漏 | 首步改为"先看已交付的构建产物与运行时报错面（bundle/sourcemap、页面与响应体、调试·诊断端点），经典文件探针退居其后" | 信息泄漏先从已交付的构建产物和报错面找，经典文件探针退后 |
| 2 | IDOR | 首步改为"单请求改 id 先证越权，再上双账号互换确认" | 越权先单请求改号证明，再上双账号确认 |
| 3 | 上传（**待标签核对**） | 追加"插件/配置对象把目标指向任意路径本身就是任意读" | 上传面先看平台能否注册插件或配置对象，目标路径即读点 |

三条都满足：不含题号/IP/具体路径/flag；不新增卡（不碰 `MAX_CARDS`/`MAX_CHARS`）；
不涉及工具改动与预算。

**验收**：① 命名测试通过；② `pytest tests -q` 维持 1846 passed / 7 skipped；
③ 合成靶上首条注入消息里该卡文本按预期出现（注入断言，不是效果断言）；
④ 效果断言等 §5 的消融。

**回滚**：一卡一 commit，`git revert <sha>` 单独可撤；文本改动无状态、无迁移成本。

## 5 消融与门控（平台 503 分支必须写死）

1. **回归语料**：`experiments/card_ab_corpus.json` —— 74 道已解题各取最便宜的成功 run，
   字段为题号 / run_id / 墙钟 / 调用次数 / 工具链 / `cards_injected:false`。
   墙钟 p50 79s、p90 333s。用途：卡改动前后跑同一批题，**只量轮次与墙钟**。
   **不把"这批题还是全绿"当能力结论**（防过拟合红线第 3 条）。
2. **能力侧**：在 3–5 道当前失败题上做"撤卡 vs 带卡"消融（优先 `docs/43` 的 14 道真能力缺口）。
   判据沿用旧例：目标 ≥3 道、回归 ≥5 道；无差异即撤卡。
3. **平台分支**：`start_instance` 自 2026-11-15 起全线 503。若 11-18/11-19 探测仍不通，
   消融无法执行 → **本批卡改动整批回滚**，只保留 `docs/44`、本文与语料；
   比赛用现状镜像。不允许用"没条件验证"当理由硬上。
4. **冻结线**：11-19 晚冻结（11-20 入围赛、11-21 正式赛）。冻结后只允许回滚，不允许新改动。

## 6 不做清单（本轮明确排除）

- 不从解法新增卡（覆盖率饱和）。

- 不改 `method_cards.py` 的选择逻辑、`MAX_CARDS`、`MAX_CHARS`、tag 路由规则。
- 不碰 `experiments/pools.json`（SHA256 `55da418b…678` 未变）。
