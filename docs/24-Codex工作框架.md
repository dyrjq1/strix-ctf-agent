## 1. 任务定义（这六条要能背下来）

### 1.1 目标函数（唯一）

```
score = 各题动态分之和（0/1 解 = 1000 分，随解题队数下降）
tiebreak = 先比出题分，再比解题总时长
```

**不是**解出题数、**不是**解出率、**不是** token 效率。

**证据要引用对**（v5 修正）：练习赛的 `my_solves=44` / `my_score=45` **不能**用来证明动态积分。
实测 `scoreboard` 全是 `score == flags_solved`（1 名 120/120、2 名 53/53、13 名 45/45）——练习赛是
`legacy` 计分，**一 flag 一分**。45 是答对的 flag 数，44 是 `fully_solved` 的题数，差 1 源自两套口径
（`CTFARENA-001` 的 question 有解、题未满分）。**动态积分只来自 QA#29**，那是正式赛规则，
本地拿不到样本。

两个量必须分开，别混着当目标：

| 量 | 含义 | 什么时候用它 |
|---|---|---|
| `fully_solved` 数 | 解出几题 | 练习/训练期的代理指标（便宜、稳定） |
| 动态分 | 这题此刻值多少分 | **正式赛真正优化的东西**：热门题早解值钱，冷门题晚解也值钱 |

三条硬约束把「时间」变成唯一稀缺资源：

| 约束 | 实测值 | 后果 |
|---|---|---|
| `max_instances_per_team_effective` | **1**（练习赛与正式赛同值） | **1 实例串行**（v5.1 拍板）。QA#26 的「≤3」是许可上限，不是可用的并发度 |
| `solve_env_mode` | `destroy` | 实例结束即销毁，跑超时 = 时间 + 预算双损 |
| 赛程 | 11-14 入围 / 11-15 初选 / 11-21 出题 / 11-22 解题，各 10h（02:00–12:00Z） | 解题场共 **30h**，出题场另算 |

所以优化对象是「**每小时拿到多少分**」。推论：先打**解得人多、分值还高**的题；一题卡到边际收益低于换题成本就该换——这正是 C1 那个自驱循环要做的决策。

### 1.2 战场：两类题，没有选择题

正赛题目只有两种形态，**没有选择题**。这条改变了整个优化方向（v2 把 52% 题库当选择题是错的）。

| | **轨 A · 远程靶机题** | **轨 B · 附件题** |
|---|---|---|
| 平台给什么 | 一个可访问的目标 | 一组文件 |
| task.json 的 `scope` | 有值（URL / `host:port` / CIDR） | `null` |
| task.json 的 `attachments` | 可能有（线索文件） | **一定有** |
| 要不要起实例 | 要（`instance`）/ 平台已起（`engagement`） | **不要** |
| 占不占那唯一的配额 | **占** | **不占** |
| 单题典型耗时 | 300–900s | 60–300s |
| 主要 category | `web` | `pwn` / `reverse` / `crypto` / `misc` |

> **战略推论（已按 QA 修正）**：两条轨的权重随赛段变。
> - **11-14/15（入围+初选）**：QA#26 六类全含，轨 B（rev/pwn/crypto/misc）必须能打；轨 B 不占实例配额，但**仍按单实例串行排**——它省的是配额，不是调度复杂度。
> - **11-22（正式赛解题）**：QA#31 明确只考 **Web / Pwn / AI Security**。即 rev/crypto/misc 只在初赛计分；决赛的「非 web」实际只剩 pwn 与 AI 安全。
>
> 所以「先 B 后 A」只在初赛成立；决赛应「Web 与 Pwn 并行，AI 安全按 web 打」。

### 1.3 六条硬约束

| # | 约束 | 数值 | 你不能违反的方式 |
|---|---|---|---|
| 1 | 实例配额 | `max_instances_per_team_effective=1`，**练习赛与正式赛同值**。QA#26 的「≤3」是上限许可 | **只跑 1 个实例，串行轮转**：拿完一题证据 → 销毁 → 起下一题。并发须同时满足「正式赛阶段 + 平台实测放行 + 不超配额」，缺一即否 |
| 2 | 实例销毁 | `destroy` | 不假设「下次还能连上同一个靶场」；重启后要重建 |
| 3 | 单实例 TTL | `launch_ttl_s=10800` | 单题占用不超 3h；到点前收工或换题 |
| 4 | 外网 | `agent_internet=deny` | 不设计「上网搜资料」的路径（VPS 可达 LLM 与赛事平台，仅此） |
| 5 | 模型 | 初赛：国内主流大模型任选；决赛：智谱，1B token 上限（QA#4/#35） | 初赛不做双模型赛马（收益未证）；决赛不依赖自备 key |
| 6 | 派发粒度 | **Agent 自主读题并决定做哪题**（QA#24） | **必须**有跨题调度：单题循环的入口在正式赛跑不起来 |
| 7 | 无外网 | `agent_internet=deny`（正式赛对象同值） | 不能靠「现场查 writeup / 拉字典」；训练期的离线资料要打进镜像 |

### 1.4 不做什么

- **不做**选择题适配。正赛没有。代码里的 `qa` 分支保持现状，不投入。
- **不重写** strix。`vendor/` 43943 行是资产，一行不改；改造只在 `src/ctf_strix/`。
- ~~**不做**跨题调度器~~ → **改为必做**（v4 C1）。QA#24 要求 Agent 自己读题、自己决定重跑还是换题；缺这一层，交付物形态就是错的。
- **不做**「通用最强 agent」。目标是这个平台这两类题，不是通用能力。
- **不做**未过 A/B 的性能改动（赛前 24 小时内，见 §8.1）。
- **不做**「多解一题就算赢」的自我安慰。验收同时看平台分与 `fully_solved` 两个口径。

### 1.5 你控制不了什么

| 控制不了 | 依据 | 你怎么应对 |
|---|---|---|
| 题目数量与顺序 | `challenges_withheld: true`、`challenge_count: null` | 运行期拉列表动态排序，不做赛前规划 |
| 单个靶场能活多久 | `launch_ttl_s=10800` | 单题按 2700s 软截止，到点换题 |
| 并发 | QA#26 许可 ≤3，但平台字段是 1，v3 又不许客户端起实例 | **不赌并发**：单实例串行轮转，把精力放在「单题更快出证据」上 |
| 有没有人给提示 | 正赛无人环 | 线索只能从题面/附件里挖 |
| 平台给多少轮 | `max_turns` 可能为 `null` | 按「没给=不设帽」处理，见 §8.3 |
| 重启次数 | 只有 3 次（QA#24） | 状态必须落盘，重启后断点续跑，别依赖内存 |

## 2. 每日循环（手册的核心）

**每天只做四件事：开工确认 → 接单 → 干活 → 收工记账。** 不允许「今天想到什么做什么」。

### 2.1 开工（15 分钟，逐条打勾）

```bash
# ① 配额是否干净（不干净先清，否则今天的评测全废）
curl -s -H "Authorization: Bearer $CTFY_TOKEN" \
  https://ctfy.tsinghua.edu.cn/api/v1/instances | python3 -m json.tool | head -20

# ② 昨天的台账最后三行（知道自己停在哪）
tail -3 docs/11-实验台账.md

# ③ 昨天有没有跑挂的评测（僵尸进程会抢配额）
ps -ef | grep -E "eval_sample|agent\.py" | grep -v grep

# ④ 镜像与代码是否同步（改了代码没重建镜像 = 白测）
git status --porcelain src/ docker/ | head
docker images --digests | grep strix-ctf-agent

# ⑤ 今天的锚题基线是否还在（锚题尚无固定文件，先用最近一次全量结果）
ls -lt reports/results.*.jsonl 2>/dev/null | head -3
```

**三个必须确认的结论**，缺一个不许开工：

- [ ] `instances` 总数为 **0**，或全是自己今天要用的
- [ ] 没有遗留进程在跑（有就先 kill，别叠加）
- [ ] 台账里最后一条改动的状态不是 `implemented`（说明昨天没收尾，先收尾）

### 2.2 接单：一个改动怎么进入队列

改动**只能**从这四个来源进入，其他一律拒绝：

| 来源 | 入口 | 进入条件 |
|---|---|---|
| 缺陷 | `docs/09-全量测试与改进总账.md` §9 / 新发现的失败 | 有日志或平台数据证明它真的发生 |
| 缺口 | 覆盖矩阵的空格（本文 §9.1/§9.2） | 有题、没测过 |
| 假设 | §3 两轨的失败模式 / §4 步骤卡的「现状」 | 能写成可证伪实验 |
| 阻塞 | 平台/镜像/凭据 | 有明确的错误码 |

> **口头想法不进队列。** 想加功能先写成 `proposed` 行，附一条证据。没有证据的想法一律排到赛后。

### 2.3 干活：任何改动的七态生命周期

不许跳态。跳态 = 这条改动不算交付。

```
proposed → adr → implemented → container-verified → ab-tested → ledgered → merged/reverted
                                                              ↑
                                        （进 ab-tested 之前，先过「证据链」自检）
```

| 态 | 你做完的标志 | 卡住时的处置 |
|---|---|---|
| `proposed` | 台账有行，附证据（日志片段/API 返回/题号） | 没证据 → 打回想法池 |
| `adr` | ADR 落盘（模板 §7.2），S 级可省 | 影响面说不清 → 降级成 S |
| `implemented` | 单测绿 | 单测写不出来 → 说明接口没设计好，回 `adr` |
| `container-verified` | **容器内**（`backend=local`）跑出 `result.json` | 跑不出 → 不许进下一态，这是最常见的卡点 |
| `ab-tested` | 差值 + 样本量写清（≥5 题）；**且每一条「解出」都有工具输出佐证** | 题不够 → 挂起，不硬凑；证据链没修 → 先修，别测 |
| `ledgered` | 台账行含**回滚命令** | 回滚命令没跑过 → 不算 |
| `merged` / `reverted` | 锚题全绿 | 有回归 → `reverted`，同样进台账 |

**「不成立」是合法结论。** 证伪一条假设和证实一条一样要写进台账，否则下一个人会重试一遍。

## 3. 两轨作战

### 3.1 分流是唯一入口，判错就全错

题型判定顺序**必须**是这个（来自平台事实，不是偏好）：

```
1. run_mode == "engagement"                    → engagement（轨 A，交报告）
2. questions 的 mode 全为 "checker"            → checker（轨 A/B 皆可）
3. scope 全为 host:port 形式                    → tcp（轨 A）
4. 无目标 且 task.json 有 attachments           → file（轨 B）
5. 无目标 且工作目录存在 attachments/ 或 files/  → file（轨 B）
6. 无目标 且 scope 全为 CIDR                    → web（轨 A，网段自摸）
7. 其余                                         → web（轨 A）
```

**判定错误的两种后果，都很贵：**

| 误判 | 后果 |
|---|---|
| 轨 B 判成轨 A | agent 去扫一个不存在的主机，实测会写出「port 80 was unavailable」这种报告，**整题 0 分且烧完全部预算** |
| 轨 A 判成轨 B | agent 读完附件后不知道要打哪里，**空转到底** |

> **当前状态（v4 核实）：七级判定全部已实现**，位置 `src/ctf_strix/agent.py:256-292`。
> 顺序与上表一致；第 5 条（工作目录存在 `attachments/` 或 `files/`）覆盖了「平台只丢文件不写 task.json」这种情形。
>
> **但有一个真缺口**：判定只决定 prompt 与工具面，**附件注入是无关条件、全题型都做的**（`agent.py:556`）。这是对的（混合题需要），别把它和分流混成一件事。

### 3.2 轨 A · 远程靶机题

**你要打的三种子形态：**

| 子形态 | 平台给的 | 你要做的 | 交付物 |
|---|---|---|---|
| `instance` | `scope` 里是起好的 URL | 拿 `LLM_API_KEY` 之外什么都不用申请，直接打 | `result.json` 的 `answers` |
| `engagement` | `target_instance` 非空，`scope` 是主机名 + CIDR | **不许**自己 POST /instances；摸清整个靶场；写报告 | `report` 端点（不是 result.json） |
| `tcp` | `scope` 是 `host:port` | 裸 TCP，没有 HTTP | `answers` |

**轨 A 的四个特有失败模式**（每条都真实发生过）：

| 失败模式 | 症状 | 判据 |
|---|---|---|
| 目标没起 | 连接被拒 / DNS 有记录但无后端 | 开工前 `GET /instances` 必须非空 |
| 预算全烧在枚举 | 90 次调用里 38 次刷同一个端点 | 连续 K 次无「证据增量」→ 早退 |
| 拿到 shell 却不找 flag | 反复写报告、写 notes | 目标函数是 flag，不是报告 |
| engagement 报告投递失败 | 网关偶发 404 | 必须重试；401/403 不重试 |
| **读到本机残留文件当答案** | `cat /tmp/flag.json` 恰好有 flag，直接交（018 实测） | flag 必须来自**本次**工具输出且带靶机上下文 |
| **模型凭空编 flag** | 无任何工具输出支撑，直接写 `FLAG{...}`（078 重试臂实测） | 同上：没有工具输出证据就不采信 |
| **站点根本没有解题入口** | 018：注册成功，但只有两个只读 JSON 接口，claim 路由 404 | 连续两次「注册/登录后无新端点」→ 换攻击面（题目页 POST / 本身） |

**轨 A 的验收**：`my_fully_solved == true`（平台回读），不是「日志里看到 flag」。

### 3.3 轨 B · 附件题

**平台怎么给文件**：`challenge.attachments` 是 `[{name, size, per_team}]`，**没有下载 URL**——文件直接落在 `$CTFY_WORK_DIR`（或 `attachments/` / `files/` 子目录）。`⚠️待验证`：具体落在哪个路径需要实跑一道题确认，三种都要兼容。

**必须解决的三个技术点**（不解决 = 附件题必然 0 分）：

| 点 | 为什么 | 做法 |
|---|---|---|
| **注入** | strix 的 sandbox 是私有临时目录，不进 `extra_files` 的话 agent **看不见文件** | 扫工作目录 → 读成 `extra_files` |
| **二进制** | 注入通道是文本 | 二进制转 base64，后缀改 `.b64` 让 agent 知道要解码 |
| **配额** | 注入有 50 文件上限，超了静默丢 | 排除 `task.json` / `result.json` / 点文件 / 源码树 |

**轨 B 的五个特有失败模式：**

| 失败模式 | 症状 | 处置 |
|---|---|---|
| 附件没注入 | agent 说「工作目录里没有文件」 | 立刻查 `extra_files` 条数是否为 0 |
| 把平台文件当题 | agent 去分析 `result.json` | reserved 名单必须排掉（已实现：`agent.py:468`） |
| 本地调试把源码树打进 sandbox | 一次占满 50 配额，agent 还读到评测脚本常量，把套题 id 当 flag 交上去 | 排除 `src/ vendor/ tests/ docs/` 等目录 |
| 大二进制读不动 | 100 MB 附件被 base64 后撑爆上下文 | 只注入清单 + 前 N KB，其余让 agent 用工具自己读 |
| 同名附件互相覆盖 | 子目录里两个 `README.txt` | 保留相对路径作 `workspace_path` |
| **只有入口没有下一步** | `file_triage` 报「这是 ELF」，然后 agent 开始自由发挥 | 需要 `checksec`/`strings`/反编译/调试的**结构化结论**，不是原始日志（v4 P1，见 §9.3 第 12 条） |

**工具面现状（v5 实测）**：`kind=="file"` 时只注册 **1 个**工具（`file_triage.py` 的 `TOOLS = (file_triage,)`，没有 `hexpeek`）。它能回答「这是什么文件、下一步跑什么」，但**rev 的动态调试、pwn 的 exp 脚手架、crypto 的编码链一个都没有**。

> 这与实测能力不矛盾：002/010/011(rev)、004(crypto)、014(misc) 已经解出——**说明模型靠通用推理能吃掉 easy 档**。缺的是 medium/hard 那一步「有工具就能省 10 轮」的结构化原语。

**轨 B 的验收**：同轨 A——平台回读 `my_fully_solved`。附加一条：**注入清单要写进 `result.json` 的诊断字段**，否则事后无法区分「没找到」和「找到了但没解出」。

### 3.4 混合题（既有目标又有附件）

真实存在：`SAMPLE-001` 是 web 题，但 `admin slug` 写在 `setup.txt` 里。

**规则：附件注入对所有题型无条件执行，不只在轨 B。** 漏注入 = 丢掉一半线索。

判定仍然按 §3.1 走（有目标 → 轨 A），但注入照做。这两件事是正交的，不要合并成一个条件。

## 4. 八步执行卡

**这是本手册的主干。** 八步是一个闭环，不是瀑布：每步有闸门，不过闸门不进下一步；但第 6 步测出「不成立」会退回到第 4 步重出方案，这是正常回路。

> **八步和 §2.3 的七态是什么关系？** 八步是**整个工作循环**（一周可能走一轮）；七态是**单个改动的生命周期**（一天可能走几轮）。走 Step 5~7 时，每一条具体改动都要按七态推进——八步管「往哪走」，七态管「这条改动到哪了」。两个都要用，不冲突。

```
1 定方向  →  2 找对标  →  3 读源码  →  4 出方案+合规
                                          │
   8 分发  ←  7 台账  ←  6 测试A/B  ←  5 改代码
   （可选，可并行）
```

**八步 × 我们现状（一眼看出卡在哪）**

| 步 | 一句话 | 现状（v4） | 卡点 |
|---|---|---|---|
| 1 | 定方向与量化缺口 | ✅ 全库 catalog + 逐套题解出率（CTFARENA 44/115、SAMPLE 11/15、XBOW 0/104、SQLILABS 0/69） | 主指标 v5 改为「web 存量 + pwn」双轨，不再用「非 web = 0」 |
| 2 | 找对标（仓库/许可证/名次） | ⚠️ 2 行（Veria MIT 900★ / STRIATUM），报告 `docs/16`；**未达 ≥5 行门槛** | 缺 pwn/rev 专项 agent 与 CyberGym 类基准的对标 |
| 3 | 源码差异表（六维） | ✅ 六维表已出（含代码行号级对比） | 对标样本仍是 2 个，偏少 |
| 4 | 出方案+过合规 | ✅ 合规表逐条签过（外网/实例/模型/人工） | — |
| 5 | 改代码/复用 MIT | ✅ 附件注入、`file` 分流、入口能力对齐、答案采集补漏 | **缺三个 P0**：证据链、沙箱隔离、跨题自驱 |
| 6 | 单测 + 同题同预算 A/B | ✅ 单测 **189** 绿（本地可写临时目录，连跑 8 轮）；A/B 4 轮，2 负 | 样本偏小（多为 2–3 题），**不足以下结论的格子要明写** |
| 7 | 报告与台账（含回滚） | ⚠️ 台账在写；回滚命令多数只是 `git revert` | 回滚命令未逐条真跑 |
| 8 | 可选分发 | ⏸ 未开始 | — |

> **v4 的重点不是「补 A/B」，而是「A/B 的测量本身不可信」**：078 编造 flag、018 读本机残留，两次都差点被记成解出。第 6 步的闸门必须先过「证据链」，否则 A/B 测的是噪声。

### Step 1 · 定方向与量化缺口（如「web 存量解出率」或「pwn」）

| 字段 | 内容 |
|---|---|
| **目标** | 把「要变好」变成「**哪个数字要变好、现在是多少、差多少**」 |
| **前置** | 先有尺子：同一配置跑两次，`fully_solved` 集合必须完全相同。尺子不准，后面每步都在放大误差 |
| **输入** | `GET /api/v1/challenges` 全库、`reports/results.*.jsonl`、`GET /api/v1/competitions` 的赛制字段 |
| **动作** | ① 拉全库 catalog 按 `category×difficulty` 建格 ② **选一个主指标**，写清分子分母 ③ 算出当前值 ④ 每个零覆盖格子写「派单」或「放弃+理由」 |
| **产出物** | `platform-snapshot-<date>.json`（已落 2026-10-31 快照）+ 覆盖矩阵写进本文 §9.1/§9.2 |
| **闸门** | 主指标有明确的分子/分母，能当场算出数；每个空格都有处置 |
| **现状（v5 实测）** | 主指标改为两个：**① web 存量** 64/366 = 17.5%（其中 XBOW 0/104、SQLILABS 0/69、CYBENCH 1/40）；**② 非 web** 5/8（rev 3/3、crypto 1/1、misc 1/2、**pwn 0/2**） |
| **坑** | ① 混用 `kind` 与 `category` 归格（我们算错过一次）② 把选择题当战场（正赛不考，411 题是空气） |

**为什么改成两个指标（v5）**：v4 押「非 web = 0」是因为它以为附件题一道没做，实测非 web 已经 5/8、带附件题整体 6/10。
现在最弱的两处是：**XBOW 104 + SQLILABS 69 完全没测**（web 存量），和 **pwn 只有 2 道题、且都是坏题**。
前者决定「web 能不能规模化」，后者决定「11-22 决赛唯一的两类之一有没有练过」。**指标要指向这两个。**

两个口径要分清，不能混着说：

| 口径 | 算法 | 我们的值 | 用途 |
|---|---|---|---|
| **样本解出率** | 解出数 / 已测数 | 附件题 6/10 = 60% | 判断「这类题我们会不会」 |
| **覆盖解出率** | 解出数 / 该类全部题量 | web 64/366 = 17.5%；XBOW 0/104 | 判断「这类题我们练了多少」 |

> 说「附件题 60%」要立刻补一句「n=10，且其中 3 道是坏题」——小样本 + 坏题，两个折扣都要打。
> 说「web 覆盖 17.5%」才是真实处境：**不是不会做，是没测过**。

## 5. 判据（什么叫做完）

### 5.1 一条改动的 DoD

六条**全部**满足才算完成：

- [ ] 台账有行，状态与代码一致
- [ ] 单测绿（新增行为有对应用例）
- [ ] **容器内**跑出 `result.json`（不是本地脚本跑通）
- [ ] A/B 有差值 + 样本量（S 级可用锚题代替）
- [ ] 回滚命令被真跑过一次
- [ ] 锚题无回归

### 5.2 不算完成的六种情况

| 说法 | 为什么不算 |
|---|---|
| 「dry run 过了」 | dry run 不跑 agent |
| 「单测过了」 | 单测不碰容器、不碰平台 |
| 「本地评测跑通了」 | 评测脚本设的变量，容器里可能没有 |
| 「日志里看到 flag 了」 | 只认平台回读的 `my_fully_solved` |
| 「代码写完了」 | 没进 `container-verified` 态 |
| 「只差重建镜像」 | 重建镜像是一步，不是「只差」 |
| **「agent 说它拿到 flag 了」** | 实测两次假阳性：078 凭空编、018 读本机残留。**必须有工具输出佐证** |
| **「本地 jsonl 里 correct=true」** | 那是提交返回值；`my_fully_solved` 才算解出（多问题题尤其） |

### 5.3 A/B 统计口径

| 项 | 要求 |
|---|---|
| 题量 | ≥5 题/格，最好 10 题。**样本不够就明写「不足以下结论」，不要凑** |
| 预算 | 两臂**完全相同**的 turns / 墙钟 / 模型 |
| 指标 | 主：`fully_solved` 数（平台回读）；副：token、耗时、`stop_reason` 分布 |
| 结论格式 | 「轨 A web/medium 格子，n=8，A 臂 5/8，B 臂 3/8，差 +2」 |
| 反例必须写 | 哪几题**变差了**，为什么 |
| **随机化** | 两臂顺序要打散（`random.shuffle`），否则时间漂移只作用在一臂上 |
| **证据链前置** | 每条「解出」都要有工具输出佐证。078 编造、018 读残留各踩一次 |
| **重复次数** | 同题至少 2 次（单次结果的方差远大于效应量） |

**实测教训（P16）**：3 题 × 1 次的 A/B 得出了「重试无效」的结论，但同一天复测 018 时
发现两臂都在读 `/tmp/flag.json`——**测的是噪声**。样本量不够 + 测量不可信，两个问题叠加时，
任何差值都不能信。

### 5.4 改动分级

| 级别 | 判据 | 必需流程 |
|---|---|---|
| **S** | ≤1 文件、不改变行为 | 单测 + 锚题 |
| **M** | 改变单题行为，影响 ≤1 个格子 | ADR 简版 + A/B ≥5 题 |
| **L** | 架构级，影响多格子或全局预算 | 完整 ADR + A/B ≥10 题 + 分批上线 |

判级不确定时按高一级走。**S 级不许夹带行为变化**——这是最常见的技术债来源。

## 11. 两起「假 flag」事故复盘（必读）

这两件事都不是模型能力问题，是**采集逻辑**问题。它们会直接污染所有 A/B 结论，所以放在正文。

### 11.1 078 重试臂：模型凭空编 flag

**现场**：`CTFARENA-078` 第二次 attempt（resume 同 session）第 1 轮就输出
`**Answer:** FLAG{3cada89232660b4a401ed3eef9c69360}`，而该题真实 flag 是
`FLAG{0fac8c26ce0348936898b2aab6a2220e}`。

**为什么没被当成答案**：这串 flag 在 strix 日志与 `agents.db` 里**零工具输出支撑**，
`flag_extract` 的「必须在靶机 host 800 字符内」判据把它挡掉了。

**但风险真实存在**：如果那次是 `finish_scan` 的参数而非普通 message，
`agent.py:982` 的 tool-args 采集会**直接采信**——因为那条路径**没有 host 证据校验**。
> （v5 补：这条已经修了。962→982 现在只 `arg_claims.append()`，必须等 `ledger.supports()` 为真才进 `answers`，见 §9.3 第 9 条。）

**修法**：tool-args 采集必须和 tool-output 采集用**同一套证据判据**，不能因为
「它在 finish_scan 里」就放行。

### 11.2 018 重试臂：读到上一题的本机残留

**现场**：agent 执行 `cat /tmp/flag.json`，拿到
`{"id":1,"title":"Vault Master Key","content":"FLAG{9b6c87b8...}"}`，
判定「这是本机残留、可能是别题」后仍然写进了 `finish_scan`。

**根因**：`local_backend.py:138` 只把 **workspace** 隔离成
`/tmp/sandbox-<pid>-<seq>`，而 agent 可以直接读宿主机的 `/tmp`。
上一题（`/tmp/flag.json`、`/tmp/tr/*.py`）全部可见。

**为什么危险**：这不是「解出来了」，是**把上一题的成绩搬到这一题**。
平台回读 `my_fully_solved=false` 才没记错，但如果碰上同一个 flag 的重复题，
会**静默虚增**。

**修法（两条都要）**：

1. 每个 run 起一个 pid+mtime 命名空间，或在容器内跑（正式赛本来就是 VPS，天然隔离）——**仍未做，P0**；
2. 答案证据链：flag 必须出现在**本次 run** 的工具输出里——**已做**（`evidence.py`）。

> v5 更正：v4 写的第 2 条「且同时出现本题靶机标识」**没有实现、也不该实现**。
> 理由：009 的形态是「写探针脚本到 `/tmp`、脚本自己打印 flag」，输出里根本没有靶机 host 串；
> 加这条判据会把真解误杀（053/054 回归就是这么验的）。**证据链只回答「这个串是不是本次读到的」，
> 不回答「它从哪来」——后者只能靠沙箱隔离解决。**

### 11.3 018 最后一次复测（同一天，20 轮，两臂各 2 次）

| 臂 | 次数 | 解出 | 备注 |
|---|---|---|---|
| attempts=1 | 2 | 0 | 都没解出，token ≈1.01M/次 |
| attempts=2 | 2 | 0 | 其中一次**交了假 flag**（读 `/tmp/flag.json`），平台判 false |

结论：**018 用 20 轮在两种配置下都解不出**，且重试臂把「本机残留」当答案的概率更高（因为 digest 里带了上一轮的路径清单，模型更容易去 `cat /tmp/*`）。

### 11.4 结论

> **在修好证据链之前，任何「解出率」数字都只能当上限看，不能当基线。**

这也是 §10 把「答案证据链」排在第一位的原因。而且它不只是「测不准」——**它会让 agent 主动去找假答案**：一旦它知道「本机某个文件里有 FLAG{...}」，它会优先复用而不是重新打靶。
