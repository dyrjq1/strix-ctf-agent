## 3 我判定 CC 夸大的两处（降级，但不丢弃）

### 3.1 A1「多问题题一分不得」→ 拆成两半，一半真一半假

**假的一半（gated）**：协议 `docs/08:482-488` 明说后续问题的 **prompt 在解锁前根本不存在**，
agent 拿不到题面，不存在「把新答案写到旧 key 上」这种失败形态。

**真的一半（多问同时可见）**：台账 4.9 有实证 —— CTFARENA-001 的 `questions` 只有 `flag`，
但平台 `flag_solves` 里还有 `xhr_token`，我们交了 flag 仍 `my_fully_solved=false`；
048/049/050 也是多问题题。`agent.py:298-315` 只取 `questions[0]`，四个写点
（`1189/1200/1336/1350`）都只写一个 key → **同时可见的多问题题，官方入口只能拿一问的分**。

**真正的窄缺口**：协议 `docs/08:811-815` 说「边跑边交」才能拿到即时判定、才能在
gated 题解锁后继续；而 `agent.py` 是跑完才把 `answers` 交出去 → 一轮内永远看不到反馈。
协议 `docs/08:974-975` 又说「You need not do anything to support rounds」，所以这不是
架构缺口，是**提交时机**的缺口。

### 3.2 A2「轮次重启后无状态衔接」→ 降级为接线修复

协议 `docs/08:959-964`：下一轮的 `README.md` 会写「第几轮、现在可见哪些题、上一轮每题
correct/wrong/not answered/newly unlocked」，且 `/ctfy/work` 跨轮保留（`result.json` 除外）。
所以状态**本来就在磁盘上**，agent 读得到。缺的只是 `agent.py` 的 instruction 没让它去读。

→ 归入 P1 接线类：一轮读完 README、把「上轮 verdict」写进 instruction 即可，无需新架构。
