## 1. 方向（第 1 步）

上轮交接的目标是"降低 043 的 token 消耗"。本轮把它拆成一个可证伪的问题：

> **在 DeepSeek 的 prefix cache 计费模型下，"压缩历史"到底省不省钱？**

因为 043 的 input token 是"平方增长"的表象（40 轮 1.7–2.2M），很容易得出
"必须压缩"的结论。但如果压缩破坏了前缀缓存，省下的 token 会以 50 倍单价补回去。

## 3. 对比分析（第 3 步）

### 3.1 三次真实跑批（同一道 043，同模型，同 40 轮）

| 配置 | 请求 | 工具调用 | raw input | cache hit | 命中率 | 等效成本(miss=1) | 墙钟 | 结果 |
|---|---:|---:|---:|---:|---:|---:|---:|---|
| A 等效不压缩（短提示，裁剪未触发） | 40 | 42 | 1,735,886 | 1,660,416 | **95.7%** | **108,678** | 342s | FAILED |
| B 按龄裁剪 v3 | 40 | 43 | 1,580,500 | 914,048 | **57.8%** | **684,733** | 595s | FAILED |
| C 内容封顶（本轮） | 40 | 55 | 1,838,512 | 1,717,888 | **93.4%** | 154,982 | 504s | FAILED |

等效成本 = `hit × 0.02 + miss`（0.006/0.3 = 0.02，即一次命中约等于 1/50 次未命中）。

**口径提醒（重要）**：三次都是「40 轮触顶」，但工具调用数 42 / 43 / 55 不同，
所以 raw input 不能直接横比——C 做了更多事，自然发得更多。按每次工具调用摊：
A `41,331`、B `36,756`、C `33,427`。**C 在单位工作量上最省**；A 的总账最低是因为
它做的事最少。真正可比的是**命中率**：A 95.7% / B 57.8% / C 93.4%。

### 3.3 为什么按龄裁剪必然打崩缓存

按龄规则 = "最近 N 条原文，更早的压掉"。同一条历史会在第 10 轮是原文、
第 11 轮被截断、第 21 轮被折成一行存根。**每跨一个档位，前缀整体改变一次。**

而 DeepSeek 的缓存单元是"请求边界处的前缀 + 固定间隔切分"。前缀一变，
之前所有缓存单元全部失配。于是每轮都是近乎全量 miss。

**这不是参数没调好，是规则本身的形状错了。**

### 3.4 一个反直觉的发现：根本不需要压缩

DeepSeek-V4.1-Flash 上下文 **1M**，而 40 轮实测单轮峰值 **74,263** token。
**没有任何溢出风险**。所以"接近上限才压缩"这类触发条件永远为假——
这也解释了为什么 strix 自带的 `maybe_compact`（阈值 180k）从来没生效过。

## 4. 方案 + 合规核对（第 4 步）

### 4.1 采用：幂等内容封顶（`HistoryCapper`）

对**每一条**工具输出单独判断，超过 `CTF_CTX_CAP_CHARS`（默认 8000）就保留
头 4800 + 尾 2400 + 其中出现过的 flag 原文。工具**调用参数**另设 4000 封顶。

三条不变量（能用它的全部理由）：

1. **幂等**：`f(f(x)) == f(x)`，同一段内容反复处理结果不变；
2. **位置无关**：第 5 条和第 50 条规则完全相同，不看"还有几条比它新"；
3. **只依赖内容**：不依赖轮次、历史长度、预算余量。

于是第 N+1 轮请求 = 第 N 轮请求 + 新增条目，**前缀严格不变**，缓存照常命中。

为什么 8000 这个阈值：043 的 42 条输出里只有 2 条超过（16,188 / 14,213），
其余 40 条原样通过。阈值精准打击那两个大块头，不误伤正常 curl 输出。

### 4.2 合规核对

| 检查项 | 结论 |
|---|---|
| `agent_internet=deny` | ✅ 纯本地字符串处理，不联网 |
| 单实例 / 单模型 | ✅ 不变 |
| 人工提示 | ✅ 无 |
| 修改 vendor | ✅ 无（只在 `StrixProvider.get_model` 外面包一层） |
| Token 总量 1B 上限 | ✅ 只减不增 |

### 4.3 被否掉的方案

| 方案 | 否决理由 |
|---|---|
| 继续调按龄参数（keep=6 等） | 规则形状错，参数怎么调都是每轮改前缀 |
| 降阈值到 48k 触发 | 单轮峰值 74k，但上下文 1M，触发即负优化（见 §3） |
| 用 strix 自带 `maybe_compact` | 阈值 180k 永不触发；且每 cycle 只跑一次 |
| 整段摘要式 compaction | 每次都要再发一次完整请求做摘要，净成本更高 |

## 7. 报告与结论（第 7 步）

### 7.1 本轮做对了什么

1. **否掉了一个负优化**。v3 若上线，等效成本会涨 6.3 倍、墙钟涨 74%，
   而解题率一点没变。
2. 把"缓存友好"变成可测试的不变量，以后再动上下文层有硬约束兜底。
3. 确认 **043 不存在上下文溢出问题**，后续不必再往这个方向投入。

### 7.2 本轮没能解决什么（必须诚实）

**C 配置的 043 仍然 FAILED。** 三次跑批，三种上下文策略，结果完全一致。
上下文管理对**解题率**的贡献是 0。

因此：**上下文这条线到此为止**。继续调参属于"用战术勤奋掩盖战略缺失"。

### 7.3 真正的瓶颈（下一轮的方向）
