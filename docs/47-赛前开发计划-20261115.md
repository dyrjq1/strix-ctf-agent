## 0 结论先行

> **2026-11-15 晚修订**：官方 Q&A 表与《TPCTF 2026 参赛接口文档 v1.0》到手，
> 推翻了本文初版对调度模型的假设（初版 F1/F2 把「平台每次 run 起一个实例」当成了比赛机制，
> 那是 `docs/08` 的宿主评测模型，**不是本赛道的比赛模型**）。以下 §0/§1 已按官方口径重写。

在没有顶尖模型的前提下，解出率的最大杠杆**不是让模型想得更聪明**，而是四件可测量的事：

1. **调度不空转**——赛制是「VPS 上常驻进程自己轮询拉题、自己排 ≥3 并发」（Q&A #49/#77/#81），
   槽位是我们自己管的，一道题占着槽就是在挤掉另一道题。这是**我们有完全控制权**的吞吐杠杆（§2）。
2. **把平台已经付费的专家分解接进来**——平台自带 hint 机制且计费是 discount 模式，
   我们一行未接（F6）。这是弱模型上唯一有 2× 实证的杠杆。
3. **把"已解过的题"做成离线检索，而不是塞进提示词**——台账已建但从未进 agent（P2）。
   **官方明确允许预置离线知识**（F10），这条从"待确认"变成"合规且优先"。
4. **部署契约不能错**——网关变量、WireGuard、重启后自恢复，任何一项错都是 0 分（§2.0，F11/F12）。

顺序：**P0 部署契约 → P0.5 早退闸门 → P1 hint 接线 → P2 解法检索 → P3 门控题追打 → P4 方法卡首步校准**。

## 2 P0 · 进度证据闸门 + 早退（最高优先）

### 2.1 机制（2026-11-15 修订：闸门早就有，死的是判据）

初版写的「新增连续 N 步无新观测的闸门」是错的——这个闸门**已经在 `progress_guard.py` 里**，
两段式（`_STALL_WINDOW` 次无增益 → 自适应深挖 `_DEEP_DIVE_ROUNDS` 轮 → `tripped` →
`agent.py:3625` 在轮边界抛 `NoProgress`）。它被正确接线、正确落盘、`stop_reason="no_progress"`。

**问题是它 180 次里一次都没响过（F7）。**

原因在判据：它把「连续 N 次探测没有**新观测**」当作停滞。而失败 run 的实测形态是
**一路上都在产出新观测，直到撞上限**——中位 35 次调用、p90 59 次，每次探测的响应签名都不一样。
它量的是**新颖度**，失败的本质是**不收敛**。新颖度永远为真，闸门永远不响，
于是 75% 的真失败一路烧到上限（F5）。

所以 P0 的改动是：**给这个闸门换判据——从"没有新观测"换成"假设空间没在收缩"**。

- 保留现有两段式结构与全部接线，只换 `gain` 的定义。
- 候选信号（都已在库里，不需要新状态）：`_mechanisms` 集合是否停止增长、
  已发现的端点键 × 已试参数是否进入平台期、`negative_guard` 的 stuck 组数、
  以及"这次新观测是否让任何一条待证假设被证实/否证"。
- 命中后仍是原路径：干净收尾、写 `result.json`、把未解问题数写清楚。
- 硬墙保持不变（**不降**），只做兜底。

### 2.2 物理依据（为什么这不是"调预算"）

- 真失败 59 条里 **44 条（75%）死于预算上限**（turn_capped 24 + wallclock 20），
  而 **0/100 成功碰过上限** → 撞上限是失败的征兆，不是原因。
- 活着到 40 次调用时 P(solve) 只剩 13.8%；600s 之后 0/14。
- 槽位是我们自己管的（F1/F2）：初选赛 3 个槽，一道题赖在上面的每一分钟，都是另外两道题
  少一分钟。省下来的直接变成吞吐，不需要任何平台行为假设。

**这条改的是判据，不是预算数值**：`budget_turns` / `budget_wall_s` 一个不动，红线成立。
上限只作为兜底继续存在；被缩短的是**判据命中之后**的那段，而不是所有人。

### 2.3 为什么不能用"时间判据"替代

按 cap 直接截断的账（159 条真实开跑的 run 实算）：

| cap | 每题均摊 | 相对无 cap | 丢掉的解出 | 净吞吐 |
|---|---|---|---|---|
| 900s | 247s | 0.97× | 0/100 | ≈0 |
| 600s | 233s | 1.09× | 0/100 | +9% |
| 420s | 212s | 1.20× | 5/100 | **+14%** |
| 300s | 176s | 1.45× | 11/100 | +29% |

420s 是低风险点、300s 是激进点。**这张表上的"再调度"由我们自己的 `compete.py` 完成**，
不需要平台配合（F1）——所以它不再是"未证实前提"，而是一个可自己验证的排程实验。
判据命中式早退仍优于固定 cap：题还在打就继续打，只有"打不动了"才撤——
因为 420s 那一行丢的 5 道解出题里，没有一道会命中"假设空间停止收缩"。

### 2.4 验收

| 项 | 线 |
|---|---|
| 单测 | 基线 1852 passed / 7 skipped 不减；新增「该响的时候响」+「不该响的时候不响」两侧用例 |
| 行为 | 离线重放历史 run（`agents.db` item 流，零 token）：闸门在**已解出**的 run 上触发率 < 10% |
| 消融 | 撤掉闸门跑同一批题；解出数不降、总时长下降才算有效 |

### 2.5 回滚

一个 config 开关置 OFF 即恢复原行为；台账记一行。不改默认预算值，所以回滚无连带影响。

### 2.6 P0.5 · 一次都没开跑的 21 条（最便宜的一类损失）

80 条失败里 **21 条（26%）一次工具调用都没发出**——它们不是解题失败，是根本没开始解。
拆开看（`zero_call.py`）：

| 类别 | 条数 | 判定 |
|---|---|---|
| `SKIPPED(需隧道)`：`services=[…internal]` 无直连地址 | 7 | **不是缺功能**。`batch_eval.py:1017` 会等 60s 的 vpn profile 再跳过，`_attach`（:2142/:2172）也会起 `VpnTunnel`。属平台侧/就绪竞态 → 只计数上报，赛前不改 |
| `TimeoutError: not ready in 180s` | 4 | 同类：平台慢。记录，不改（改它是调预算） |
| 平台 4xx/503/断管 | 5 | 环境。记录 |
| `KeyError: 前缀不在已知 suite 表` | 2 | **接线缺口，可合并修** |
| `400 … max_tokens should be [1, 8192]` | 1 | **确定性硬伤，见下** |

**`max_tokens` 那条要单独说**：它让一次已经跑了 854s、40 轮的 run 直接死掉。而
`llm_preflight.py:310` 固定发 `max_tokens=1`——**结构上永远探不到这个错**，
`llm_compat.py` 的模块注释也自己写了这一点。比赛网关公布的区间就是 `[1, 8192]`，
一旦部署侧把 `LLM_MAX_TOKENS` 配到 8192 以上，**整个比赛的每一次 run 都会在第一步 400**.

处置（接线类，允许合并进同一批）：预检改用**部署声明的那个值**探一次，
或启动时对该 400 直接 fail-fast 并打出一条人能读的配置错误，
不让它以"跑到一半才炸"的方式消耗 run。

## 3 P1 · hint 接线（弱模型上唯一有 2× 实证的杠杆）

### 3.1 机制

平台把 hint 作为 MCP 工具暴露（`list_hints` / `view_hint`），且本题计费是 **discount**：
开提示只封顶本题收益（`cost_percent`），**不扣总分**。在动态衰减已经把所有晚解题压到
10% 下限的赛制里，这个代价基本可以忽略。

改动：给 agent 一个 hint 工具，配闸门——**卡住 ≥ N 步才允许调用**，避免第一轮就要答案。

### 3.2 物理依据

- 外部实证：Cybench 上 Llama 3.1 405B 由无引导 7.5% 升至**子任务引导** 15.0%（40 题，约 2×；
  arXiv 2408.08926）。注意这是"把题拆成子任务"的引导，**不是"给提示答案"**——两者都叫 hint 容易混。
  同表 GPT-4o 12.5% → 17.5%，量级一致。
- 该增益能否迁移到**平台发放的 hint** 上，没有任何直接实证（Cybench 的引导是脚本化子任务，不是
  人写的提示）。这条只支撑"分解式引导对弱模型有效"，不支撑"要 hint 能翻倍"。
- 我方失败面：40 道零解出里 14 道是能力缺口（`docs/24` 套路缺口清单），hint 正好补这个缺口，
  且**不引入过拟合**（提示是题目作者写的，不是我们对着失败日志编的）。

### 3.3 风险与前提

- 入围赛 5 题 `hints_released = 0`、`list_hints` 返回 404 → **这个比赛的题可能压根没有 hint**。
  官方 Q&A 印证了这种不确定性：*"命题团队题目在长期无队伍解题情况下可能放出 hint"*（#60）
  ——即 hint 由人工在窗口内**择时释放**，开赛时大概率一条都没有，且**同一道题可能在下午才有**。
  所以探测必须是**周期性且廉价**的，不是开赛探一次就永久静默。
- 所以：探测做成**低频轮询**（每题至多每 20 分钟一次 `list_hints`，空返回就静默到下一轮，
  不进退避、不进上下文），而不是开赛探一次。按 10 小时窗口算，单题最多 ~30 次调用，
  相对 40 次工具调用的单题预算可忽略；而错过一条后半天才放的 hint 的代价是整道题。
- 判据：一旦某题 `hints_released > 0`，该题**立刻**允许走 hint 闸门（卡住 ≥N 步才调用），
  其余题维持静默。

### 3.4 验收

探测到 `hints_released > 0` 的题才算接线成功；A/B 在**未解题**上比解出率（不看分数，分数受衰减污染）。

## 4 P2 · 离线解法检索（自家台账进 agent）

### 4.1 现状

`docs/44-解出题解法台账` 已建：99 条解法记录 / 74 道题，含方法、工具链、结论。
但它是**文档，不是工具**——agent 看不到。

### 4.2 为什么不能直接当方法卡塞进提示词

- 99/99 条解出记录里**方法卡一张都没注入过**（`experiments/card_ab_corpus.json`），说明
  "解法"不是靠提示词给的。
- 按标签路由会把无关题误导进去（`docs/44` §2 已实测）。

### 4.3 合规性（2026-11-15 已确认）

官方 Q&A #80 原话：*"部署阶段预置离线知识是允许范围，视为智能体部署的包含环节"*，
提问者举的例子正是 writeup 语料库、漏洞库、本地 RAG。这条把 P2 从"赌规则"变成
"照规则做"。唯一限制在模型侧（#79 不许中转站、#21 不许境外），与离线检索无关。

### 4.4 做法

做成**按需检索**：agent 显式调用时，按「题型 / 工具 / 首个线索形态」返回 ≤ 400 字的检索结果，
不进 system prompt、不常驻上下文。

外部依据（2026-11-15 逐条核对二手引用后更正）：网上流传的「CTFAgent 去掉 writeup 检索 73%→61%」
**是误引**——73→61 是去掉**交互式环境（EA）**的消融。去掉 RAG 的真实数字是 InterCode 部分口径
73%→59%（−14pp）、严格口径 82%→76%，而 NYU 上只有 **9%→7.5%（−1.5pp）**（arXiv 2506.17644）。
换言之 RAG 的增益高度依赖基准，在接近实战的 NYU 上是个位数 pp。CRAKEN 的旁证一致：
Graph-RAG 22.0% / 经典 RAG 21.0% vs 无 RAG 基线 19.0%（+2–3pp，arXiv 2505.17107）。
**所以 P2 的预期收益按 +2–3pp 估，不按 +12pp 估**；能不能兑现取决于检索条目质量而非检索算法
（CRAKEN 换知识库内容后反而掉到 15.5–17.5%）。

更要紧的反面：给「不许用预训练知识直接给答案」指令后，NYU 上 D-CIPHER 从 13.6% 掉到 9.7%
（相对 −29%；arXiv 2605.11504）——说明静态基准上相当一部分"检索收益"其实是背答案。
我们量 P2 必须在**未解过的题**上量，并且要预期收益比文献小。

### 4.5 验收

只在**未解过的题**上量；已解题上量不出东西。检索空命中率必须 < 30%，否则是噪声。

## 5 P3 · 门控问题（`requires`）追打闭环

**先纠一个名**：这个比赛**没有多 flag 渗透题**，官方原话是"都是单 Flag，只有完整完成挑战
才能获得 Flag"（#59）。所以初版写的"多 flag 追打"是伪需求。真实存在的是**一个问题组**：
`POST /instances` 返回的 `questions[]` 带 `requires`，答对前置问题后后续问题才解锁
（接口文档 §3.1、§6.6 的 409 `question_locked`）。

掉分点仍在：`gated_questions > 0` 时，「只答第一题就停」会拿到一小部分分数
（`share_percent`）并**看起来像放弃**。

我方现状：`autosubmit.py:457` 的 G1 已经会重读并把未解锁题回写给模型，入围赛 4 checkpoint 全取。
缺口是**回写 ≠ 推动**：没有把"还有未解问题"变成收尾的硬性条件。

另配一条硬约束（F13）：`attempts_cap` 用尽后平台返回 429 `question_attempt_cap_exceeded`，
**此时该问题在本实例上永久不可再交**，必须当作终态而不是可重试错误——
`autosubmit.py:624-636/758` 已在读 `attempts_remaining` 并在为 0 时跳过，本轮只补
"429 不进退避重试"的断言。

改动：`gated_questions > 0` 且仍有未解问题时，收尾动作必须显式回答"为什么不继续"
（写进 result.json 的 summary），而不是静默结束。

## 12 调研落点（2026-11-15，三路并行调研汇总）

三路：① 弱模型提解出率的论文证据（逐条核对到 arXiv ID）；② 往届冠军 agent 的打法（AIxCC 2025 决赛、
Tencent Hackathon AK 队、DEF CON）；③ 我方语料审计（402 run 的负结果台账 + 引用溯源）。

### 12.1 先纠正目标函数：解出率不是瓶颈

入围赛成绩单实测（520 队，`dynamic_points / exponential / decay_solvers=30 / minimum_fraction=0.1`）：

- 名次 3–79 共 77 队分数**完全相同**（442 分 / 4 题 / 7 flag），并列靠**到达时间**拆。
- 我们 rank 58、442 分、4 题，与 rank 30 同分，只是晚了约 1h40m。
- 5 题的价值极不均：`The Last 3 Minutes`（2 队解出）= **970 分**，占榜首 1412 分的 68.7%，
  比我们全部 442 分还多一倍；其余 4 题挤在 100–142 分。

**结论**：中位队伍已经全解了便宜题，抬"平均解出率"对名次贡献趋近 0。**只有尾巴题动名次。**
所以本计划的重心应偏向 P3（门控追打）与"单题投入深度"，而不是"多解几道中位题"。

### 12.2 有实证的杠杆（按证据强度排序，不是按我偏好）

1. **独立重试，新上下文，N=5–10。** 证据最硬且模型无关：ReAct&Plan 在 InterCode-CTF 上 @1 89%
   → @5 95%（arXiv 2412.02776）；AutoPenBench 上多跑一次新上下文单题 27.3% → 45.5%（+18.2pp）；
   弱模型更吃这个——DeepSeek 5 次采样以约 1/3 成本超过前沿单次（arXiv 2407.21787）。
   CTF 曲线在 **k=5 后收益递减**，k>10 无公开数据。**注意：这是"新上下文重开"，不是"把一个上下文拖长"**。
2. **agent loop 与 ACI，而不是更长的提示词。** ReAct 反思-行动循环 +26pp（57%→83%）；
   结构化工具输出 +10pp（95%→85% 反向）；交互式工具（gdb + pwntools server）去掉后 CyBench 20%→10%、
   pwn 类 20.45%→11.36%（arXiv 2409.16165）。这些效应量普遍大于 planning/checklist 类，且弱模型同样受益。
3. **离线检索（RAG），预期压到 +2–3pp。** 见 §4.4 更正：NYU 上只 +1.5pp；静态基准上的"检索收益"
   有相当部分是背答案（加反泄漏指令后掉 29% 相对）。

### 12.3 冠军打法里可迁移的四条

AIxCC 2025 决赛：Team Atlanta 第 1（392.8，43 个 PoV、100% 提交精度）；**Trail of Bits Buttercup 第 2
（219.4），明确号称"全部使用更便宜的非推理模型"**，单点成本最低（$181/point）；Theori 第 3（210.7），
55 次提交只有 61.8% 精度，被精度罚分 −16.3 **直接掉一名**。

- **非推理模型能拿亚军** → "没有顶尖模型"不是判死刑，harness 与流程决定大部分。
- **传统工具为底，LLM 只做语义判断**（不是让 LLM 干所有活）。
- **提交精度是第一杀手**：错一次比少交一次贵得多。我们入围赛 **64 次提交 / 7 个 flag（约 11%）**，
  而平台单题有 `attempts_cap`——精度低会**先耗尽机会**再谈能力。
- **提前交、严格去重**：AIxCC 的 PoV 平均在窗口 25% 处就已提交。

反例同样重要：D-CIPHER 自测里 **auto-prompter 让成绩从 22.0% 掉到 19.0%**；
Theori 发现裸 `bash` + grep 会炸上下文（一次 grep 9MB），改用窄工具 + `tool_choice=required` + 终止工具，
并注明"**这对工具调用能力弱的模型帮助最大**"。

### 12.4 我们自己的负结果（不要重做）

402 run 台账已settled：turn 方向 8 种全部否决；事实台账 7% < 80% 阈值；source_harvest 6/397；
P5 前提 0 输出；P16 重试无增益；上下文按龄裁剪是负优化（缓存命中 95.7%→57.8%）。
**这些不要再花预算验证。**

### 12.5 本轮唯一"零代码"的新发现

`STRIX_FORCE_REQUIRED_TOOL_CHOICE=1` —— vendored strix 早就有这个开关
（`strix/config/settings.py:59` → `core/inputs.py:269` → `core/runner.py:374`），
`_accepts_required_tool_choice` 对 `openai/*` 放行，正是我们的 `STRIX_LLM=openai/deepseek-v4.1-flash`。
外部依据是 EnIGMA 实测 Claude 3.5 Sonnet 有 **48.4% 轨迹出现"自言自语"式编造观测**
（arXiv 2409.16165）+ Theori 的同类发现。**一个环境变量，不动 vendor，不动预算。**
但它会改变每轮的采样行为，按纪律仍需**单独立项 + A/B**，不能和别的改动打包。
