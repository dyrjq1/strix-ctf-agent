# strix CTF 化改造：A/B 基线实验报告

> 实验时间：2026-10-28
> 环境：`unix_local` 后端（无 Docker），DeepSeek-V4.1-Flash，20 turns 上限
> 靶机：CTFY 平台 `UPLOADLABS-001`（easy，AvatarVault 文件上传 → RCE）
> 结论状态：**已验证**（平台返回 `correct: true`）

---

## 1. 实验设计

同一道题、同一模型、同一 turn 预算，**只改一处**：给 agent 的任务指令。

| 组 | 指令内容 |
|---|---|
| **A 基线** | 空（strix 默认 prompt，只给 target URL） |
| **B 对照** | `config/ctf_goal.txt`，仅重定义**成功标准**，**不含任何漏洞位置信息** |

关键设计约束：B 组指令**没有**提及"扩展名校验是客户端"、"上传 PHP"、"读 /answers" 等任何题目细节。它只说了三件事：

1. 成功 = 输出一个 `FLAG{...}`
2. 不要产出报告/coverage/threat_model
3. **拿到代码执行后，立刻用它去找并读取目标文件**

第 3 条是**方法论约束**，不是答案。它可复用到任意一道题。

---

## 2. 结果

### 2.1 主对照（同一道题，只改指令）

| 指标 | A 基线（默认 prompt） | B 对照（改目标定义） | 变化 |
|---|---|---|---|
| **拿到 flag** | ❌ | ✅ `FLAG{b10c8d01...}` | — |
| 平台判定 | — | `correct: true` | — |
| 平台计时 | — | **456.1 s** | — |
| 运行耗时 | 845.7 s | **432.5 s** | **−48.9%** |
| 工具调用总数 | 123 | **42** | **−65.9%** |
| 派生 agent 数 | 5 | 3 | −2 |
| 结束原因 | `MaxTurnsExceeded` | `[done]` 正常完成 | — |

**关键事实：B 组用不到一半的调用、不到一半的时间，解出了 A 组解不出的题。**

### 2.2 泛化验证（同一指令，换难度）

`config/ctf_goal.txt` 一字不改，在另外两道机制不同的题上重跑：

| 题号 | 难度 | 机制 | 工具面 | 结果 | 工具调用 | 运行耗时 | 平台计时 | solve_rank |
|---|---|---|---|---|---|---|---|---|
| UPLOADLABS-001 | easy | 纯前端扩展名校验 | 完整 43 | ✅ | 42 | 432.5 s | 456.1 s | 0 |
| UPLOADLABS-003 | medium | 后缀黑名单 + MIME | 完整 43 | ✅ | 36 | 314.8 s | 340.7 s | 0 |
| UPLOADLABS-011 | hard | 保存路径操纵 | 完整 43 | ✅ | 42 | 436.0 s | 458.8 s | **16** |
| UPLOADLABS-006 | medium | 尾缀接收 | **裁剪 20** | ✅ | 48 | 559.0 s | 583.7 s | **17** |

**4/4 通过，覆盖 easy / medium / hard。** 四题的手法各不相同，agent 自己选的绕过方式也不一样：

- 001：直接上传 `.php`（前端 JS 校验，绕过前端即可）
- 003：`GIF89a` 魔数 + `.phtml` 后缀（双重绕过）
- 011：路径操纵而非后缀绕过
- 006：尾缀接收特性

这说明 `ctf_goal.txt` 里的约束是**方法论级**的，不是对某道题的答案泄露。

> `solve_rank: 16/17` 说明这两道题在平台上分别已有 15、16 支队伍解出，是可靠的难度锚点。001/003 的 rank 为 0，是因为练习套件内已被本账号解过，不再计排名。

### 2.3 工具裁剪实验：一个诚实的负面结果

`tool_trim.py` 把 43 个基础工具裁到 20 个（摘掉 17 个记账类 + 6 个 Caido 依赖项），跑 006 得到 **48 次调用**，而 011 未裁剪是 **42 次**。

**但这不能证明裁剪有害**，因为两题难度和机制不同。能确定的只有三条：

1. 裁剪**没有引入崩溃**，agent 在被摘掉工具后仍然解出了题。
2. 全程只出现 **1 次真实的 `Tool not found`**（另外 2 条 `not found` 是靶机 404 和容器缺 `dig`，与裁剪无关）。
3. `prompt 仍在教 agent 用已摘掉的工具`——这是唯一的确定代价，`get_threat_model` 那次无效调用就是它造成的。

**结论：裁剪本身不是收益点。** 想真正省预算，必须同时改 prompt（把工具说明一起删），否则只是把"调用记账工具"换成"调用失败"。这件事的优先级应当下调。

## 3. 根因：A 组并不是"能力不够"

A 组的日志证据（原样摘录）：

```
[a7cab27b] CMD: uid=33(www-data) gid=33(www-data)
[a7cab27b] TOOL update_coverage {"outcome": "reported",
  "evidence": "CONFIRMED RCE. Uploaded a7cmd.php (<?php system('id');?>) -> GET /uploads/a7cmd.php returned uid=33(www-data)"}
```

**它已经拿到 `www-data` 的任意命令执行，webshell 可用。** 紧接着的 8 个动作是：

```
create_note                → 写"CONFIRMED: Unauthenticated upload -> RCE"
update_coverage  ×3        → 登记三条 finding
save_threat_model          → 存威胁模型
create_agent               → 派"Upload RCE Validation Agent"做独立复现
create_vulnerability_report → 生成漏洞报告
```

**没有一次 `cat` / `find` 去找 flag 文件。** 最后 root agent 自己说：

> `Turn budget exhausted; confirmed RCE evidence already captured in coverage. Finalizing scan.`

它把 RCE 证据写进 coverage，就认为任务完成了。这不是推理能力问题，是**目标函数问题**——strix 被训练成"交付渗透测试结论"，而不是"取走目标物"。

## 4. 预算去哪了：量化工具面浪费

A 组 123 次调用的分类：

| 类别 | 次数 | 占比 | 说明 |
|---|---|---|---|
| 真实攻击动作（exec / write_stdin / apply_patch） | 72 | 58.5% | 其中仍含部分本地文件操作 |
| **记账类**（coverage / notes / threat_model / report / graph） | **34** | **27.6%** | 对拿 flag 零贡献 |
| **子 agent 管理**（create / wait / stop / send） | **10** | 8.1% | 编排开销 |
| 其他（think / todo / finish） | 7 | 5.7% | |

B 组 42 次调用里，**记账类降到 0 次**（仅 1 次 `create_note` 记 flag）。

这直接给出第一个改造点：**`instance` 模式下应把 11 个记账类工具从工具面摘掉**。不是"建议别用"，是让它根本没得选——prompt 只能降低概率，摘工具才能消除。

## 5. 一个意外的架构发现：root 应当只做调度

B 组三个 agent 的分工，干净得超出预期：

| agent | 调用数 | 干了什么 |
|---|---|---|
| root `0bf8ec41` | **9** | 全是管理动作：create_agent×2、wait_for_agents×2、view_agent_graph、mark_todo_done、finish_scan、create_todo |
| 侦察/攻击 `68785ddc` | 21 | 18 次 exec + 2 次 apply_patch，全部打靶机 |
| 验证 `0d70ce7e` | 11 | 10 次 exec，独立复现并 `cat /answers/flag` |

**root 一次都没直接打靶机。** 它把攻击全部下放，自己的上下文只装编排决策。

这比"多 agent 并行提速"更有价值：**root 的上下文是最稀缺资源**。A 组失败的一部分原因就是 root 自己也去做侦察（29 次调用），把上下文喂给了一堆扫描输出。

> 待验证：这个分工是 prompt 自然涌现，还是 strix 的 root prompt 本来就这么写的。如果是后者，`ENABLE_CHILD_AGENTS=false` 这个开关就要重新评估——关掉它可能反而损害性能。

## 6. 已固化的资产

| 文件 | 作用 | 状态 |
|---|---|---|
| `config/ctf_goal.txt` | 被验证有效的目标定义，4 题复用未改动 | ✅ 已验证 |
| `src/ctf_strix/local_backend.py` | 无 Docker 执行后端 | ✅ 已验证 |
| `src/ctf_strix/tool_trim.py` | 工具面裁剪（43 → 20） | ⚠️ 可运行但无收益 |
| `src/ctf_strix/agent.py` | CTFY 合规入口：task.json → 跑 → result.json → exit 0 | ✅ 降级分支已测 |
| `scripts/run_strix_ctf.py` | 单题驱动脚本，带 `--trim-tools` 开关 | ✅ 已验证 |

`agent.py` 的三条设计承诺，每条都对应一个已核实的失败模式：

1. **无论成功、超时还是崩溃，都写 `result.json` 并 `exit 0`。** `no_result_file` 是 blocking 判据，缺失等于零分。
2. **写文件用临时文件 + rename。** 半截 JSON 比没有文件更糟——平台会尝试解析它，把"超时"变成"格式错误"。
3. **`result.path` 从 `task.json` 读，不硬编码。** 平台可能改路径，硬编码会在某个时刻静默失效。

已验证：喂一份 `scope: []` 的假 task.json，输出
`{"answers": {}, "turns": 0, "tokens": 0, "writeup": "…error: task.json 里没有可用的 target URL…"}`，`exit 0`。
失败原因被如实记录，而不是伪装成"进程崩溃"或"静默零分"。

## 7. 这次实验**不能**证明什么

必须写清楚，避免过度外推：

1. **样本 4 道题，且全部是同一类漏洞（文件上传）。** UPLOADLABS 是专门的文件上传靶场，题目描述本身就点明了上传接口和字段名。**换成 SQL 注入、SSRF、反序列化，`ctf_goal.txt` 未必有效**——尤其"拿到 RCE 后去找文件"这条，对不回显 shell 的题不适用。
2. **每组只跑 1 次，无重复。** LLM 有随机性，单次结果不能当稳定成功率。
3. **`solve_time_s` 320-580 s 不是好成绩。** 这里面没有并发、没有失败重试、没有多题调度。且 006 明显比 003 慢（583.7 vs 340.7），说明同难度下波动很大。
4. **平台 TTL 只有 3 小时**（`ttl: 10800`）。这个限制对"一题磨很久"的策略是硬约束。
5. **没有验证过真实的 `ctfy agent check`。** 本机无 Docker，`agent.py` 只在"读 task.json → 写 result.json"这条链路上自测过，没有跑过容器内的完整 dry run。

## 8. 下一步（按性价比排序，已按本轮结果重排）

1. **接真实 `ctfy agent check`** —— 这是唯一的 blocking 未验证项。需要一台有 Docker 的机器或 CI。**没有它，前面所有成绩都不能保证能进赛场。**
2. **泛化目标定义** —— `ctf_goal.txt` 里"拿到 RCE 后去找文件"对不回显 shell 的题不适用。要改成与漏洞类型无关的表述。
3. **扩到非上传类题目** —— 在 misc / prompt_injection 类里挑几道，验证指令是否只在文件上传场景有效。
4. ~~摘工具~~ —— **本轮已证伪**，单摘工具无收益且会引出无效调用。降级为"改 prompt 时顺带做"。
