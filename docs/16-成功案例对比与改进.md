# 16 · 成功案例对比与改进（2026-10-31）

> 本文按用户指定的 8 步工作流写成：定方向 → 找案例 → 读代码对比 → 方案与合规 →
> 改代码/复用 → 测试 → 报告 → （可选）分发。
> 结论先行：**这轮最大的问题不是模型能力，而是“评测装了的工具，正赛入口没装”。**
> 已在 `P15` 修复；案例里真正值得抄的不是多模型并发，而是“失败后带洞察重试”。

---

## 一、8 步工作流的固化形态

| 步 | 动作 | 产物（必须落盘） |
|---|---|---|
| 1 | 定大方向需求 | 一句话目标 + 可量化缺口（如“非 web 解出率”） |
| 2 | 找成功案例 | 仓库 URL、许可证、比赛名次、可核对的战绩 |
| 3 | 读代码对比 | 差异表：并发 / 上下文 / 工具 / 组织 / 预算 / 测量 |
| 4 | 方案 + 合规 | 每条改动标注是否碰 `internet_policy`、实例数、模型数、人工提示 |
| 5 | 改代码或复用 | 优先复用 MIT 工具；新工具必须注册且进守卫名单 |
| 6 | 测试 | 单测 + 同题同预算 A/B；看 `my_fully_solved`，不看 `SOLVED` 日志 |
| 7 | 报告 | 本文 + `docs/11-实验台账.md` 一行基线/回滚 |
| 8 | 分发（可选） | 只分发文件梳理/测试生成；不把 token、凭据交给外部 agent |

**节奏约束**：每改 3 次代码，至少查 1 次权威资料（论文 / 官方文档 / 往届项目源码）。
本轮的资料就是两个项目的源码 + STRIATUM 的 180 次实验数据，属于一手来源。

## 二、案例 A：ctf-agent（Veria Labs）

- 仓库：`https://github.com/verialabs/ctf-agent`，MIT，900 stars（2026-10-31）。
- 战绩：BSidesSF 2026 **52/52，第一名**；作者来自 CTFTime 美国第一战队 smiley。
- 结构：Coordinator LLM + 每题一个 `ChallengeSwarm`；swarm 内 5 个模型各自一个
  Docker 沙箱并行跑，先拿到 flag 的胜出，其余取消。

### 2.1 值得抄的三处（代码级）

| 机制 | 位置 | 做法 | 我们的对应物 |
|---|---|---|---|
| 循环检测 | `backend/loop_detect.py` | 窗口 12；同一 `(tool, args[:500])` 出现 3 次警告、5 次**直接不执行**，把警告当工具结果返回 | `enum_guard.py` 更强：按 host + 路径族 + **响应指纹**归一化，2 次同响应警告、4 次硬警告、6 次跨族停滞 |
| 失败后注入同伴洞察 | `backend/agents/swarm.py` + `message_bus.py` | 每次重试前 `bump(insights)`；冷却 `min(30·n, 300)s`；连续 3 次 ERROR 才放弃；0 步 0 费用的“坏启动”不计重试 | **无**。我们失败后是整题重跑，洞察不跨 attempt |
| 先到先取消 | `swarm.py::run` | `asyncio.wait(FIRST_COMPLETED)`，首个 flag 到达即取消其余任务 | 单 agent，无此问题 |

另外两个细节：`message_bus` 上限 200 条、每 5 步注入一次未读发现；提交层有
`_submitted_flags` 去重和按模型计的错误提交次数。这些是“多 agent 才有意义”的
配套，单 agent 不需要照搬。

### 2.2 不能照抄的两处

1. **多模型赛马**。正式赛是单模型契约（智谱），且每队同时只有 1 个题目实例
   （练习赛 `max_instances_per_team_effective=1`）。5 路赛马会变成 5 倍 token
   换 1 个答案，还要额外处理限流；规则上也不允许按角色切模型。
2. **每题一个 Docker**。我们的运行环境没有嵌套 Docker，strix 已用本地
   `unix_local` 后端替代；再引入容器层只会增加启动失败面。

### 2.3 并发到底能抄什么

可抄的是**调度语义**，不是线程数：

- 首解即取消（单 agent 无意义，但批量跑多题时可用于提前结束）；
- 失败后的“带洞察重试”（P16 的核心）；
- 按 `solves_count` / 动态分值排序，而不是按难度标签（QA#34 只保证类型标签）。

## 三、案例 B：STRIATUM-CTF（FSU）

- 仓库：`https://github.com/jawh3/striatum-ctf`，MIT；论文 arXiv:2603.22577，
  IEEE CARS 2026 **Best Paper**。
- 结构：6 个 MCP server（filesystem / commands / gdb / ghidra / angr / secops），
  一个 `triage.py` 做赛前分类，模型按“阶段协议”解题。

### 3.1 它最重要的数据是否定性的

180 次实验 = 15 题 × 4 种文档条件 × 3 次：

| 条件 | 文档规模 | 解出 |
|---|---:|---:|
| Minimal（只有工具 schema） | 55 行 / 591 tok | 35/45（77.8%） |
| Lessons | 1,478 行 / 12.9k tok | 37/45（82.2%） |
| Templates | 1,976 行 / 17.3k tok | 38/45（84.4%） |
| Baseline（全量） | 4,147 行 / 36k tok | 39/45（86.7%） |

- 最大差距 4/45 = **+8.9pp**；论文自己的 Kruskal–Wallis `p=0.77`、GEE `p=0.29`，
  不显著。和 `docs/10` 引用的 “When Skills Don’t Help” 结论一致。
- **唯一被文档翻盘的题**是 `sample7`（heap overflow）：Minimal/Lessons/Templates
  都是 0/3，Baseline 是 3/3。Baseline 多了 `HEAP_EXPLOITATION_LESSONS.md`（353 行）
  和 `HEAP_OVERFLOW_ADDENDUM.md`（240 行）——**具体技术笔记 + 可执行步骤**，不是
  泛泛的方法论。

**裁决**：停止扩充技能文档（我们已有 12 个索引 / 178 个子文件）；把预算转向
“可执行原语”和“具体题型的 worked example”。若要做 pwn，就做一份能直接跑的
heap 笔记 + 脚本，而不是再加一篇概览。

### 3.2 它的上下文管理其实是“协议 + 外部状态”

`code/triage/triage.py`（545 行）在开赛前对附件做一次确定性探测：

- `file` / 大小 / 可执行位；
- `strings` 分类：flag、成功/失败提示、crypto 常量、网络线索、框架线索、输入限制；
- 崩溃探测：1000 个 A、超长输入、`%s`/`%x`、空字节、换行；
- 时序探测：10 组输入 + **同一输入重复 5 次**做噪声对照，方差 >15% 才提示时序侧信道；
- Python 脚本的 RSA/AES/编码模式识别；
- 输出 `classification / confidence / recommended_approach / recommended_tools`，
  并落一份 JSON。

它的协议还要求：Phase 0 读完所有源码、维护 `PROGRESS.md`、每 5–7 次工具调用
停下来复述假设。

**对照我们**：

- `file_triage.py` 已覆盖“一次调用给家族 + 下一条命令”，但**没有崩溃/时序/格式串
  探测**，也没有结构化 JSON 供后续步骤消费；
- 我们的“外部状态”是 `[ENUMERATION GUARD]` / `[STATE]` 注入，属于同一思路
  （把约束放在工具结果里），而且更贴近决策点；
- strix 自带 `auto_compact=True`、`compact_buffer_tokens=20k`，上下文压缩不是缺口。

**裁决**：不重写 triage；只在 `kind=="file"` 时把“崩溃/格式串/时序”三组探测
并进 `file_triage`（P17），并且只在二进制题注册，避免 web 题付 schema token。

## 四、逐项对比：我们到底差在哪

| 维度 | Veria | STRIATUM | 我们（改前） | 判断 |
|---|---|---|---|---|
| 并发 | 5 模型 × 5 容器赛马 | 单 agent + 6 MCP | 单 agent，批测串行 | 不抄赛马；抄失败重试 |
| 上下文 | 每 5 步注入同伴发现；重试换新上下文 | 文档 + PROGRESS.md + 定期复述 | vendor 自动压缩；守卫注入 | 不缺点，缺“跨 attempt 的记忆” |
| 工具面 | bash + 10 个专用工具 | 6 个 MCP server | 44 基础裁到 ~21；+5 原语 | web 够强；非 web 缺原语 |
| 组织 | Coordinator 调度 swarm | 单 agent + 阶段协议 | 默认关子 agent（实测协调占 22%） | 组织方式正确，别加回来 |
| 预算 | step cap + bump 冷却 | 60 分钟上限 | turns + 可选软截止 | 缺 attempt 间预算分配 |
| 测量 | cost/token/step 全记 | 180 次对照实验 | batch_eval 记 solved/turns/tokens | 测量够；**入口与评测不一致** |

### 4.1 本轮发现的真问题（按严重度）

1. **P0 · 入口能力缺失（已修）**：`scripts/run_strix_ctf.py` 装了 `http_probe`、
   `route_map`、`method_sweep`；`src/ctf_strix/agent.py` 没装。也就是说 009 从
   77 次降到 13 次的收益，**在正式提交的镜像里根本不存在**。
2. **P0 · 工具面不一致（已修）**：评测摘掉 17 个记账工具，正赛入口保留。
   web/file 题白付 schema token，还诱导模型写报告。
3. **P1 · 失败无记忆（待做）**：重跑是“从零再来”，不携带上一轮试过什么、
   哪条报错最有信息量。Veria 的 `bump` 正是补这个。
4. **P2 · 非 web 原语不足（待做）**：pwn/crypto/misc 只有 `file_triage` 一个入口，
   没有偏移计算、ELF 结构、RSA/AES 快速路径。
5. **P3 · 难度调度粗（待做）**：按 easy/medium/hard 乘 turns，而平台只保证类型
   标签；应按 `solves_count` / 动态分值 / 剩余时间排。

| 改动 | 外网 | 实例数 | 模型数 | 人工提示 | 结论 |
|---|---|---|---|---|---|
| P15 入口装 `http_probe`/`route_map`/`method_sweep` | 否，全本地 | 不变（1） | 不变（1） | 否 | 合规 |
| P15 非 engagement 摘记账工具 | 否 | 不变 | 不变 | 否 | 合规 |
| P15 软截止（`CTFY_SOFT_DEADLINE`，默认关） | 否 | 不变 | 不变 | 否 | 合规 |
| P16 带洞察重试（计划） | 否，摘要只来自自己的工具输出 | 同一实例内顺序重试 | 不变 | 否 | 合规；须先确认单题墙钟 |

| 不采用：运行期下载工具 | 违反 `internet_policy=deny` | — | — | — | **不采用** |

符合“人类不得给提示”的红线——摘要是 agent 自己观测的压缩，不是外部知识。

## 七、下一步（按 ROI 排序）

### P16 · 带洞察重试（Veria `bump` 的单 agent 版）——已实现，A/B 未通过

- 触发：一轮结束仍无答案，且剩余墙钟 ≥ 一轮预计耗时。
- 摘要（确定性、无 LLM）：本轮试过的 method+path（去重）、每个 path 见过的状态码、
  最有信息量的 3 条错误原文、尚未试过的 method、已确认的凭据/cookie 名。
- 第二轮指令：附摘要 + “这些已试过，换机制”，并给 60/40 的 turn 切分。
- 开关：`CTF_ATTEMPTS=2`（默认 1），`CTF_ATTEMPT_SPLIT=0.6`。
- 验收：在 5 道当前未解的 medium 上 A/B；只有 `my_fully_solved` 增加且
  token 增幅 < 2.2× 才算通过。
- 回滚：环境变量改回 1。

**实现位置**：

- `src/ctf_strix/attempt_digest.py`：确定性摘要。输入是本轮 root agent 的
  `(tool, args)` 与输出，输出是“试过的 method+target → 首个信号”、去重后的
  高信息错误行、以及繁忙路径上未试过的方法。过滤 `FLAG{...}` 与
  `token/password/session` 的值；过滤 `finish_scan` / `load_skill` 等元工具，
  避免把“收工被拒”的文本当成一次探测。
- `src/ctf_strix/agent.py`：`_attempt_count()` 把 `CTF_ATTEMPTS` 限制在 1–3；
  `_attempt_turns()` 按 `CTF_ATTEMPT_SPLIT` 切分总轮次；`_go()` 在第 2 次起
  用**同一个 `scan_id` 续跑**（strix 会恢复沙箱与 SDK 会话，再注入
  `resume_instruction`），并明确要求“换机制，不换参数”。
- 第二遍不是新开沙箱：`/tmp` 下的脚本、登录 cookie 都保留；这是 Veria
  `bump` 的真实等价物。新开沙箱的版本已废弃（A/B 首轮即证明会丢登录态）。
- 工具调用与输出按 `call_id` 配对；provider 不给 `call_id` 时退回顺序配对，
  再退回“最老的在途调用”，避免 `load_skill` 的输出被配到 `http_probe` 上。

**已验证**：

- 单测：`tests/test_attempt_digest.py` 7 条（动作性错误、flag/凭据抹白、去重、
  元工具过滤、空输入、硬上限、shell 命令）。
- 本地 mock 靶机：首轮 3 次探测 → 470 字摘要 → 第二轮启动；摘要包含
  `GET 127.0.0.1:18080/ -> 404` 与未试方法。
- 真题 `CTFARENA-082`：首轮 8 次探测 → 1363 字摘要 → 第二轮 8 轮启动，
  `result.json` 正常写出；**该题未解出**，因此本轮不主张解出率提升。

**A/B 结果（新沙箱版本，已废弃；3 道未解 medium，统一 20 轮）**：

| 题目 | attempts=1 | attempts=2 | 解出 |
|---|---:|---:|---|
| CTFARENA-082 | 10 轮 / 358,779 tok / 33.4s | 17 轮 / 654,508 tok / 70.9s | 都未解 |
| CTFARENA-018 | 23 轮 / 1,248,405 tok / 234.1s | 22 轮 / 955,592 tok / 127.7s | 都未解 |
| CTFARENA-078 | 12 轮 / 439,049 tok / 48.6s | 21 轮 / 738,033 tok / 76.9s | 都未解 |

**裁决：P16 未通过验收**。没有多解出任何一题；token 比值为 1.82× / 0.77× / 1.68×，
平均约 1.42×。因此 **`CTF_ATTEMPTS` 默认保持 1**，代码保留但不在正赛启用。
这不是“机制一定无效”，而是“当前摘要的信息量不足以让第二遍换对方向”；在拿到
正向证据前，不应拿它消耗决赛墙钟。

**同会话续跑版本（最终形态）**：082 的第二轮在 `finish_scan` 参数里已经写出
正确答案 `FLAG{93ac...}`，但入口只扫描工具输出，没有采集。修复后重跑：

| 题目 | attempts=1 | attempts=2 | 归因 |
|---|---|---|---|
| CTFARENA-082 | 未解（修复前旧跑） | **解出**（提交 `correct=true`，平台 `my_fully_solved=true`） | 单轮内解出，`retry_logged=false`；**归因于 flag 采集修复，不是重试** |
| CTFARENA-078 | **解出**（16 轮 / 628k tok / 63.5s） | 未解（13 轮 / 523k tok / 47.2s，`retry_logged=true`） | **重试臂反而失败**，不支持 P16 |
| CTFARENA-018 | 未解（22 轮） | 未解（23 轮） | 无差异 |

**最终裁决：P16 仍不通过验收，默认关闭。** 但同一次实验暴露并修复了一个
更高价值的得分漏点：`finish_scan` 的**调用参数**里可能带着答案，而入口原先只
扫描工具输出。修复后 082、078 两题从“未解”变为“确认解出”（平台
`my_fully_solved=true`），这是本轮唯一可归因的正向收益。

**已知限制**：

- 摘要不包含响应头（如 `Location`、`Set-Cookie`），对 302 链路的提示偏弱；
  下一版可从 `http_probe` 的结构化字段直接取。
- 摘要目前只看 method/path 与错误行，不看“上一轮最后卡在哪个假设”；第二遍
  仍可能重复同一类思路，只是换了参数。

### P16.1 · 答案采集补漏（已修，独立于重试）

- `agent.py` 在 `tool_call_item` 上用**完整参数**（不是截断后的 300 字）跑
  `_extract_flag`，覆盖 `finish_scan` / `answer` 这类把答案放在参数里的收工调用。
- 过滤条件仍走 `flag_extract.best_flag`：本题 host 邻近、排除 recon 残留、
  排除模板占位符。engagement 不启用。
- 单测：`tests/test_tool_arg_flag.py` 2 条。
- 实测：082、078 均提交成功，平台确认 `my_fully_solved=true`。

### P16.2 · 验收口径修复（已修）

- `batch_eval.Client.detail()` 原先把 `/challenges/{id}` 的快照当权威；该快照
  在提交后可能仍返回 `my_fully_solved=false`。
- 现改为先查**竞赛列表**（`/competitions/{id}/challenges`，必须分页：默认 50，
  本题库 115），查不到再退回详情端点。
- 实测：修复前 082 显示 false，修复后显示 true；078 同样由 false 变 true。
- 这条修复影响所有“解出率”统计，属于测量可信度问题，优先级高于任何解题技巧。

### P17 · 非 web 原语（复用 directions-pack）

- 优先级：`elfpeek`（ELF/节/符号/反汇编入口）→ `pwngen`/`pwnfind`（偏移）→
  `tcp`/`tcp_batch`（交互）→ `rsatool`/`aesblock`/`prng` → `decode_blob`/
  `unpack_archive`/`hexpeek`。
- 只在 `kind=="file"` 注册；每个工具单独 pytest；工具名登记进
  `enum_guard._PROBE_TOOLS`（踩过的坑：漏登记 = 守卫静默失效）。
- 验收：3 道 pwn/rev 样例题各跑一次，至少 1 道从“无入口”变成“有明确下一步”。

### P18 · 难度调度

- 用 `solves_count` 与动态分值排序，不依赖 easy/medium/hard 标签。
- 剩余时间 < 25% 时只做“高分解 + 已有部分进展”的题。

### P19 · 赛后 playbook（可选）

- 只记录“哪类题、第几次调用、哪个原语首次拿到新信息”，不记录 flag；
- 下一题按 tag 注入最多 3 条；若 P16 的 A/B 没有增益就不做。
