## 0. 口径（先说清楚怎么算的）

| 概念 | 定义 | 数据源 |
|---|---|---|
| **run 行** | 结果 JSONL 里一行，`run_id` 去重后的**一次派单** | VM `/home/rjq/**/*.jsonl`，740 条 |
| **进入（entered）** | 该 run 的 `agents.db` 里 **≥1 条 `function_call`**——模型真的调用过工具 | 459 个 `agents.db` 只读连接 |
| **接触（contact）** | 目标类工具（`http_probe`/`tcp`/`route_map`…）或带 URL 的 `exec_command`，且输出**无**传输失败标记 | 同 docs/39 §3.1 口径 |
| **会话** | `agents.db` 里的一个 `session_id`，一次 run 可能有多个 | 462 个会话 |

两条分母必须分开说：**run 行**回答"派单有没有变成一次真实尝试"，**会话**回答"尝试里有没有连上题"。
混用会得出"一半的题碰不到"这种错结论。

> 下面的 §2.1/§5/§6 数字是首次口径，已被 §11 修正；**结构性结论不变、且更强**。

## 1. 结论先行

1. **题级接触率 96.3%**（182/189 道有过结果行的题，至少进入过一次；§11 复算）。这不是瓶颈。
2. **run 级只有 51.6%**（382/740，§11 复算；首次口径 50.1%）进入 agent；但未进入的 358 条里 **262 条（73%）是 3 道题被重试了 233 次**——`compete` 的 B-23 连跳计数上线之前，state 里没有 `skips` 字段，调度器会对同一题无限重派。**已修复，11-14 同类只剩 15 条。**
3. **真正从未进入过的题：7 道**（全部是单次受害于平台抖动/隧道）。曾误记为"另有 8 道零工具题"，复核证明它们都有工具调用（§11）。
4. **run 内的接触质量不是问题**：有判定的 346 场会话里 98.1–98.6% 是 `CONTACT_OK`，首次成功接触中位落在**第 1–2 次调用**。
5. 还活着的接触风险是**"整队静默失效"**类（凭据、配额、实例就绪），不是"agent 摸不到目标"。这类风险在 10 小时赛里会一次性烧掉整批派单。

## 4. 需隧道 262 条的解剖（最大的一坨，也是最容易被误读的一坨）

| 维度 | 数值 |
|---|---|
| run 数 | 262（占全部未进入的 71%） |
| **不同题数** | **15** |
| 前三题 | SAMPLE-023（80）、SAMPLE-024（79）、SAMPLE-017（74）= **233（89%）** |
| 时间分布 | 11-13 一天里 239 条；11-14 15 条；其余 8 条散在 10-30/11-01/11-03 |
| 11-13 窗口 | 09:34 → 16:12，**约 30 秒一次重派** |
| 这三题最终解出 | SAMPLE-017 **1 次**、SAMPLE-023 **1 次**、SAMPLE-024 **2 次** |

**根因不是"隧道永远建不起来"，而是两个叠在一起的问题：**

1. **实例间歇可达**：同一题在 78–85 次尝试里有 1–3 次是干净 run，且解出过。靶面是 netns/`.internal` 型，平台侧放行不稳定。
2. **调度器无限重派**：`compete-state-run2` 的 state 里 **`skips: None`**——B-23 的连跳计数还没写入，判据永远是 0，于是每 30 秒重派一次，一整天。

**已修复的证据**：B-23 落地后，11-14 同类只剩 15 条（全是 AUTHORED-*），不再滚雪球。B-25 的 DNS 竞态重试（6×5s）也在这条路径上。

> 教训写在这里：**"35% 的派单白扔了"这句话本身是错的**。它是 3 道题 × 78 次重试的产物，
> 题级损失只有 3 道，而且这 3 道后来都解出来了。**看漏斗必须同时看 run 数和题数。**

## 11. 勘误：`agents.db` 联表少算了「进入」（2026-11-15 夜，C 项复核）

### 11.1 怎么发现的

C 项要复核 9 条"零工具但判 correct"。打开结果行发现它们自带 `tool_calls` 字段：
SECQA 各 1、SAMPLE-005 6、SAMPLE-020 22——**都有调用**。再去 460 个 `agents.db` 里找这 9 个
`run_id`，**一条都没有**（box 已被 `night-state-3` 清理）。而早先的 `source_leak_gap*.json`
里对 SAMPLE-005/020 记的正是 `calls: 6` / `calls: 22`——两份历史材料互相印证：它们跑过工具。

### 11.2 换判据后的漏斗

结果行的 `tool_calls` 字段**出现即代表 agent 起来了**：

| 行 | 数 | 说明 |
|---|---|---|
| 740 条 run 行 | 100% | 与 §0 同一批（`run_id` 去重） |
| └ **有 `tool_calls` 字段** | **401** | agent 起来了 |
| └ 无字段 | 339 | 全是没起来的：SKIP 281 / http403 21 / Timeout 16 / Runtime 7 / Proxy 5 / Connect 3 / KeyError 2 / Header 2 / BrokenPipe 1 / TimeoutExpired 1 ——**判 correct 的 0 条** |

| 指标 | 首次口径（agents.db） | 复算（行字段） |
|---|---|---|
| run 级进入 | 371 / 740（50.1%） | **382 / 740（51.6%）** |
| 进入且解出 | 206 | **214**（56.0%） |
| 未进入但解出 | 9 | **1**（SAMPLE-006 假阳性） |
| 题级进入 | 174 / 189（92.1%） | **182 / 189（96.3%）** |
| 从未进入也从未解出 | 7 | **7（名单一模一样）** |

**两条独立口径给出同一份 7 题名单**，这是本文最稳的结论：接触损失就是那 7 道。

### 11.3 唯一一条真正的「零工具 but correct」

`SAMPLE-006 / 20261113-150824`：`tool_calls=0`、`stop_reason=error`、
`error=transport:openai.PermissionDeniedError`、`agent_s=9.1`，却记了 `correct=True`。
**凭据都没过、一次工具都没调**——这条只能来自提交链路把候选答案当成了真解，
与 docs/39 §3.4 的 autosubmit 假阳性同源。**不要计入能力，也不要计入接触。**

### 11.4 方法论结论（下次直接照这个来）

- 算"派单有没有变成尝试"，**用结果行的 `tool_calls` 字段**，不要去联 `agents.db`：
  box 有保留期，联表只会少算，且少算得没有规律。
- `agents.db` 仍然只适合回答"这次尝试里调了什么、连没连上"（会话级接触质量，§2.2 不变）。
- 任何"零工具"结论都必须先说清口径：是**没起 agent**（无字段）还是**起了但没调工具**（`tool_calls=0`）。
