## 0. 结论先行

1. **我们的失败不是「不知道有哪些漏洞」，而是「知道，但打不深、不收手」。**
   失败的 run 试的漏洞族**比成功的更多**（source_leak 45.6% vs 23.1%，SSRF 61.1% vs 40.8%），
   调用数是成功的 2.8 倍（36 vs 13），却解不出来。再加一类工具的边际收益因此很低。
2. **我们自建的结构化原语正在被模型绕过。** 277 个 run 里 `exec_command` 占 64% 的调用，
   `http_probe` 只占 14%；HTTP 大多走 curl/python 命令行，**不进流量台账**（台账 §4.182 已记）。
   后果：依赖台账的 `traffic_list`(27 次)、`traffic_view`(116 次)、`viability_probe`(**0 次**)
   实际上等于没上线。这是今晚最值得修的结构问题。
3. **外部证据一致指向三个与题目无关的机制**：成功在 40 次调用内见分晓（止损早于加量）、
   灰盒源码显著优于纯黑盒（AXE 1.75×）、结构化反思/事实台账优于裸长上下文。
   三者都**不需要**我们再加一个漏洞族工具。

## 2. 外部证据（按证据强度）

1. **止损 vs 加量**（最强、且就在我们的题型上）：MAPTA 在 **104 道 XBOW web 题**上，
   成功与工具调用数强负相关（r=−0.661），失败题烧更多时间/成本；建议约 40 次调用 /
   $0.30 / 300s 无进展即换线。<https://arxiv.org/html/2508.20816v1>
2. **验证门（独立 oracle）**：AIxCC 决赛中采用 multi-PoV 校验/反思的队伍语义错误 16–21%，
   未采用者 38–46%（相关性，非受控消融）；XBOW 用 validator + 无头浏览器真跑 XSS。
   <https://arxiv.org/html/2602.07666v4> · <https://xbow.com/blog/top-1-how-xbow-did-it>
   ⚠️ CTF-ABACUS 反向证据：强制"执行证据"后分数普降 17–22%，说明**自报成功被高估**——
   验证主要提升精度，不一定提升解出数。
3. **灰盒优于黑盒**：AXE 在 CVE-Bench 用灰盒元数据拿到 30%（SOTA 13% 的 3×），
   单 agent 下灰盒元数据带来 1.75×；纯黑盒上限 13%。
   <https://arxiv.org/abs/2602.14345> · <https://arxiv.org/abs/2503.17332>
4. **事实/意图台账**：Intentest 在 10+ 类漏洞的 web CTF 上 88.2%（+44pt），hard +50pt，
   轮数 −33~−48%。<https://arxiv.org/abs/2609.07344>
   但注意：ACE 的外置台账实证不在 CTF 上；**长上下文会腐化**（Context Rot），
   摘要压缩有损且可能吃掉 62% 墙钟。<https://www.trychroma.com/research/context-rot>
5. **结构化反思**：Cybench 的 Reflection/Plan/Log 脚手架优于纯 action-only
   （GPT-4o 17.5% vs 12.5%）。<https://arxiv.org/html/2408.08926v4>
6. **子任务分解不灵**：Cybench 自己的消融显示拆 subtask 不一致（Claude 17.5%→15.0%，
   GPT-4o 12.5%→17.5%）。不要照抄"先规划再执行"。
7. **多角色架构本身不提分**：2605.21497 中单体 claude-code 在 30 道 web CTF 上
   打平工程化多段流水线（19/30）。<https://arxiv.org/html/2605.21497>
8. **不该做**：把技能文档堆进上下文（STRIATUM 四档文档量无显著差异）；
   让 agent 自评成功（62–87% 的"找到的 flag"对应不到真实利用）；
   开 web search 提分（12.59%→24.07%，但部分 flag 直接来自公开 write-up，属污染）。

## 4. 候选改动（排序；含预期、成本、验证方法、风险）

### P1（推荐先做）让 shell 发的 HTTP 进台账 —— **已落地（S1），见 §5.2**
- **问题**：`exec_command` 占 64% 的调用，模型用 curl/python 发请求；台账记不到，
  `traffic_list`/`traffic_view`/`viability_probe` 全部失效。
- **做法（最小版）**：在 `exec_command` 的守卫里解析命令文本中的 URL/方法/参数，
  以 `source="shell"` 记一条**意图记录**（无响应体）。这不需要改镜像，约 50 行。
  进阶版：镜像里放一个 `curl` shim，把请求/响应对写进台账文件（需要重建镜像，11-19 前可做）。
- **预期**：解锁已有工具的输入；同时给 P2 提供「新 URL = 新信号」的判据。
- **验证**：单测（命令→记录）+ 一场 real run 看 `traffic_list` 是否非空；
  消融：只看记录对解题率是否有影响（应无负面影响）。
- **风险**：正则误报记垃圾条目 → 只记 URL+方法，不解析 body。

### P2 停滞检测 → 注入换向指令（只追加文本，不拒绝调用）——**已有骨架，问题是判据，不是缺功能**
- **证据**：MAPTA r=−0.661；我方失败 36 次/563s vs 成功 13 次/73s。
- **已有**：`enum_guard.py` 的 `_stall_hint()`（跨族连续 K=6 次无新观测）与 `_class_hint()`
  （同一 CAPEC 机制类别连击 K=6）**都已实现**，都是只追加文本、不拦截；
  `write_stdin` 轮询也在 `PROBE_TOOLS` 里另有判据。参见 §3 的勘误。
- **真问题**：`_obs_signature()` 认为"正文前 1500 字符有任何差异 = 新信息"，
  于是失败 run 里每一次 curl 的微小差异都重置计数，提示几乎不响（19/149）。
- **做法（按证据走）**：先加**只读诊断**（`max_stall` / `max_class_streak` / hits），
  在真跑里量"失败 run 离阈值差多远"；再决定是收紧指纹（例如按**状态码 + 结构**分桶）
  还是调阈值。**不先改判据再回头找证据**。
  「新观测」定义的目标形态：新 URL / 新状态码 / 新路由形状 / 新命中（guard 计数变化）。
- **预期**：失败题调用数下降；在 10h 赛程里把省下的预算变成**多做的题数**（题量是乘数）。
- **验证**：留出 20 题 A/B；命名测试（描述里不能出现题号/路径/flag）。
- **风险**：打断合法的长任务 → 只追加提示、绝不拦截；后台任务（`write_stdin` 轮询）不算停滞。

### P3 灰盒源码优先（source_harvest）
- **证据**：AXE 灰盒 1.75×；我方 45.6% 的失败 run 碰过 source_leak 却没转化。
- **做法**：确定性工具：`.git/.svn/.map/备份/swagger/robots` 逐个试（**不是字典爆破**）→
  命中即取回 → 抽出路由/参数/密钥形态/危险 sink，输出一张小表。
  同时把「拿到源码先读源码」写成机制级规则（不含题面字符串）。
- **验证**：构造 3 个本地样例站（有 .git / 有 sourcemap / 什么都没有）做单测 + 端到端；
  真实场景 A/B。
- **风险**：像 `viability_probe` 一样没人调用 → **必须挂在 route_map 的结果尾部**
  （检测到 bundle 或框架指纹时指路），而不是只放进工具列表。

### P4（顺手）`viability_probe` 的部署默认已是 0（台账 §4.186），维持；不要复活。

### P5（备选，本窗口不做）超窗输出：落盘 + 摘要 + 可回看
- **证据**：EnIGMA 对超过 105 行的输出不截断，全文落盘、LLM 摘要进上下文、`open` 回看；
  我方 `exec_command` 占 64% 的调用，大输出（nmap/ffuf/大 JS）中段被头尾截断吃掉。
- **做法**：`_with_bounded_result` 超限时把**全文**写进本轮工作目录，返回「摘要 + 文件路径 + 行数」；
  prompt 里给一条「要看全文中段就 `sed -n 'a,bp' <路径>`」。
- **为什么本窗口不做**：它改的是上下文体积，而台账 §4.x 记过按龄裁剪导致缓存命中崩到 57.8%；
  要动就必须同时测 token/成本，属于另一条改动线。**先做完 P1/P2**。

### P6（备选，需先验前提）容器内 OOB 回连
- **证据**：NYU 在容器内起 :8000 收外带；我方 `agent_internet=deny` 下 SSRF/XSS/blind 只能看时间/错误/长度。
- **前提**：先确认 `jail.py`/netns 里进程能否 bind 端口、靶机能否回连到 agent 容器——
  **这个前提没验证之前不写任何代码**。

## 5. 今晚已落地并验证的改动

### 5.1 `tool_arg_repair`：工具参数「形状错误」修复层

- 证据：11-12 日志里 `finish_scan` 145 次调用 127 次失败，78 次是
  `{"arguments": "<json 字符串>"}`；SDK 把 JSON 解析失败与 pydantic 校验失败
  都报成 `Invalid JSON input`，模型无法自我纠正（CYBENCH-028 重试 82 次、33M token）。
- 做法：在挂载缝的**最外层**做三件事——能无损拆包就拆；不能拆就把**期望字段 + 实际发出的键**
  原样返回（内层不执行）；同一形状第 3 次起升级措辞。两个入口都装（`agent.py` +
  `run_strix_ctf.py`），并有源码级单测钉住"两个入口都得装"。
- 验证：单测 10 条全绿；VM 全量 1748 passed / 7 skipped（基线 1738/7，无回归）；
  **真题冒烟**：CTFARENA-083（allow_burned，只验接线）→ `SOLVED，14 次调用，38.5s`，
  `run.log` 出现 `[guard] tool argument repair installed`，无形状错误（正常题本就不该有）。
- 回滚：删掉两个入口的 3 行安装，或 `CTF_ARG_REPAIR=0`（若需要，可加）。

### 5.2 `shell_traffic`：shell 发出的 HTTP 进台账（P1 / S1）

- 证据：277 run 里 `exec_command` 5090 次 / `http_probe` 1099 次；`traffic_list` 27 次、
  `viability_probe` 0 次——台账读不到 shell 请求，建在它上面的东西全是摆设。
- 做法：只记录层。认 curl/wget/requests/httpx/urlopen/http.client 锚点 + 绝对 URL，
  以 `phase="shell"` 记 method+URL（**不记响应**，`status=None`，读的人不会误以为有证据）；

### 5.3 停滞判据：从「文本重复」改成「形态重复」（P2 / S2）

**方法先改**：之前判断「停滞检测不存在」是错的，判断「必须真跑才能量」也是错的。
`/var/tmp/ctfbox/<run>//strix_runs/<run>/.state/agents.db` 里存着完整的 item 流
（`function_call` 带原始参数、`function_call_output` 带模型**看到的那份结果**，
和守卫拿到的输入一致），所以 271 场历史 run 可以用**今天的守卫代码**离线重放，
不花一个 token、不碰任何靶机。脚本在会话临时目录 `replay_*.py`。

**重放测出来的三件事**（271 场：解出 143 / 失败 128）：

| 信号 | 解出组 | 失败组 | 判定 |
|---|---|---|---|
| 完全相同观测连续 ≥6 次（现行 stall） | 2/143（1%） | 9/128（7%） | 失败 run **几乎不重复同一份文本** |
| 机制类别连击 ≥6（现行 class hint） | 12/143（8%） | 37/128（29%） | 会响，但首次落在第 28 次调用（中位） |
| 覆盖的机制类别数（第 15/20/25 次调用时） | 中位 1 | 中位 1–2 | **反相关**：覆盖多的反而解出率低（36% vs 29%） |
| 每次调用换来新「响应形态」的比例 | 0.73 | 0.55 | **唯一干净的分离信号** |

结论：**失败 run 不是在原地打转，而是在"同一类页面"上高效地做无用功**——
正文每次都不同（所以文本指纹判成"新信息"），状态码/类型/体积/标签词表却不变。
把阈值从 6 降到 3 只是让一个错的判据响得更早（失败 49% / 误伤 17%），所以**不动阈值**。

**改动（一处）**：`_structure_signature()` = 状态码 | 媒体类型 | 体积档（200B） |
标签词表规模；只有带目标侧标记（`[HTTP nnn]` / `phase=`）的结果才算响应。
它**只喂 stall 计数**，`counts`/`_seen`/硬拦截仍用原来的文本指纹——
拦截需要比提示强得多的证据（分页 API 合法地重复同一形态）。
没有标记的结果（本地 `ls`、`date`）退回文本指纹，与今天完全一致。`CTF_STRUCT_SIG=0` 消融。

**离线预测（同一批 271 场，K 不变 = 6）**：

| 判据 | 失败组会提示 | 解出组会被打扰 |
|---|---|---|
| 现行文本指纹 | 7% | 1% |
| 状态+类型+体积 | 33% | 10% |
| **+ 标签词表（采用）** | **30%** | **7%** |
| + 单词桶 | 24% | 4% |

**已知风险**：盲注式提取（同一端点、同形态、不同 payload）会被提示，但只追加文本、
不拒绝调用；真正的拦截判据没动。**采纳与否看 S2 的 A/B**（判据在 §9 预注册）。

**踩坑**：`body.lstrip()[:1] in "{["` 对空 body 恒为真（空串是任何串的子串），
空响应体被当成 JSON——单测当场抓到。

## 7. 附件：可执行的漏洞族决策表（给 P2/P3 用）

来源：OWASP WSTG v4.2、PortSwigger Web Security Academy、HackTricks。要点：

1. 先建立基线（status/长度/头/耗时），之后一切判断都是 diff。
2. 最高性价比的两档：**源码/元文件泄漏**（`.git`、`.map`、备份、注释、robots）
   与**认证/授权边界改值**（删 cookie、id±1、加 role 字段）——先吃掉这两档再做别的。

   看回显/报错/长度差异；无差异立刻换族。
4. 无外网时的强制降级：SSRF 用 `127.0.0.1:<同端口>` 与错误文本/长度/耗时三 oracle；
   XXE 用错误型回显；盲 SQLi 用 time-based；JWT 弱密钥离线爆破（hashcat -m 16500）。
5. 反蛮力：目录爆破、参数喷洒、整包 sqlmap/nuclei 在单题上性价比低——
   路由应从 JS/源码/报错里取，而不是猜。

### 9.4 P5 的前提也被证伪（2026-11-15，同日，零 token）

§3 的分支是「S4 证伪 → 改做 P5」，所以在写任何代码之前，先量 P5 的前提——

| 证据面（453 run / 12,259 条工具输出） | 值 |
|---|---|
| 输出字节 p50 / p90 / p99 / max | 550 B / 3.3 KB / 16.7 KB / **51,039 B** |
| >10 KiB 的输出 | 285 |
| **>50 KiB（会触发截断）** | **0** |
| 截断通知（`[... N lines ... truncated ...]`） | **4 条，全部是 `load_skill`** |
| 落盘通知（`full output saved to …`） | **0 条** |
